AutoRefine：检索之后先提炼，再继续想

传统检索增强推理把整篇文档直接塞回上下文，模型要在噪声里自己找证据。AutoRefine 在每次 <search> 之后强制插入一个 <refine> 块：先过滤、蒸馏、整理文档，再决定下一步搜什么或直接作答。训练用答案奖励加检索奖励，走 GRPO。

Yaorui Shi 等 · USTC / DP Technology / NUS 原文 ↗ 代码 ↗
TL;DR · 30 秒抓住核心

搜索动作解决“去哪里找”，refine 动作解决“找到之后留下什么”。AutoRefine 把后者显式写进轨迹模板，并用一个二值检索奖励要求 refine 文本覆盖标准答案的全部词。

奖励是分段的：答案 F1 大于 0 就拿 F1；答案错但 refine 覆盖了标准答案，给 0.1；两者都没有，给 0。这样即使最终没答对，中间提炼对了也有学习信号。

Qwen2.5-3B-Base 上，七个 QA 基准平均 EM 0.405；比表内最强基线 Search-R1-Instruct 的 0.336 高 0.069（相对 20.54%），比同底座 Search-R1-Base 的 0.312 高 0.093（相对 29.81%）。

边界：只测 3B/7B；检索语料是 2018 年 Wikipedia 快照；指标以 EM/F1/CEM 为主；refine 增加生成步骤，但论文没有给端到端延迟与费用账。

问题不是“搜不到”，而是“搜到了却不会用”

这一节建立问题：search-during-think 范式把检索和推理交替起来，但缺少一个显式的证据整理步骤。

RAG 的常见流程是：模型发现问题需要外部知识 → 发一次搜索 → 拿到若干文档 → 直接在这些文档上生成答案。论文把这种范式叫 search-during-think。它比“不检索”强，但有两个结构性弱点。

第一，文档是噪声和信号的混合物。检索器按相关性返回 top-k 文档，其中可能包含错误实体、过时信息、与问题无关的段落。模型没有显式的“先筛再答”步骤，噪声会直接进入后续推理，错误答案因此被放大。论文 Figure 1(a) 的例子是“David Beckham 最后效力的球队的主场在哪”：同一篇文档先写他出道于 Manchester United，末尾才写他最后效力 Paris Saint-Germain；直接读文档的 previous method 搜 Manchester United、答 Old Trafford，AutoRefine 先 refine 出“David Beckham's last professional team was Paris Saint-Germain”，再答 Parc des Princes。

第二，奖励只落在最终答案上。如果只用答案正确性做 RL 奖励，一条轨迹只有最后 0/1 或 F1 一个标量；中间“有没有找到关键证据”没有被单独评价。对多跳问题，这会让模型难以学习“先找到中间实体，再用它去搜下一步”的行为。

AutoRefine 的切入点不是换检索器，也不是换更大模型，而是在轨迹里加一个 <refine> 动作，并给这个动作单独设计奖励。检索仍然由同一个 E5 检索器完成，变化发生在模型如何使用检索结果。

这些方法的共同点是：模型学会在推理中调用搜索，但检索回来的文档仍然被直接拼进上下文。AutoRefine 的区别只在模板和奖励：模板多一个 <refine>，奖励多一个 RRet。论文没有换检索器，也没有换底座，这让消融能比较干净地归因到这两个改动。

03

关键不是搜索，而是搜索后的显式提炼

这一节拆两件事：refine 在轨迹里长什么样，奖励怎么算。

轨迹：think → search → documents → refine → … → answer

一条轨迹由若干步组成，每步可以是一个 <think>、一个 <search>、一个 <documents>、一个 <refine> 或最终的 <answer>。<search> 产生查询，检索器返回文档；文档被放进上下文后，模型必须先写一个 <refine> 块，把与问题相关的证据提炼出来，再决定继续搜索还是作答。

这个模板强制模型在“读文档”和“用文档”之间插入一个可观察的中间产物。refine 文本既是下一步推理的上下文，也是检索奖励的评估对象。

答案奖励：F1

RAns 把预测答案与标准答案都看成词集合，用 F1 计算重叠：

RAns = F1(oans, a) = 2·|oans ∩ a| / (|oans| + |a|)
答案完全正确时 F1 = 1；部分词重叠时介于 0 和 1 之间。公式 (1)。

检索奖励：refine 是否覆盖标准答案

RRet 是一个二值指示函数：把整条轨迹里所有 <refine> 块的内容拼成 orefine，如果标准答案的每个词都出现在其中，就给 1，否则给 0。公式 (2)：

RRet = 𝟙(a ∩ orefine = a)
注意：奖励只统计 refine 文本；把文档留在 <documents> 里不算，但把整篇文档抄进 refine 也能通过覆盖检查——它约束的是覆盖，不是精简。

组合奖励：先保答案，再给部分学分

总奖励 ROverall 不是简单相加，而是分段函数：

ROverall = RAns  如果 RAns > 0
ROverall = 0.1  如果 RAns = 0 且 RRet > 0
ROverall = 0  如果 RAns = RRet = 0
公式 (3)。答案对时直接用 F1，避免检索奖励稀释答案质量；答案错但提炼对时给 0.1，作为中间步骤的部分学分。

论文在 Appendix C.3 对比了线性组合 RAns + RRet 和这个非线性设计，结论是非线性更好；作者假设是线性组合会过度强调中间行为。这个消融只在附录报告，主表没有展开。

优化：GRPO，检索文档的 loss 被 mask

训练用 GRPO。每个问题采样一组 G 条轨迹，用组内相对优势更新策略；检索回来的文档 token 不参与 loss，只有模型自己生成的 think/search/refine/answer token 参与。这样模型学到的是“怎么搜、怎么提炼、怎么答”，而不是“怎么复述文档”。

底座。主实验用 Qwen2.5-3B 的 Base 与 Instruct 两个版本；v5 另加 Qwen2.5-7B 的规模消融（Table 3）。检索器固定为 E5-base-v2，知识源是 2018 年 12 月的 Wikipedia dump，每次查询取 top-3 文档。

数据。训练集由 NQ 与 HotpotQA 的 train split 合并，共 169,615 条；评测集由七个数据集的 test/dev split 合并，共 51,713 条。NQ、TriviaQA、PopQA、Bamboogle 用 test split；HotpotQA、2Wiki、Musique 没有 test split，用 dev split。

发现 1：refine 把上下文压短，但保留答案词

论文对 Figure 5(a)(b) 的正文描述是：refine 块大约 100–200 token，检索文档（documents 块）至少约 600 token；同时 refine 动作的成功率与 <search> 动作接近。页面不把这些正文数值当表格数字，只引用正文的近似区间。机制上，RRet 要求标准答案的词出现在 refine 文本里，这直接逼着模型保留关键实体，而不是写一段泛泛的摘要。推断（由公式 (2) 的覆盖条件反推）

发现 2：单跳涨得少，多跳涨得多

Base 上 NQ 0.467 对 Search-R1-Base 0.421（+0.046），TriviaQA 0.620 对 0.583（+0.037），PopQA 0.450 对 0.413（+0.037）；多跳的 2Wiki 是 +0.119，Musique 是 +0.091（0.157−0.066）。单跳问题通常一次搜索就能拿到答案，refine 的边际收益小；多跳问题需要把上一轮的证据整理成下一轮的查询，refine 的作用更大。这与论文的动机一致，但论文没有做“单跳/多跳分别训练”的对照，不能把差异完全归因于任务类型。推断

07

它解决不了：静态语料、3B/7B 规模、没有延迟账

这些限制决定了 0.405 能推广到哪里，以及“refine 更聪明”是否等于“系统更可用”。

限制 1

知识源是 2018 年的静态快照

检索器是 E5-base-v2，语料是 2018 年 12 月的 Wikipedia dump。实时搜索、网页广告、格式多变、时效性问题都没有覆盖；论文在 Limitations 里把 static retrieval corpus 列为限制。

限制 2

只测 3B 与 7B

v5 加了 7B 规模消融，但没有 70B、MoE 或 API 模型。更大模型是否还需要显式 refine，论文没有回答；v1 的 Limitations 原句是 “all experiments in this paper use 3B-parameter language models”，v5 已改成只列指标与静态语料。

限制 3

没有端到端延迟/费用

refine 是额外的生成步骤，搜索最多 5 轮；论文没有报告墙钟延迟、token 成本或费用。准确率提升是否值得这些开销，需要按场景测。

指标覆盖有限。主表用 EM；v5 的 Table 3 加了 F1 与 CEM，但仍以短答案 QA 为主。长答案、开放式生成、需要引用来源的任务没有实验。EM 对同义改写很苛刻，F1 也只能看词重叠，不能判断事实一致性。

奖励可以被“提取”而不是“理解”。RRet 只检查标准答案的词是否出现在 refine 文本里。如果标准答案是一个短实体，模型可以把含答案词的文本甚至整篇文档抄进 refine 拿到奖励，而不一定理解它。论文用“refine 在原始文档之后、答案之前”的模板降低这种风险，但没有做 reward hacking 实验。推断

什么时候别用：如果任务只需要一次检索、答案是一句短事实，refine 的额外生成可能是多余开销；如果知识源必须实时更新，2018 年快照不适合；如果需要引用级可追溯性，refine 文本不是引用，仍需额外做来源对齐。反过来，在多跳、文档噪声大、答案需要跨文档整合的任务里，AutoRefine 的思路最直接：先把证据整理成可检查的中间文本，再继续推理。
