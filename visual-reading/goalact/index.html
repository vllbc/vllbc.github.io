GoalAct：每一步都重排一张全局计划，执行时只挑「技能」

ReAct 每步只看眼前，容易卡进局部分支；Plan-and-Execute 先给全局计划，却常常超出 Agent 的动作空间。 GoalAct 在每个时间步重新生成一张由「计划步骤 + 技能」组成的全局计划，执行层再按技能选择 Searching / Coding / Writing 等分工。 代价是按 Table 4 的 prompt，每步通常要一次规划调用推断，而且它在 LegalAgentBench 上的证据全部来自 API 模型的黑盒对比，不是训练出来的能力。

Junjie Chen, Haitao Li, Jingli Yang, Yiqun Liu, Qingyao Ai · 清华大学 DCST arXiv 2504.16563v3 ↗ 代码仓库 ↗
TL;DR · 30 秒抓住核心

论文把 Agent 的两个环节分开骂：规划层「要么没有全局目标，要么计划很难执行」；执行层「复杂度与稳定性不可兼得」。 GoalAct 的计划只写到技能粒度：G = (P₁A₁, …, PₙAₙ)，每个 Aᵢ 是一个高级技能，最后一步被指定为 Finish。

和 Plan-and-Execute 的区别在于：它每一步都用 Gₜ = π(Q|T|Sₜ) 整体重算计划，Sₜ 是此前的「计划步骤—动作—观察」三元组历史。 好处是计划永远贴着最新观察走，代价是按 Table 4 的 prompt，每步通常一次规划调用推断。

证据只有一个基准（LegalAgentBench，300 题）和三个 API 模型。在「同一模型内」比较最强基线，三个模型分别高出 14.45 / 10.09 / 12.11 个百分点（绝对值），均值正好是论文反复引用的 12.22。 论文在同一段里把这个数称作「average improvement of 12.22%」，口径问题见 06 节。

01

规划要么没方向，要么不可执行；执行要么太脆，要么表达力不够

读完这一节，你应该知道 GoalAct 想同时堵上的两个口子分别在哪里。

论文在 §1 把问题拆成两层，每一层都点了一种典型框架的毛病：

规划层

局部最优 vs 不可执行

ReAct 用「Thought-Action-Observation」增量推理，"focusing only on the immediate step without a comprehensive global perspective"（§1），在多分支任务里"frequently become stuck in local optima"。

Plan-and-Execute 会给全局计划并按反馈调整，但"often fail to effectively integrate concrete executable actions into the global plan, resulting in plans that exceed the agents' action space"（§1）。

执行层

简单格式不够用 vs 代码太脆

ReAct 用 text / json 调工具，"lack the capability to handle complex logic structures, such as loops and conditional branches"（§1）。

CodeAct 用 Python 代码统一动作空间，表达力上去了，但"highly complex invocation logic is more prone to errors, making the system less stable"；而且并非所有任务都靠代码解决，论文点名了法律文书生成与 Lateral Thinking Puzzles。

在 Figure 2 的案例里，这句设计判断有具体的失败画面：

ReAct："No data found for the specified identifier." 连试多次 → "Get stuck in local branch!"
CodeAct：一次代码里串多个工具 → "Use too many tools in a single code!"
GoalAct：先 Coding 排序找最高金额案件，再 Searching 查被告
Figure 2，GLM-4-Plus 为底座模型（§4.2.3）

关键的共同点是：两个毛病都发生在「计划要写多细」这个决策上。写得粗，计划落不了地；写得太具体、或者根本不独立规划，又会在环境反馈变化时失去方向。GoalAct 的切入点就是把「写什么粒度」固定下来。

CodeAct

03

把计划写成技能序列，每一步整张重算

读完这一节，你应该能用两条公式说清 GoalAct 与 Plan-and-Execute、ReAct 的差别，并用下面的重放器亲手复现 Figure 2 里那条轨迹。

全局计划 = 一串「计划步骤 → 技能」

G = (P₁A₁, P₂A₂, P₃A₃, …, PₙAₙ)
Eq. (1) · Pᵢ 是第 i 个计划步骤，Aᵢ 是它对应的动作；"The final step, An, is always designated as Finish."

论文原话：由于在全局计划里直接写详细动作描述很难，"we only require the specification of high-level skills"（§3.1）。计划层只需要指定高级技能，不必写出内部执行细节；Figure 2 的 Action 1 里仍留有表名、字段等较粗的参数描述。

每一步都用历史重算整张计划

Gₜ = π(Q | T | Sₜ)    Sₜ = (P₁A₁O₁, P₂A₂O₂, …, Pₜ₋₁Aₜ₋₁Oₜ₋₁)
Eq. (2) 与 Eq. (3) · Q 是用户查询，T 是可用工具集，Oᵢ 是动作 Aᵢ 的观察；t = 1 时 Sₜ 为空

三个要点（前两条取自原文，第三条是本页的形式化）：

  • π 被写成「策略」，实际载体是 prompt。π 被定义为「update policy (detailed in the Table 4)」，Table 4 是完整的规划 prompt，要求模型返回 [{"Thinking": "", "Action": ""}] 的 JSON 数组。推断（依据：Table 4 的输入输出格式）：按 Eq. (2) 每步重算计划，Table 4 的 prompt 表明这一步通常是一次 LLM 规划调用；原文未说明它是否与执行调用合并。
  • Table 4 的转录范围：Table 4 为 prompt 全文，本页未逐字转录，仅引用其输出格式与 {tool_prompt} / {memory} / {scratchpad} 占位符。
  • 历史是三元组，不是自由文本。Sₜ 的每个元素是 PᵢAᵢOᵢ，每个过去的步骤都带观察 Oᵢ，这就是「计划贴着执行走」的具体机制。
  • 重算没有把上一版 G 作为输入。Eq. (2) 的右侧只有 Q、T、Sₜ。本页把它称为「整张重算」是据此的形式化；Figure 2 只在 "Global Plan (updated)" 节点给出了更新后计划的第一条（"Plan Step 1 : Next, we need to query the defendant company name …"），计划是否与上一版逐条对应，原文没有展示。

执行层：三种技能，各自吃自己的格式

技能调用形式（Figure 1 / §3.2）适合论文点名的短板
Searching Text / Json 格式，含 tool_name 与 arguments 简单探询；"simplicity and stability in complex external environments" "cannot handle complex tool calls or data processing logic, such as conditional branches and loops"
Coding Python Code，可写 loops / branch，可用 max/sort/sum 复杂逻辑；"expanding the agent's action space and enhancing execution efficiency" "even the most sophisticated code can produce unforeseen bugs"
Writing Special Process：gathering info → first draft → polishing… 法律文书这类"cannot be effectively addressed through either Searching or Coding" 的任务 §3.2 未点名 Writing 的短板
Other Skills Figure 1 列出 Reasoning… / Research… / Create… "expanding the skill pack according to task-specific requirements" §3.2 原文："this expansion process is easy and highly iterative"；未给实现细节

技能表来自 Figure 1 与 §3.2 的描述；表格里没有给出各技能内部的具体工具名、参数 schema 或 Writing 的流程实现。

手算两组：步数怎么数、删除后剩几步与回放器逐位对账

回放器里唯一的派生数值是「已走步数 / 总步数」。常量直接取自 Figure 2 的可见节点；英文原句逐字转写如下（readout 为中文概述，不是逐字翻译）：初始 Global Plan: […]；Plan Step 1: First, we need to query all cases involving Anhui Ankang Law Firm … 与 Action 1: Coding[Query the LegalDoc table to retrieve all cases involving Anhui Ankang Law Firm, returning the case number and monetary amount fields. …]（含 Observation 1）；Global Plan (updated): […]、Plan Step 1 : Next, we need to query the defendant company name … 与 Action 2: Searching[Search the LegalDoc table for the case with case number (2020) Wan 0603 Min Chu 2364 and return the defendant field]（含 Observation 2）；最后是 "…."。Figure 2 可见四块（初始计划、Plan Step 1 + Action 1、更新后的计划、Plan Step 1 + Action 2），加上 "…." 收敛节点，回放器共 5 个节点（初始计划与合并的「Plan Step 1 + Action 1」各算一个节点）。

第 1 组（默认，data-f = 0）：节点序列为 [0,1,2,3,4]，共 5 个节点；len = 5；第一次点「下一步」时 k = 1，进度 = 1/5 = 20%，即 round(1/5 × 1000)/10 = 200/10 = 20.0，读数为「已走 1 / 共 5 步，位于节点 1」。

第 2 组（不给搜索，data-f = 1）：删除下标 2、3（Global Plan 重排、Searching 查被告），剩下 [0,1,4]，len = 3；点两步后 k = 2，进度 = round(2/3 × 1000)/10 = round(666.67)/10 = 667/10 = 66.7，读数为「已走 2 / 共 3 步，位于节点 2」。

其余两种设置同理：去掉重排（data-f = 3）去掉的是下标 2（Global Plan 重排），序列 [0,1,3,4]，len = 4；点 1 次得 round(1/4 × 1000)/10 = 250/10 = 25.0%。不给编码（data-f = 4）序列 [0,5,3,4]，共 4 个节点；其中下标 5 是回放器新增的合成节点「Action 1 · Searching」，用来替代原来的 Coding（已在面板中声明为回放器自定）；点 2 次得 round(2/4 × 1000)/10 = 50.0%。进度 = round(k / len × 1000) / 10（百分比保留一位小数，四舍五入）。保持默认设置（5 节点）时点 3 次得 round(3/5 × 1000)/10 = 60.0%；不给搜索时点 3 次（走完）得 round(3/3 × 1000)/10 = 100.0%。回放进度只依赖节点数，不含任何耗时或 token 估计。

04

成本是一条串行链：每步通常一次规划 + 每个技能内部若干次调用

读完这一节，你应该知道这套方法的开销由什么决定，以及论文对开销交代到了哪一步。

按 Eq. (2) 与 Table 4 的 prompt，每步通常伴随一次规划调用推断；原文未说明规划调用与执行调用是否合并。GoalAct 本身没有训练阶段：三个基础模型全部经 API 调用，温度设为 0（§4.1.2），所以「怎么算」的问题只剩推理侧的开销。

每个任务 ≈ Σt=1..T [ 至多 1 次 π(Q|T|Sₜ) 规划调用 + 技能 Aₜ 内部的 nₜ 次工具/LLM 调用 ]
依据 Eq. (2)（π 由 Table 4 的 prompt 承载）与 §4.1.2 的迭代上限 T = 10；「至多 1 次」是因为原文没有说明规划调用与执行调用是否合并；nₜ 与整个 Σ 是本页为说明成本结构写出的形式化，原文没有给出这个公式
  • 串行：Gₜ 依赖 Sₜ，而 Sₜ 依赖 Aₜ₋₁ 的观察，步与步之间无法并行。
  • 终止条件："When the LLM outputs Finish or reaches the maximum iteration limit T = 10, it summarizes the current trajectory and provides the final answer."（§4.1.2）。
  • prompt 已固定：每个流程给两个示例引导工具使用与输出格式（§4.1.2）；Table 4 显示规划 prompt 里带了 {tool_prompt}、{memory}、{scratchpad} 三块内容，推断（依据：Table 4 模板）这三块会随任务变长而变长，单步规划调用的输入 token 也随之增长。
  • 没有量化的部分：论文没有报告 token 消耗、延迟或 API 费用，也没有给出 GoalAct 与 ReAct / CodeAct 的调用次数对照。Table 1 给出任务规模、query/answer 长度与关键元素统计；Writing query 平均长度 1059.95、answer 平均长度 678.75（Table 1 只写 Avg. length，长度单位按词计为本页表述）；不含调用次数，不能直接换算调用成本。
工程含义

「每步重算」是一个明确的可调旋钮

如果重排是收益的主要来源，那么减少重排次数（例如每两步重排一次）应当是最直接的省成本手段。但论文没有做这一消融：w/o global plan 是移除全局规划模块，不是降低重排频率；具体如何降级论文未说明推断（见 06 节的白盒变体）。

Table 2 的 ALL 列是怎么合成的按 Table 1 题数加权，15 行全部复现

Table 1 给出每类任务题数 80 / 80 / 60 / 40 / 20 / 20（合计 300）。用这组题数对六列加权：ALL = (80·1-hop + 80·2-hop + 60·3-hop + 40·4-hop + 20·5-hop + 20·Writing) / 300。逐行复算后，Table 2 的 15 行全部等于打印的 ALL（最大差 0.0001），所以 ALL 是按题数加权的平均，不是六列等权平均。

加权与不加权的差距：GoalAct 行 3.44 pp，Table 3 的 w/o global plan 行 1.85 pp；Table 2 的 15 行与这一行合起来（16 行）的范围是 1.85–11.21 pp。以 GLM-4-Plus 为例：GoalAct 加权 0.8710（与 ALL 逐位相同）、不加权 0.8366；w/o global plan 加权 0.7896（与 ALL 相同）、不加权 0.7711。

另外，0.7117 × 80 × 1.88 = 107.04 是「成功率 × 题数 × 每题关键元素数」得到的命中 key_answer 元素期望数，不是题数；1.88 与 2.25 是 Table 1 的「# Avg. key_answer per query」，不能用来反推题数。

07

什么时候不能直接拿 GoalAct 的结论用

这节只列论文自己能查到的边界：单一基准、单次运行、正文未给实现细节、没有开销数据。

边界一

只有一个领域、一个基准

全部实验都在 LegalAgentBench 上（§4.1.1），任务类型是 1-hop 到 5-hop 的法律问答与辩护文书写作。论文未在其他领域（代码、科研、开放网页）上评测；§3.2 只是提出「reasoning / research / creative」等扩展技能的设想，没有对应实验。

边界二

单一运行、无方差、无显著性检验

论文没有报告重复运行的均值±方差，也没有做显著性检验。Table 2 里的差距中最小的是 Qwen-max 5-hop：0.6117 vs 0.6083，仅 0.34 pp。推断（依据：该列 baseline 值 0.6083 出自 ReAct，且论文无方差信息）：这一格更可能落在随机波动范围内，不能当作「GoalAct 在 5-hop 上普遍更强」的证据。

边界三

官方仓库有代码，但正文没有复现级细节

Abstract 写 "Our code can be found at https://github.com/cjj826/GoalAct"，仓库 public，确实有代码。但论文给出 Figure 1–2、Eq. (1)–(4)、Table 1–4，没有基线/skill 代码清单或超参数细节；无法从论文判断仓库是否与 v3 的实验代码一致。本页未逐行核对仓库内容，也未用仓库作为出处。

边界四

没有成本对照，「每步重算」的代价未量化

§4 没有报告 token、延迟或费用。按 Eq. (2) 每步都要重算计划；Table 4 的 prompt 表明这一步通常是一次规划调用推断，但原文未说明它是否与执行调用合并。单次规划调用在 Table 4 的 prompt 下有多长、GoalAct 相对 ReAct / CodeAct 多调用多少次，论文没有给数。若部署对成本敏感，这一段是本方法的主要风险。

边界五

技能的扩展性只有设计论证

§3.2 称扩展技能 "easy and highly iterative"，但实验中没有新增或评测三个技能之外的技能，也没有新增技能的成本测量。Writing 技能只在一个 20 题的类别上评测（Table 1）。

一句话：GoalAct 在这个基准上证明了「计划写到技能粒度 + 每步重排」比四种常见组织方式在 API 模型上更有效，并且消融显示三个技能都不可少；但要把它搬进自己的系统，最需要先补上的是开销对照与跨领域验证，这两块论文都没有给。
