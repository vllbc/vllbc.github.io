Llama 4：
400B 的容量，17B 的算力，10M 的上下文

Llama 4 没有继续把稠密模型放大。Maverick 用 400B 总参数、17B 激活参数和 128 个 routed experts， Scout 用 109B 总参数、17B 激活参数和 16 个 experts，把“存多少”和“每 token 算多少”拆成两本账。 两者都把文本与图像 token 放进同一个 backbone（early fusion）；Scout 的输入上下文标到 10M。 代价是全部专家都要进显存，路由与长上下文泛化仍缺公开细节。

TL;DR · 30 秒抓住核心

Llama 3 405B 是稠密模型：每个 token 都要过 405B 参数。论文为它花了 3.8×1025 FLOPs、15.6T 文本 token， 并在 最多 16K 张 H100 上训练；BF16 MFU 是 38–43%。容量、显存和每 token 计算绑在同一根轴上。

Llama 4 把账拆开。Maverick 是 400B 总参数、 17B 激活参数，MoE 层用 128 routed experts + 1 shared，每个 token 走 shared 和 1 个 routed； Scout 是 109B 总参数、17B 激活、16 experts。 激活占比分别是 4.25% 与 15.6%。

收益不是“全面”的。同表 bf16、同 #shots/metric 下，Maverick 的 MMLU 比 Llama 3.1 405B 高 0.3 个百分点（85.5 − 85.2），MATH 高 7.7 个百分点（61.2 − 53.5）；TydiQA 低 2.6 个百分点（31.7 − 34.3）。 跨代模型不是受控消融，不能把差值全部归因于 MoE。

01

稠密 405B 的每个 token，都要付 405B 的账

Llama 3 把规模推到 405B dense；这同时抬高了训练 FLOPs、权重容量和每 token 的计算，三者没有分开的旋钮。

Llama 3 的旗舰模型是 dense Transformer：405B 个可训练参数， 15.6T 个文本 token，预训练上下文 8K，继续预训练后到 128K；训练预算约 3.8×1025 FLOPs。 论文给出的硬件上限是 16K 张 H100，每张 700W、80GB HBM3； 在 Table 4 的三组配置里，BF16 MFU 为 38–43%。

dense 的意思是每个 token 都经过全部 405B 参数。总参数一涨，权重容量、每 token 的权重读取和训练 FLOPs 一起涨； 想把“知识容量”做大，就得同时接受“每 token 更贵”。MoE 的切入点正是把这根轴拆成两根： 总参数决定容量与存储，激活参数决定每 token 的计算。

第二条轴是上下文。Llama 3 的 128K 已经需要继续预训练来扩；再往上到 1M/ 10M，attention 与 KV cache 的成本、 位置编码的外推都会变成独立问题。Llama 4 的 iRoPE 就是针对这条轴的设计（§05）。

第三条轴是多模态。Llama 3 论文把图像、视频、语音能力作为 compositional approach 接在语言模型上 （Abstract）；视觉模块并不是与文本从预训练一开始就共享同一个 backbone 推断（依据：论文称其为 compositional approach，且视觉实验与语言预训练分开描述）。 Llama 4 改用 early fusion，把 text 与 vision token 放进统一 backbone （博客 §Pre-training）。这让“多模态”不再是后接适配器， 而是预训练数据与架构一起变。

核心矛盾

容量、每 token 计算、上下文/多模态，是三本账

继续放大 dense 能同时改善三本账里的“容量”，但会把“每 token 计算”一起抬高；后接视觉模块能把多模态做出来， 但视觉与语言没有共享同一个预训练 backbone。Llama 4 的选择是：MoE 拆容量与计算，early fusion 拆语言与视觉， iRoPE 拆上下文长度与位置外推。

02

两条旧路：继续放大 dense，或把视觉后接

Llama 3 用 dense + compositional vision 把能力做上去；Llama 4 换成 MoE + early fusion，把成本和模态都换了一种摊法。

路线 A

dense 继续放大

Llama 3 405B 的做法：所有 token 过全部参数。优点是行为可预测、并行实现成熟； 缺点是每 token 的权重读取与 FLOPs 随总参数线性增长。Table 4 的三组配置给出的 BF16 MFU 分别是 43%、41%、38%，三组并不相同。

路线 B

MoE 稀疏激活

Llama 4 的做法：总参数 400B， 激活 17B；MoE 层用 128 routed experts + 1 shared，每 token 只走 shared 和 1 个 routed。 优点是容量与每 token 计算解耦；缺点是所有专家都要存，路由、负载均衡和专家并行带来新的系统问题。

多模态 A

compositional：后接视觉模块

Llama 3 论文把 image/video/speech 作为 compositional approach 接在语言模型上 （Abstract）。模块边界清楚，但视觉与语言不是从预训练第一步就共享 backbone 推断（依据：论文将视觉实验放在单独的 Vision Experiments 章节，语言预训练在前）。

多模态 B

early fusion：统一 backbone

Llama 4 把 text 与 vision token 在入口就合进同一个 backbone，并用基于 MetaCLIP、但与 frozen Llama 分开训练、配合使用的视觉编码器 （§Pre-training）。这样可以用未标注的 text/image/video 联合预训练， 代价是数据配比与模态对齐更复杂。

MoE 本身不是 Llama 4 才有的想法；这页的重点是 Llama 4 的具体配置： 128 routed + 1 shared、 每 token 选 1 个 routed expert（选择规则未公开，博客只写 “one of the 128 routed experts”）、alternating dense/MoE， 以及 Scout 的 16 experts。 另一个容易被忽略的变量是蒸馏：Maverick 从 Behemoth （288B active、16 experts、近 2T total） 做 teacher 蒸馏（博客 §2T Behemoth）。因此后面的 benchmark 差值不能只归因于 MoE 结构。

03

Maverick 每个 token 只走 shared + 1/128 个 routed expert

MoE 把总参数与激活参数拆开；early fusion 把图像 token 放进同一个入口；iRoPE 把长上下文外推交给交错注意力。

MoE：容量按总参数算，计算按激活参数算

Maverick 的配置是 400B 总参数、 17B 激活参数、 128 routed experts + 1 shared expert。 每个 token 同时送入 shared expert 和 router 选出的 1 个 routed expert（博客未写先后/串并联关系）；其余 127 个 routed experts 只存在显存里， 不参与这个 token 的计算。层与层之间是 dense 与 MoE 交替 （alternating dense and MoE layers）。

激活占比 = active / total = 17 / 400 = 4.25%   |   单 token 路由覆盖 = 1 / 128 = 0.78125%
Maverick 的口径；17B 与 400B 来自 Llama 4 model card §Model Information，128 routed 来自 Meta 博客 §Pre-training。 0.78125% 只是 routed expert 的覆盖比例，不含 shared expert、attention 与 embedding。

Scout 的配置是 109B 总参数、 17B 激活参数、 16 experts。 博客只对 Maverick 明确写了“128 routed + 1 shared、每 token 走 1 个 routed”；Scout 的路由条数与 shared expert 细节未获取。 不要把 Maverick 的 1/128 直接套到 Scout。

“17B 激活”是一个 per-token 口径，不等于 17B 显存。模型卡与博客均未给出 17B 的内部拆解 （shared expert、attention、embedding 各占多少），也未给出路由负载均衡损失、router 温度或专家并行的通信量； 这些细节未获取。能做的是把两本账分开：存储按 total，计算按 active。

Early fusion：text 与 image token 在入口合并

Llama 4 的 native multimodality 走的是 early fusion：博客说 text 与 vision token 在预训练阶段就合进同一个 model backbone，并说这样可以用大量未标注的 text、image、video 数据联合预训练。视觉编码器基于 MetaCLIP， 但与 frozen Llama 分开训练、配合使用，以适配 LLM（博客 §Pre-training）。

条件要写清：模型卡说预训练数据是“multilingual text and image”，输出是“multilingual text and code” （§Model Information）；博客说预训练用了 image 与 video frame stills， 模型预训练见过最多 48 张图，后训练测试到 8 张。模型卡又说 image understanding 测试到 5 张输入图。三处条件不同，页面并列呈现， 不合并成一个“最大图像数”。

iRoPE：不是所有层都加位置编码

iRoPE 的“i”是 interleaved：一部分 attention 层不加位置编码，另一部分仍用 RoPE；再配合推理时对 attention 的温度缩放 （inference time temperature scaling of attention）做长度外推。博客给的名字解释是“interleaved attention layers”， 长期目标是支持“infinite” context（§Post-training）。

Scout 在预训练与后训练阶段用 256K 上下文， 模型卡标称支持 10M 输入；Maverick 标称 1M。10M 是最大输入长度的能力声明，不等于 10M 上的有效检索； 博客提到的 needle-in-a-haystack 与 10M code NLL 未给出具体数值；模型卡也未提供对应的 10M 评测表（未获取）。

04

训练账本：40T/22T token，7.38M GPU hours，FP8 + MetaP

Llama 4 用更多 token、FP8 和超参迁移把 MoE 训练跑起来；推理侧则按 active 参数而不是 total 参数算每 token 成本。

单模型预训练 token：Scout ~40T，Maverick ~22T。博客给出的整体数据混合是 >30T token，超过 Llama 3 混合数据的 2×；语言覆盖 200 种， 其中 100+ 种 各超过 1B token，多语 token 总量是 Llama 3 的 10×。这些数字的条件是“整体混合数据”，不能拿来替换 Scout/Maverick 的单模型 token 数。

训练技术上，博客点名了 FP8 与 MetaP：MetaP 用来设定 per-layer learning rate 与 initialization scale， 并声称这些超参能跨 batch size、width、depth、training tokens 迁移 （§Pre-training）。FP8 的具体 recipe （scale 粒度、amax 历史、哪些算子留高精度）博客未展开，未获取；能确认的是 Behemoth 用 FP8 在 32K GPUs 上跑到 390 TFLOPs/GPU，这是 Behemoth 的数字，不是 Scout/Maverick 的。

手算：总参数 / 激活参数与精度 与上面的交互逐位一致

组 1（Scout，BF16）：总参数 109B，激活 17B，2 B/参数。

  • 权重存储 = 109×2 = 218.0 GB；每 token 权重读取 = 17×2 = 34.0 GB。
  • 激活占比 = 17/109×100 = 15.60%；总/激活 = 109/17 = 6.41×。

组 2（Maverick，FP8）：总参数 400B，激活 17B，1 B/参数。

  • 权重存储 = 400×1 = 400.0 GB；每 token 权重读取 = 17×1 = 17.0 GB。
  • 激活占比 = 17/400×100 = 4.25%；总/激活 = 400/17 = 23.53×。

这个模型简化了什么：只算权重存储与每 token 的权重读取，假设 active 参数都按同样的字节宽度存放； 不含 KV cache、激活、optimizer、通信 buffer、shared expert 的实际尺寸与路由开销。 覆盖“总参数 / 激活参数 / 每参数字节”三个变量；未覆盖专家并行、路由负载不均衡和量化误差。 JS 与手算都用十进制 GB（109 B），GB 保留一位小数，百分比与倍数保留两位。

05

一个 token 的路径：early fusion → 交替 dense/MoE → iRoPE

文本与图像在 backbone 入口合并；每层要么 dense，要么 shared + 1 个 routed expert（选择规则未公开）；长上下文靠交错注意力外推。

逐步拆开：哪些张量进哪个模块

  1. 输入。文本 token 与图像 token 进入同一个 backbone；博客说预训练用了 image 与 video frame stills，模型见过最多 48 张图，后训练测试到 8 张（§Post-training）。模型卡另说 image understanding 测试到 5 张输入图（§Intended Use 注 2）。
  2. Early fusion。视觉编码器基于 MetaCLIP，但与 frozen Llama 分开训练、配合使用；text/vision token 在入口合并（§Pre-training）。
  3. 层栈。dense 与 MoE 交替；Maverick 的 MoE 层是 shared + 1/128 routed，Scout 是 16 experts。
  4. iRoPE。部分 attention 层不加位置编码，其余用 RoPE；推理时对 attention 做温度缩放（§Post-training）。
  5. 部署。Scout 以 BF16 发布，可用 on-the-fly int4 量化放进单张 H100；Maverick 以 BF16 与 FP8 发布，FP8 权重可放进单台 H100 DGX 主机（§Quantization）。

长上下文项：MTOB half book 的 Scout 是 42.2/36.6， Maverick 是 54.0/46.4；full book 的 Scout 是 39.7/36.3，Maverick 是 50.8/46.7。指标是 chrF，任务是把半本/整本书做 eng→kgv 与 kgv→eng 翻译；它不是 10M 检索测试。Llama 3 两列原表注明 context window 128K。

07

边界：400B 全都要存，10M 不等于 10M 可用，路由细节未公开

MoE 省的是每 token 计算，不是显存；长上下文与多模态的能力声明各有测试条件，超出条件的部分未获取。

显存：省的是计算，不是权重

所有 routed experts 都要存。Table 6 给出权重-only 的折算：Maverick 的 BF16/FP8/INT4、 Scout 的 BF16/INT4，以及 Llama 3.1 405B 的 BF16 基线。模型卡说 Scout 的 int4 量化可放进单张 H100， Maverick 的 FP8 可放进单台 H100 DGX 主机（§Quantization）； 这两个“放得进”是权重与部署层面的说法，不含 KV cache 与长上下文带来的额外显存。

Table 6（本页计算）：参数来自 Llama 4 model card §Model Information（Scout 109B、Maverick 400B）与 Llama 3 §3（405B）；每参数字节为格式定义（BF16 2 B、FP8 1 B、INT4 0.5 B）。 只算权重，不含 KV cache、激活、optimizer、通信 buffer。

路由：每 token 选 1 个 routed，但没有选择规则、负载均衡与消融细节

博客只说了“每 token 送 shared 与 128 个 routed 中的一个”的结构；router 的选择规则、 负载均衡损失、容量因子、dropless 策略、专家并行的切分与通信量均未获取。模型卡/博客也未提供 MoE vs dense 的受控消融（未获取）。因此不能从 benchmark 反推“MoE 一定比 dense 好”； 能说的是这套配置在报告的任务上达到了这些分数。

上下文：10M 是最大输入，不是有效检索保证

Scout 预训练/后训练用 256K，模型卡标称 10M；博客把 iRoPE 与 inference-time temperature scaling 作为长度外推手段，并提到 needle-in-a-haystack 与 10M code NLL，但未给出具体数值（未获取）。MTOB 是半本/整本书的翻译， 不是 10M 检索；因此页面不把 MTOB 的 chrF 当作 10M 能力的证据。温度缩放的具体温度、插值方式与消融也未获取。

多模态：三处图像数条件不同

模型卡 §Intended Use 注 2 写“tested for image understanding up to 5 input images”；博客 §Post-training 写 “pre-trained on up to 48 images, tested in post-training with good results up to eight images”。 两处数字与条件都照原样并列：模型卡说的是 image understanding 测试，博客说的是预训练/后训练图像数。 页面不把它们合并成一个上限，也不把 48 当作推理时可用的图像数。

评测与发布：bf16、跨代、未覆盖量化

模型卡明确说所有报告评测都在 bf16 模型上做（§Benchmarks）； 量化 checkpoint 只提供部署灵活性，没有进表。两张 benchmark 表的基线是 Llama 3.1 70B/405B 与 Llama 3.3 70B， 和 Llama 4 不是同一代、同一数据、同一后训练 recipe；跨代差值不能当作受控消融 推断 （依据：博客称 Llama 4 用超过 Llama 3 2× 的数据混合，且 Scout/Maverick 从 Behemoth 蒸馏）。 表里没有置信区间或显著性检验；小差值（如 MMLU 0.3 个百分点）不应被当作稳定优势。

发布层面，Llama 4 是 open-weight：模型卡写的是 Llama 4 Community License （§Model Information），属于自定义商业许可。 它不是 OSI 定义/认证的 open-source 判断（依据：模型卡未声明 OSI 认证，许可条款为自定义）。 Behemoth 仍是 teacher、还在训练， 未发布；它的 288B active、16 experts、近 2T total 不能当作已发布模型的规格（博客 §2T Behemoth）。

什么时候别用

  • 只有单张 H100，又想跑 BF16 Maverick。Table 6 的 Maverick BF16 行远超单卡 80GB HBM3；模型卡给的是 FP8 单台 DGX 主机，不是单卡 BF16。
  • 需要可解释、可复现的路由。从 128 个 routed 中选 1 个的选择规则与 router 细节未公开；同一输入在不同 batch/并行配置下的路由是否稳定， 模型卡/博客未提供（未获取）。
  • 需要 10M 上下文的确定性检索。10M 是标称最大输入； 公开的 MTOB 与博客叙述未给出 10M 检索的数值（未获取）。上线前要在自己的长文档任务上复测。
  • 需要超过 5 张输入图。模型卡的 image understanding 测试上限是 5 张；博客说后训练测试到 8 张。两处条件不同，保守做法是按 5 张设计，超出部分自行验证。
  • 需要 OSI open-source 许可。Llama 4 Community License 是自定义商业许可 （模型卡 §Model Information）；它不是 OSI 认证的开源许可 判断（依据：模型卡未声明 OSI 认证，许可为自定义条款）。
一句话

Llama 4 把 405B 稠密账本拆成 400B 容量 + 17B 激活

省的是每 token 计算，不是显存，也不是所有 benchmark 的一致提升。把总参数、激活参数、精度、上下文四个条件分开读， 再决定 Table 6 的权重存储与标称上下文对你意味着什么。
