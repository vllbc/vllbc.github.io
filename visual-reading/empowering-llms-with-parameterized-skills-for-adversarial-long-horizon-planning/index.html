PLAP：让 LLM 在「技能」层规划，把落地交给执行器

LLM 直接输出底层动作，动作空间大、非法动作多；只输出高层任务，又要靠专家规则或额外训练把它翻译成动作。 PLAP 在两者之间插入参数化技能：LLM 只负责选技能和参数，预定义的执行器负责把技能拆成可执行动作。 论文在 MicroRTS 上验证，不做额外训练，每 k=100 个游戏步才调用一次 LLM。

Sijia Cui, Shuai Xu, Aiyao He, Yanna Wang, Bo Xu · CAS 自动化所 / UCAS / 南京AI研究院 / NUIST arXiv 2509.13127v1 ↗ 代码 ↗
TL;DR · 30 秒抓住核心

论文把 LLM 智能体的接地问题拆成两层：高层用语言规划，低层用环境动作执行。直接让 LLM 输出低层动作，空间大且容易出非法动作；让 LLM 输出高层任务，又要靠专家经验或额外训练把任务翻译成动作。PLAP 选中间层：参数化技能。

技能库给出 5 个技能（Table I），每个技能有名字和参数，内部对应若干原子动作。LLM 在提示里看到规则、技能表、示例、tips 和当前战场文本，输出 [Skill](params) 形式的计划；解析器丢掉非法行。执行器每步检查技能是否可用（Ii），调用预定义函数 πi 取当前状态下的第一个动作，再拼成动作向量；技能终止就删除。每 k=100 步重新规划。

在 5 个脚本基线上，16 个 PLAP 设置的平均分是 0.91，高于 RandomBiasedAI、LightRush、NaiveMCTS；Qwen-fs-tip 与 DeepSeek-fs-tip 超过 CoacAI。另一张表是 8 个 LLM 的循环赛：GPT-4o 49 分、84.3% 胜率，Gemini 1.5 Flash 25 分、65.7%。注意 84.3% 是 LLM 之间的胜率，不是对脚本基线的胜率。

01

动作空间太大，LLM 直接落地会踩空

先看 MicroRTS 的观测与动作编码，才能理解为什么需要中间层。

MicroRTS 是实时战略游戏：红蓝双方在对称地图上采集资源、建造单位、击败对手。一局有成千上万个游戏步，每一步都要做实时决策（§IV）。论文主要用 basesWorkers8x8 地图，双方各从一个基地和一个工人开始。

环境给智能体的观测是一个 (h, w, nf) 张量，nf=27 个特征平面，由多组 one-hot 特征拼接而成（Table III）。要让 LLM 读，还得把这 27 个平面转成结构化文本（Fig.5）。

Table III 转录 · MicroRTS 观测的 27 个特征平面（5+5+3+8+6）。
特征平面数取值
Hit Points50, 1, 2, 3, ≥4
Resources50, 1, 2, 3, ≥4
Owner3player 1, -, player 2
Unit Types8-, resource, base, barrack, worker, light, heavy, ranged
Current Action6-, move, harvest, return, produce, attack
合计27—

动作侧更紧。MicroRTS 的每个动作编码长度是 78，整个动作向量是 78 × w·h 维。Table IV 把 78 拆成 7 段 one-hot：动作类型 6、移动方向 4、采集方向 4、返回方向 4、生产方向 4、生产类型 7、相对攻击位置 49（ar=7，ar2=49），相加正好是 78。推断（由 Table IV 的各段取值范围相加得到；论文只直接给出 78 这个总长度。）

把两个数字放在一起

27 个平面描述状态，78 维编码描述一个动作

在 8×8 地图上，动作向量长度是 78×8×8 = 4992。LLM 若直接生成底层动作，每一步都要在这个 4992 维空间里给出一个合法组合；对手一行动，上一步的组合还可能立刻失效。这就是论文说的“invalid actions + curse of dimensionality”（§I）。

另一条路是把输出空间抬到高层任务，但“高层任务 → 底层动作”的翻译本身没有解决：要么靠人写规则，要么训练一个辅助模块。问题于是变成：能不能找一个比动作抽象、又比任务具体的中间层？

02

两条老路：一条踩空动作，一条卡在翻译

论文把现有做法归成两类，各自的失败点正好相反。

Fig.1(a)

直接生成底层动作

把 LLM 的输出空间约束成环境的低层动作空间。好处是接口直接；坏处是动作空间巨大，模型容易生成无效或非法动作，论文称之为 curse of dimensionality（§I）。

卡点：可靠性。每一步都要合法，长序列里错误会累积。推断（依据：§I 指出直接生成低层动作会遇到 invalid actions 与 curse of dimensionality；错误随序列累积是本页的延伸。）

Fig.1(b)

先生成高层任务

把输出空间抬到高层任务或语言指南，再把任务翻译成底层动作。翻译环节通常依赖专家经验，或者额外训练一个模块。

卡点：高层与低层对不齐；论文原话是 “the latter faces challenges in effectively bridging high-level planning with execution”（§I）。

论文在 §II 列了几种代表做法：SayCan 需要训练一个 value function 来过滤可执行动作；Plan-Seq-Learn 依赖训练好的低层控制策略；EES 需要学习一个参数选择策略来指导执行；LLaMAR 用四个 LLM 模块协作，推理时间和调用成本都高。这些方法在机器人任务上有效，但到了对抗环境，技能参数空间会动态变化（比如新造出来的兵种），再训练一个参数生成策略很难。

论文的选择

中间层：参数化技能空间

Fig.1(c) 在低层动作和高层任务之间插入 parameterized skill space。每个技能是一个预定义函数，带明确参数，内部映射到一串底层动作。LLM 只在这个技能空间里规划，执行器负责把技能展开成动作。这样既不需要 LLM 直接碰 4992 维动作向量，也不需要再训练一个“任务 → 动作”的翻译器。

和 EES 的关键差别在参数由谁选：EES 学一个参数选择策略；PLAP 把技能选择和参数选择都交给 LLM（§IV-B），因此不需要额外的参数生成网络。

03

在技能层规划：LLM 选技能和参数，执行器负责每一步

核心是把「做什么」和「怎么做」拆开；公式只有 active set、动作向量、终止删除三行。

论文沿用 parameterized action MDP（PAMDP）的设定，用一个五元组描述任务：(S, U, R, T, γ)。其中 U 是参数化技能集合。每个技能 ui 写成四元组：

ui = (πi, Θi, Ii, βi)
§III-A · πi 是低层控制策略；Θi 是参数空间；Ii 判断技能在当前状态是否可用；βi 是终止条件

技能库是人工设计的，论文在 MicroRTS 里放了 5 个技能。每个技能只需要 LLM 给出技能名和参数，内部包含哪些原子动作由执行器处理：

Table I 转录 · Skill-RTS 的 5 个参数化技能；每个技能可包含一个或多个原子动作。
SkillParametersAtomic ActionsDescription
Deploy Unitunit type, deployment locationmove, NOOPMoves a unit of a specified type to a specified location.
Harvest Mineralmineral locationmove, harvest, returnMove to a specified location to harvest resources and return to base.
Build Buildingbuilding type, building locationmove, produceBuild a building of the specified type at the specified location.
Produce Unitunit type, produce directionproduceProduce a specified type of unit from a specified direction.
Attack Enemyunit type, enemy typemove, AttackCommand a specified type of unit to attack a specified enemy type of unit.

LLM 的输出不是单个技能，而是一个技能计划。解析器 f 用正则从 START OF SKILL_PLAN / END OF SKILL_PLAN 之间提取 [SKILL_NAME](PARAMETERS)，格式错误、技能不存在、参数非法的行直接丢掉。剩下的 ct 个技能组成：

Qt = { u1(θ1), u2(θ2), …, uct(θct) }
Eq.4 · 计划只在第 t 步生成；接下来的 k 步由执行器维护

执行器每步先筛出当前状态可用的技能：

Qt′active = { ui ∈ Qt | Ii(st′) = 1 }
Eq.5 · 不可用的技能不参与这一步，但不会从计划里删除

对每个活跃技能，执行器调用它的策略 πi，只取当前状态下的第一个动作，再把所有活跃技能的动作拼成动作向量：

at′ = [ a0(t′,0), a1(t′,0), …, act′(t′,0) ]
Eq.7 · ct′ 是当前活跃技能数；动作向量里每个分量来自一个技能的第一步
关键细节

执行器不是把技能展开成固定序列后回放

论文特别说明：下一步不会直接使用上一步序列里的第二个动作 ai(t′,1)。原因有两个：技能可能在新的状态里不可用；对手行为不可预测，原来的第二个动作可能已经无效。所以每一步都重新调用 πi(st′+1, θi)，取新状态下的第一个动作（§IV-C）。

技能终止后从计划里删除：

Qt ← Qt \ { ui ∈ Qt | βi(st″) = 1 }
Eq.8 · 终止条件硬编码在技能函数里；删除后执行器继续处理剩余技能

这套循环把“规划”和“执行”拆成两个时间尺度：LLM 每 k 步重新看一次战场，执行器每一步都按当前状态重算动作。下一节看 k 带来的调用成本。

04

不训练，只靠提示和 k 步节奏

PLAP 的开销主要不在执行器，而在 LLM 调用次数；k 决定调用频率。

论文强调 PLAP 不需要额外学习成本，也不依赖专家经验或先验知识（§I）。实验里没有训练或微调，主要超参数只有 temperature 和 max_tokens：temperature 设为 0，max_tokens 设为 256，规划间隔 k 默认 100。地图主要是 basesWorkers8x8；论文称 prompt 的构造与具体地图无关，因此换地图可基于同一框架实现（§V-B）。

每次规划的 prompt 由六部分组成（Eq.1）：用户指令 Inst、游戏手册 Manu、技能描述 Udesc、few-shot 示例 shots、专家提示 tips、当前文本观察 Ottext。few-shot 只用 2 个手工构造的例子；tips 可以为空，也可以放“先打敌方兵营”这类专家建议。

Dt ← Construction( Inst, Manu, Udesc, shots, tips, Ottext )
Eq.1 · prompt 的动态部分是当前战场观察；技能表、手册、示例、tips 相对固定

如果一局需要 n 个游戏步，规划每 k 步发生一次，LLM 只需被调用 n/k 次（§IV）。执行器本身是预定义函数，不调用 LLM。下面把 n 和 k 做成可调的，看调用次数怎么变。

LLM 调用次数
n=1000，k=100 → 10 次 LLM 调用；逐 step 调用需要 1000 次，少 100.0×。
手算对账：两组 n / k调用次数 = ceil(n/k)

组 1：n=1000, k=100 → ceil(1000/100)=10 次；逐 step 调用 1000 次，1000/10=100 倍。

组 2：n=2000, k=50 → ceil(2000/50)=40 次；逐 step 调用 2000 次，2000/40=50 倍。

两组都能整除，所以 ceil 不改变结果；滑块取不能整除的值时，JS 用 Math.ceil 向上取整，读数会略高于 n/k。论文没有报告端到端延迟或 API 成本，这里只比较调用次数，不比较实际耗时。

这也是 PLAP 和 LLaMAR 那类多模块架构的差别：LLaMAR 要四个 LLM 模块协作，PLAP 每次规划只调用一个 LLM，靠执行器承担高频决策（§II）。代价是执行器的技能函数要人工写；论文把这一点列进了限制。

05

一次规划管 k 步，执行器每步重算动作

看图：LLM 只在 t=0, k, 2k... 介入；中间每一步由技能函数闭环执行。

1环境 → 文本观察
MicroRTS 的 27 个特征平面被转成结构化文本。
2Prompt → LLM Planner
每 k=100 步构造一次 prompt，LLM 输出技能计划。
3Parser / 校验
正则提取技能与参数，非法行丢弃，得到 Q_t。
4Skill Executor
每步筛出 I_i(s)=1 的技能，调用 π_i 取第一个动作。
5动作向量 → Env.step
拼成动作向量执行；新状态回传，进入下一步。
6β_i 终止删除
终止条件成立后，从 Q_t 删除该技能。

Algorithm 1 的循环可以压成三行：

  • t % k == 0：构造 Dt，调用 LLM，解析出 Qt。
  • 每一步：按 Ii(st) 求活跃技能集，调用各自的 πi，取第一个动作，拼成 at。
  • 执行后：Env.step 返回新状态；按 βi 删除已终止技能；t ← t+1。

07

技能库是人写的，对手意图没有建模

论文自己列了三条限制；每一条都直接决定 PLAP 能用到哪。

限制一

只在 MicroRTS 上验证

论文原话：“PLAP has only been tested in the MicroRTS environment, lacking validation in more realistic adversarial scenarios.”（§VI）8×8 的网格游戏和真实世界的对抗场景差得远。推断 换到高维观察、连续动作或部分可观测环境，技能库和执行器能否直接复用，论文没有验证（依据：§VI 只列“仅在 MicroRTS 验证”这一限制，没有报告其他环境的实验）。

限制二

技能函数是人工构造的

论文原话：“The skill functions used in PLAP are manually constructed, which limits generalization across different domains.”（§VI）推断 技能库的粒度和覆盖范围直接决定规划空间：太粗，LLM 没有足够表达力；太细，又退回到底层动作（依据：Table I 的 5 个技能覆盖部署、采集、建造、生产、攻击五类操作；§IV-B 把技能与参数都交给 LLM 选）。论文没有给出技能库设计的系统方法，只把“用 LLM 生成技能代码”列为未来方向。

限制三

没有建模对手的策略意图

论文原话：“PLAP currently focuses on explicit state(observation) changes in the environment and opponent, without modeling the opponent’s strategic intent. This limits its upper performance bound.”（§VI）执行器只对显式状态变化做反应；对手下一步想做什么、为什么这么做，不在模型里。论文把对手建模列为未来工作。

本页的推断

还有两个没被实验覆盖的口子

推断 文本化观察的可扩展性没有测。论文把 27 个特征平面转成结构化文本，在 8×8 地图上够用；但更高维的观察要压成多长的文本、会不会丢关键信息，论文没有实验（依据：§V-A 定义 Skill-RTS 的指标与 5 个技能，观察转换示例见 Fig.5，动作/观测细节见 Appendix VII-A；§V-B 主实验用 basesWorkers8x8）。

推断 失败归因没有专门机制。Algorithm 1 在 t % k == 0 时重新规划，但没有“分析上一轮为什么失败”的步骤；计划失败后主要靠下一轮重新看状态（依据：Algorithm 1 的循环里没有失败归因分支）。论文提到可以接入 Reflection 等推理模块（§V-D），但那是可选扩展，不是基础循环的一部分。

论文也没有报告端到端延迟或 API 成本；k 步规划降低的是调用次数，单次 LLM 延迟仍然存在。
