AI Search · 工具调用 · arXiv 2508.04604v2

TURA：把「查不到的实时信息」接到工具上，再用 DAG 把它们并行办掉

RAG 只能读静态网页快照：机票余票、酒店库存这类必须现场调用才会产生的信息，它从结构上就拿不到。 TURA 把网页检索也包装成一种 MCP Server，和各类 API 放在同一个池子里——先用意图分解 + 索引增强选出该用哪个，再用 DAG 把互不依赖的调用并行发出去，最后交给一个蒸馏过的 4B 小模型逐步执行工具。 代价是：整个离线评估建立在一个从生产日志构建的内部基准 MCP-Bench 上，而网页检索被放进了同一个检索池里。

Zhejun Zhao, Yuchen Li, Alley Liu 等（前三位贡献相同）· 百度 arXiv 2508.04604v2 ↗ MCP-Bench 仓库 ↗

arXiv v2 于 2026-03-12 提交，晚于笔记日期 2025-08-15；表号与结论以 v2 为准。

TL;DR · 30 秒抓住核心

论文把 AI 搜索定义成一个带延迟上限的组合优化：选一组 MCP Server 调用策略 π，在 L(π) ≤ τmax 下最大化答案质量 Q(A)（Eq.1）。网页搜索本身也被当成一个 MCP Server，于是静态检索和动态 API 走同一套规划与执行。

三段各解决一个卡点：意图分解 + 为每个 Server 合成查询来扩充索引，把「用户口语 → 开发者文档」的词汇鸿沟垫平（Table 4/5）；DAG 规划器只在判定为复杂查询时被调用，简单查询走单任务方案（§4.3）；蒸馏执行器训练时学完整的 thought + action，上线时连 thought 一起生成以减少 token 与延迟（§4.4.2）。

最强的信号来自蒸馏：Qwen3-4B Distilled 工具调用准确率 88.3%，比它的基座 70.1% 高 18.2 个百分点，比教师 Deepseek-V3（671B-A37B）的 82.4% 高 5.9 个百分点；P80 延迟 750ms，是基座 2200ms 的 65.9% 降幅（Table 7）。但端到端 Table 1 的对比对象只是 LLM + RAG / Dynamic RAG / Tool-Agent，没有 "TURA 去掉蒸馏" 这一行，所以 Table 1 的差距里，蒸馏占多少、规划与检索占多少，论文没有拆分。

01

RAG 的盲区不是「召回不好」，而是答案根本不在索引里

读完这节应能说清：为什么更强的检索模型救不了实时查询，以及论文把这类查询形式化成了什么。

网页检索读的是预先建好的静态快照。但有一类信息的产生方式就是「现场问一次系统」：某个日期的机票余票、电商数据库里的实时库存、铁路车次在指定日期的时刻表。这些内容在索引时还不存在，召回率再高也召不回来。

"they cannot query a flight booking system for ticket availability on a specific future date or check real-time inventory from an e-commerce database, as this information is only accessible through interactive queries to APIs or databases." §1 Introduction

论文的做法不是给 RAG 打补丁，而是换一个形式化：把所有能力——包括网页搜索本身——都表示成 MCP Server M = {M₁, …, M_N}；一次具体的调用组合与顺序记作执行策略 π；目标是

π* = arg maxπ Q(A(π))    subject to    L(π) ≤ τmax
Eq.1 · L(π) 是端到端延迟，Q(A) 是答案质量；单次工具调用不是问题，多步、有依赖、还要压延迟才是问题

这个改写把三类难点一次摆到台面：选哪些 Server（工具选择的语义鸿沟）、按什么顺序与并行度调用（多跳依赖）、用什么模型执行（生产环境的延迟）。后面三节依次对应。

02

三路前人方案各有各的天花板，线上指标给出三段台阶

读完这节应能说清：LLM+RAG、Dynamic RAG、Tool-Agent 各自卡在哪，以及它们在人工评测里分别落在什么水平。

LLM + RAG

Deepseek-V3 配百度的检索 API（跳过 rerank 只取原始文档），合成答案，不调用工具。

卡点：索引里没有实时数据，再强的 LLM 也只能复述旧网页。

Dynamic RAG

生成过程中动态决定何时、检索什么，但仍然局限在静态索引。

卡点：检索时机变聪明了，仍然碰不到事务型 API。

Tool-Agent

ReAct 式与 DAG 式 agent，用同一批 MCP Server，但没有 TURA 的统一检索模块与蒸馏执行器。

卡点：能调工具了，但工具选择与执行延迟没做优化。

并行省的只是「等最慢那条分支」的时间：关键路径不变，其余分支重叠执行，总延迟由最长的那条路径决定。下图把 Figure 2 那张 DAG 搬到一个极简的耗时模型上（四个子任务等长、各为 t），切换规划模式、拖动子任务耗时，观察总延迟与节省比例。

在本模型里，降幅恒等于 1 − 步数 / 4：Figure 2 的 DAG 恒为 1 − 2/4 = 50.0%，全部无依赖恒为 1 − 1/4 = 75.0%，与 t 的取值无关。滑块只改绝对延迟（毫秒），比例的读数不随 t 变。

规则（本页自定的示意模型，不是论文的算法）：

  • Sequential：4 个任务逐个跑，总延迟 = 4t。
  • DAG（Figure 2）：三组互不相等的行是 [天气]、[景点 → 路径]、[酒店 → 路径]，各占 t、2t、2t，总延迟 = max(t, 2t, 2t) = 2t——不是 3t；本模型假定 Sub-task4 在两条分支上共用一个执行结果、只跑一次（论文 §4.3 未讨论 S4 被调用多次的情形，这是页面自定的假设）。
  • 全部无依赖：max(t, t, t, t) = t。
  • 「降低比例」= 1 − total(模式) / total(Sequential)，百分比保留 1 位小数。

04

执行器为什么要变小：大模型每步 8.7 秒，实时搜索等不起

读完这节应能说清：教师轨迹怎么被筛成数据、学生为什么能超过教师，以及线上为什么最后选 4B 而不是最准的 30B。

用 Deepseek-V3 直接做细粒度执行在生产上不可行：每一步决策的上下文包括对话历史、Server 描述，以及论文所说的（未明确是每个 Server 之内还是整个上下文的）"dozens of tool APIs"（§4.4）。Table 7 的数字给出了量级：教师模型每步平均 P80 延迟 8,700ms。

数据是筛出来的，不是攒出来的

教师模型按 ReAct 式三元组 ⟨ot, tht, at⟩ 生成轨迹（观察、思维、动作），然后过两道自动质检（§4.4.1）：

  • Correctness Filtering：裁判模型 Jcorrect 检查是否遵守 API schema、参数值是否合法、思维是否逻辑成立，失败的整条丢弃。
  • Efficiency Filtering：Jefficient 检查动作冗余、路径次优，这类轨迹 "either pruned or programmatically corrected"。

训练用 Qwen3 系列，标准交叉熵损失覆盖 thought + action 的完整 token 序列（Eq.8）；上线时 prompt 明确要求直接产出 action、跳过 thought——这就是 "train-with-thought, infer-without-thought"。

05

检索、规划、执行三段接力，每一段都有可量化的口径

07

这套账在什么条件下才成立

读完这节应能判断：什么场景直接借鉴没问题，什么场景需要重新验证。

边界一

离线评估全部在一个内部构建的基准上进行

MCP-Bench 来自百度搜索的匿名化生产日志，人工标注（Cohens kappa 0.87），Server 与工具标识被匿名化后公开发布（§5.1.1 原句只承诺 "anonymizing server and tool identifiers"，页面不据此推断 service 侧域名或属性也已匿名化）。Table 1/4/5/6/7 的所有对比都在这个基准上，论文没有报告它与公开 benchmark 的交叉结果。

边界二

「网页检索也进检索池」带来的静态查询风险

传统网页检索本身被当作一个 MCP Server（§3："traditional web retrieval is itself treated as an MCP server"）。推断（依据：§4.2 的召回在 top-K 处截断，"selecting the top-K servers"，且 Table 4 的 Recall@5 不满 1）：搜索引擎若没挤进 top-K，原本纯静态的查询也会失效——论文未单独报告纯静态查询子集上的效果，这个风险有多大无法从表中判断。

边界三

DAG 只对少数复杂查询有意义，且省的是等待不是计算

只有被判为复杂的查询才进 DAG 规划器，简单查询走单任务方案（§4.3）；MCP-Bench 中 95.02% 是单意图、平均 DAG 宽度 1.147，Table 6 的 44.2% 延迟降幅只在「复杂多跳、存在并行」的子集上测得，不能外推到全量。并行只压缩关键路径之外的等待，不减少总工具调用本地计算。

边界四

成功的上限被教师与数据管线锁住

训练数据来自教师在「一组具有代表性的子任务」上生成的轨迹（§4.4.1："For a large set of representative sub-tasks"），再由两道裁判模型筛选。教师无法正确解决的子任务类型，学生也没有对应的正例。推断（依据：Eq.7 的 Ddistill 全部来源于 Dexpert；§5.3.3 把学生超教师解释为数据管线 "filters noise and crystallizes optimal reasoning paths"，未讨论管线之外的类型）。

边界五

执行失败、重规划与权限没有在文中给出评估

论文的指标围绕答案质量、忠实度、SSR 与延迟；对 API 失败/超时后的重规划、工具调用的权限与安全，文中没有对应的实验或指标。推断（依据：§5.1.3 列出的评估指标全集不含失败恢复类指标）。

一句话

可迁移的是「统一 Server 池 + 先分解再检索 + 按依赖图并行 + 用生产数据蒸馏小执行器」

其中每一步的可复用性、以及在非百度搜索场景下能拿回多少收益，都要用自己的流量日志重新测——尤其第二块，它依赖教师模型和服务端 API 的具体分布。
