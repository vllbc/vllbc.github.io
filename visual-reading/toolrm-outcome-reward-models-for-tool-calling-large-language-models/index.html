ToolRM：给工具调用配一个专用裁判，而不是让通用奖励模型猜

通用奖励模型看的是「这段文字好不好」，工具调用要判断的是「函数名、参数、参数类型、调用数量对不对」。ToolRM 先用 25 个开源模型在 BFCL-v3 上生成真实错误，做成 1,500 条正确/错误配对的 FC-RewardBench；再用 11 个开源模型合成 180K 条偏好数据，训练 1.5B、7B、14B 三个结果奖励模型。

Mayank Agarwal 等 · IBM Research arXiv 2509.11963v2 ↗
TL;DR · 30 秒抓住核心

问题不在「有没有奖励模型」，而在「奖励模型看不看得懂工具调用」。 现有奖励模型主要在自然语言输出上训练；工具调用是结构化输出，一个参数值写错、漏掉可选参数、函数数量不对，都会让调用失败，但这些错误在自然语言评分里往往不明显（§1、§3.1）。

先造一个能测裁判的基准。 FC-RewardBench 从 BFCL-v3 单轮 split 取用户 query、工具目录和正确调用，再让 25 个模型（0.5B–685B）生成错误调用，每个 query 随机保留一条错误；共 1,500 条。错误类型以参数值错（650 条，占 43.3%）和函数名错（403 条，占 26.9%）为主。

再用错误调用反向训练裁判。 11 个开源模型在 API-Gen、SGD、xlam-irrelevance 等数据上生成调用，与 ground truth 不一致的保留为负样本；最终 85K 单轮 + 85K 多轮 + 10K irrelevance，合计 180K。ToolRM 用 Bradley–Terry 成对偏好目标训练，只替换最后一层为标量奖励头（§3.2、§4）。

三个用法：推理时选最好的、训练前筛数据、RL 里当奖励。 Best-of-32 让 Qwen3-0.6B 从 39.5% 升到 64.4%（+24.9 个百分点）；数据过滤只保留 ToolRM 评分最高的 8K，平均分 62.5%，高于全量 16K 的 61.0% 和随机 8K 的 58.4%。

01

工具调用的错，往往不是「句子写得不好」

先看错误分布：绝大多数错误是参数值、函数名、函数数量这类结构化错误，而不是自然语言流畅度。

工具调用的输出是一个结构化对象：选哪个函数、传哪些参数、参数值是什么、类型对不对、要不要一次调用多个函数。任何一处不匹配，执行都会失败。通用奖励模型在自然语言偏好数据上训练，能判断回答是否有帮助、语气是否合适，却不一定能发现「参数值写成了相近但错误的字符串」这种细粒度问题（§1、§3.1）。

论文把这个问题拆成两个缺口：一是没有专门评估「工具调用奖励模型」的基准；二是现有奖励模型在工具调用上表现不稳，LLM-as-Judge 虽然准确率更高，但参数量大、推理成本高（§1）。为了量化缺口，作者先构造 FC-RewardBench，再把错误类型逐项统计出来。

02

三条已有路线：通用 RM、工具增强 RM、LLM-as-Judge

论文的对照不是「谁参数多」，而是「谁真的看得懂工具调用」。

路线 A

通用奖励模型

在 RewardBench 等自然语言偏好数据上训练，擅长判断回答质量、安全性和帮助性。论文从 RewardBench 选了 8 个 3B–70B 的强 RM 作为对照，发现它们在 FC-RewardBench 上并不能稳定区分正确与错误调用（§4、§5.1）。

路线 B

工具增强奖励模型

Themis 是专门做工具增强的 RM，但在 FC-RewardBench 上只达到 45% 准确率。论文认为这说明「加工具」不等于「懂工具调用的细粒度错误」（§5.1）。

路线 C

LLM-as-Judge

用大模型成对比较两个候选调用，论文的 6 个裁判覆盖 70B–685B。准确率可达 80% 以上，但参数规模大、每次比较都要跑一次大模型，成本高（§4、§5.1）。

这三条路线的共同问题是：没有一个统一的、专门针对工具调用的测试集。论文的切入点不是先训练一个更大的 RM，而是先造 FC-RewardBench，让「裁判好不好」可以被单独测量；然后再用同样的错误生成思路，反向造出训练数据（§3.1、§3.3）。

03

用「正确 vs 错误」的成对数据，训练一个标量裁判

基准和训练集共用同一个思路：让模型真实地生成调用，再把与 ground truth 不一致的输出保留为负样本。

3.1 FC-RewardBench：1,500 条真实错误

基准的输入侧直接取自 BFCL-v3 的单轮 split：用户 query、可用工具目录、正确调用都由 BFCL-v3 提供。负样本不是人工改写，而是让 25 个开源模型（0.5B–685B）实际生成调用；与 ground truth 不一致的才保留。每个 query 随机抽一条错误，避免某个 query 被过度代表，最后随机选 1,500 条（§3.1）。

这样构造出的错误分布更接近模型真实会犯的错：参数值错、函数名错、函数数量错占了大头（Table 1）。评测时，奖励模型对正确调用和错误调用分别打分；正确调用的分数更高，才算判断正确。LLM-as-Judge 则用成对比较 prompt，并随机交换候选顺序以减少位置偏差（§5.1）。

3.2 ToolRM：11 个模型合成 180K 偏好对

训练数据覆盖三类场景：API-Gen 的单轮交互、Schema-Guided Dialogue（SGD）的多轮工具调用、xlam-irrelevance 的「没有合适工具」场景。论文先用随机字符串替换函数名和参数名、重排 schema 的 key，做混淆处理，防止模型背训练集；然后让 11 个开源模型（0.5B–32B）生成调用，只保留与 ground truth 不一致的负样本（§3.3、§4）。

数据规模

85K 单轮 + 85K 多轮 + 10K 不相关

合计 180K 条偏好样本。每个输入只保留一条错误输出，避免同一 query 在训练集中被重复计权（§4）。

模型

Qwen2.5-Instruct 1.5B / 7B / 14B

以指令微调权重初始化，把最后的语言模型头换成线性层，输出一个标量奖励。输入包含工具规格、对话历史和候选调用（§4）。

训练目标是 Bradley–Terry 成对偏好：让正确调用的奖励高于错误调用，并用 sigmoid 转成概率；同时加奖励中心化正则，把正负样本的奖励和往 0 拉（§3.2、Eq.1–3）。论文没有把它称为 DPO，页面也不把它写成 DPO。

P(y+ ≻ y− | x) = σ(r(x, y+) − r(x, y−))
Jreg(r) = J(r) + η · E[(r(x, y+) + r(x, y−))2]
§3.2 · 成对偏好目标与奖励中心化；η 是小的正系数，实验中取 0.01（§4）

这个目标只要求「正确比错误分高」，不要求奖励的绝对值有物理意义。因此在 Best-of-n 里，ToolRM 只需要把 32 个候选排序；在数据过滤里，只需要保留分数最高的一半；在 RL 里，奖励取值在 [−3, 3]（§5.3.2）。

04

训练很轻：1 个 epoch、lr 1e-6、3% warmup；但论文没报 GPU

奖励模型训练本身不重，重的是数据合成与 Best-of-32 推理；这两项的成本论文都没有折算成 GPU 小时。

RM 训练

1 epoch，lr 1e-6，cosine

三个规模都用相同配置：训练 1 个 epoch，学习率 1e-6，cosine schedule，warmup 占总步数 3%，奖励中心化系数 0.01（§4）。

数据合成

11 个模型生成 180K 负样本

每个 query 至少跑一次生成；错误输出保留，正确输出丢弃。论文没有报告合成 180K 数据用了多少 GPU 或多少 API 调用（§3.3、§4）。

GRPO

15 epochs，4 rollouts，batch 512

策略优化实验用 verl + ToolRL 代码：max prompt 2048、max response 1024、lr 1e-6、PPO mini-batch 128、4 条 rollout、15 个 epoch、train batch 512（Table 9）。

推理

Best-of-32：每个输入采样 32 次

温度为 0.6，每个输入独立采样 32 个候选，再用 ToolRM 打分选最高。这个开销随 n 线性增长，论文没有给延迟或费用（§5.2）。

数据过滤实验另有一套微调配置：Llama-3.1-8B-Instruct，LoRA rank 16、alpha 32、学习率 2e-4、1 个 epoch、cosine、warmup 10%（§5.3.1）。这部分算力同样没有折算成 GPU 小时。

05

一条数据管线，三种用法

上面是造基准与造训练数据，下面是三个下游场景；共用同一个「正确 vs 错误」偏好结构。

这三条支路不是互斥的：同一个 ToolRM 可以在推理时排序、在训练前过滤、在 RL 中给奖励，区别只在「分数怎么用」。论文的 RQ2 对应 Best-of-n；RQ3 对应奖励引导的数据过滤与策略优化，后者在 §5.3.2 与 Table 5。

06

裁判更准、小模型增益更大、筛数据有效，但不是每一项都赢

先看基准上的裁判能力，再看 Best-of-n、数据过滤与 GRPO 三个下游场景。

6.1 FC-RewardBench：ToolRM 超过通用 RM 与大模型裁判

Figure 1 把 ToolRM、RewardBench 上的强 RM、Themis 和 LLM-as-Judge 放在同一张图上。论文的文字结论是：ToolRM-7B 与 ToolRM-14B 超过所有生成式与序列分类器；ToolRM-1.5B 超过 gpt-oss-120B，接近更大的 Llama-4 裁判（§5.1）。Themis 只有 45%，说明「工具增强」本身不等于「懂工具调用」。LLM-as-Judge 的准确率可达 80% 以上，但参数量在 70B–685B，成本高（§4、§5.1）。

6.5 错误分析：总错误下降，但「不相关调用」上升

Appendix A.6 用 Qwen3-1.7B 在 BFCL-v3 单轮上比较贪心解码与 Best-of-32。总错误从 742 降到 573，少 169 条（相对 22.7%）。参数值错误从 321 降到 231（−90，相对 28.0%），格式错误从 86 降到 34（−52，相对 60.5%），函数名错误从 62 降到 39（−23，相对 37.1%），函数数量错误从 21 降到 9（−12，相对 57.1%）。

但「不相关错误」从 185 增到 210（+25，相对 13.5%）。论文的解释是 ToolRM 倾向于「生成一个函数调用」，即使没有合适工具能满足 query（Appendix A.6）。这说明 Best-of-n 不是单调变好推断（依据：Table 8 的总错误下降、不相关错误上升）：它在减少参数级错误的同时，会把一部分「本该不调用」的样本推向「硬调用」。

07

边界：单轮基准、合成负样本、只训 Qwen2.5

这些条件决定了 ToolRM 能推广到哪一步，也解释了为什么有些单元格不是最高。

基准

FC-RewardBench 来自 BFCL-v3 单轮 split

输入侧是单轮 query；错误由 25 个模型生成。它不覆盖多轮状态、工具执行后的环境反馈、失败后的纠错恢复。下游评测虽然包含多轮 BFCL 指标，但基准本身不测这些能力（§3.1、§5.2）。

负样本

全是合成错误，没有人偏好

负样本来自 11 个开源模型（训练）与 25 个模型（基准）的真实输出，但「正确 vs 错误」是二元的；两个功能都正确、一个有更简洁写法的细微偏好没有被建模推断（由「只保留与 ground truth 不一致的负样本」反推，§3.3、§4）。

模型

只训 Qwen2.5-Instruct 三个规模

1.5B/7B/14B 都基于 Qwen2.5-Instruct；没有 Llama、Mistral 或闭源模型的同方法对照。跨家族泛化只能从「换生成器」的下游实验间接看推断（依据：§4 的 RM 底座只有 Qwen2.5，Table 2 换的是生成器而不是 RM）。

成本

没有 GPU 小时，也没有延迟

论文给了训练超参与数据规模，但没有 GPU 型号/数量/时长、合成成本、Best-of-32 的延迟或费用。不能把「1.5B」直接换算成「便宜」，也不能和 LLM-as-Judge 做严格的成本对比（§4、§5.2）。

结果层面还有三条边界。第一，Best-of-32 不是每个单元格都赢：Qwen3-8B 的 Overall 67.14 低于 Majority Voting 的 67.96，Llama-xLAM-2-8b 的 Multi-Turn 61.62 低于 Greedy 的 67.00。第二，数据过滤不是每一项都更好：FT-Best-8K 只在 Nexus 上低于 FT-16K（72.0 vs 75.5）；其余五项不低于 FT-16K，平均分更高（62.5 vs 61.0）。第三，GRPO 不总是超过 ground-truth 奖励：Qwen2.5-3B 的 Non-Live AST 上 RToolRM 低于 RToolRL。

方法层面最值得记住的是「错误生成」这个数据引擎：它不需要人工标注，也能覆盖模型真实会犯的错；代价是负样本分布受生成模型池限制，且可能放大「倾向于调用」的偏差。Table 8 的不相关错误上升就是这种偏差的直接证据。
