GRPO 训练排查：
先分清策略坍塌与训练崩溃，再决定改哪一层

同一个 reward 断崖，可能来自算法层的分布变窄，也可能来自工程层的概率口径、数值或显存故障。DAPO §3.1 直接描述了 entropy collapse；verl 的代码把非有限梯度和零方差组暴露在不同的位置。先做 0/1 的工程检查，再谈裁剪、采样和学习率。

TL;DR · 30 秒抓住核心

GRPO 没有 critic，学习信号来自同一 prompt 的一组回答。组内 reward 全同时，advantage 的分子为 0（core_algos.py:326）；这是没有信号，不是崩溃。策略坍塌是分布逐步变窄：DAPO §3.1 写的是 entropy 快速下降、组内回答趋同；训练崩溃是某个 step 的工程/数值事故：非有限梯度、KL 爆炸、OOM、训练侧与推理侧的概率口径对不上。

两类会互相转化：坍塌的末端可能以 reward 断崖出现；崩溃也可能渐进 工程判断。所以不要用「渐进 vs 突发」直接定性，先读 rollout，再做概率一致性、mask、数值路径这些 0/1 检查。前一层不通过，后一层的曲线没有解释意义。

DAPO 的处置是 Clip-Higher、Dynamic Sampling、Token-Level Loss、Overlong Shaping；verl 的 filter_groups 默认关闭（algorithm.py:57），rollout.n 默认 1（rollout.yaml:135），actor/entropy 来自更新前的 old_log_prob 前向（ray_trainer.py:1300）。这些默认值会改变你看到的曲线。

01

同一个 reward 断崖，可能死在不同层

先建立共同认知：坍塌是分布变窄，崩溃是某一步的工程/数值事故；两者的证据不在同一张曲线上。

GRPO 用同一 prompt 的一组回答做基线，而不是训练一个 critic。对第 i 条回答，组内 advantage 是：

Ai = (ri − mean(r1..G)) / std(r1..G)
DeepSeekMath §4.1.2 与 DAPO Eq.9（两处公式均无 ε）；verl 的实现见 verl/trainer/ppo/core_algos.py:308-326，分母另加 ε，默认 1e-6（:272）

减均值决定「谁比同组平均更好」，除以 std 决定「这组差异按多大音量进入训练」。两个操作合起来有一个硬边界：组内所有 reward 相同，分子就是 0，不管 std 是不是 0，advantage 都是 0（core_algos.py:326）。这时这一组没有任务梯度；它既可能是「模型已经全对」，也可能是「模型已经全错」。

先分类

策略坍塌：分布逐步变窄，reward 可能还在涨

DAPO §3.1 的原文术语是 entropy collapse：训练推进时 entropy 快速下降，某些组的采样回答「tend to be nearly identical」，原文把这种状态描述为有限的探索和过早确定的策略。本页沿用笔记的「策略坍塌」指这一类算法层故障，但判据只用原文能支持的部分：entropy 持续下降 + 组内回答趋同。

另一类

训练崩溃：某个 step 之后，工程或数值先坏了

「训练崩溃」是笔记的工程分类，不是 verl 的代码术语。它对应的是可定位的 0/1 故障：两侧 logprob 对不上、loss mask 写错、log-ratio 溢出、非有限 grad、OOM。表现为 reward 断崖、输出乱码/复读、KL 或 grad norm 突然跳高。它没有「更合适的学习率」，只有写对和写错。

为什么曲线不够

entropy 低和 entropy 高，原文都当成问题

DAPO §3.1 处理的是 entropy 快速下降，做法是放宽上界 εhigh；§4.3 同时写「excessively low entropy」会失去探索能力，「excessively high entropy」常伴随 gibberish 和 repetitive generation。两处并列：低和高的处置方向不同，原文没有给一个统一阈值。DeepSeekMath §5.2.2 也只报告 RL 提升 Maj@K、没有提升 Pass@K（Figure 7）——单看一条准确率上涨，不能证明分布没有变窄。

还有一个容易混淆的配置边界：rollout.n 默认是 1（verl/trainer/config/rollout/rollout.yaml:135）。当一组只有一条样本时，verl 把该组的 mean 设为 0、std 设为 1（core_algos.py:316-317），advantage 退化成原始 reward，组内基线消失。这不是策略坍塌，也不是数值崩溃，而是配置错误：你以为在跑 GRPO，实际没有组内比较。

02

DAPO 盯熵与采样，verl 盯概率与数值：两条路线各覆盖一半

已有工作给的是两种镜头：一种解释算法层为什么会变窄，一种暴露工程层具体哪个张量坏了；两者都不能单独完成诊断。

算法层

DAPO / DeepSeekMath：从目标函数和采样看

DeepSeekMath 给出 GRPO 的目标、组内归一化 advantage 和原始训练设置：G=64、KL 系数 0.04、max length 1024、batch 1024、每个探索阶段只更新一次（§4.2）。DAPO 在 naive GRPO 上直接观察到 entropy collapse（§3.1），并给出四件套：Clip-Higher（§3.1）、Dynamic Sampling（§3.2）、Token-Level Policy Gradient Loss（§3.3）、Overlong Reward Shaping（§3.4）。

卡在：它能解释「分布为什么变窄」，但不能告诉你 loss mask 哪一位写错、推理引擎和训练框架的 logprob 差在哪、显存为什么爆。

工程层

verl：从代码路径和指标看

verl 把关键故障点拆成了可检查的代码：log-ratio 在 exp 前 clamp 到 [-20,20]（core_algos.py:1256）；非有限 grad norm 会跳过 optimizer step（workers/engine/fsdp/transformer_impl.py:765-769）；KL 有 reward 和 loss 两条路径；零方差组过滤是 algorithm.filter_groups，默认关闭；OOM 有 micro-batch 配置。

卡在：代码能告诉你「这个值坏了」，不能告诉你 reward 是否在测对的东西，也不能替你判断「全对组变多」是数据太简单还是策略已经变窄。

所以顺序不是二选一，而是先工程、后算法：工程层是 0/1，能被穷尽排除；算法层是目标函数的倾向，只能设计上缓解。这个顺序来自笔记的工程实践，原论文没有把它写成流程；本页把它和代码里的实际故障点对齐。

03

先看 advantage 是否还有信号，再定位信号在哪一步坏掉

GRPO 的 advantage 公式给出一个硬边界；其余症状要沿 rollout → logprob → advantage → update 的信号链分层。

把「策略坍塌」和「训练崩溃」落到可操作判据，先记住三件事：

  • 组内全同 → advantage 0。这是数学结果，不是故障类型。它说明这一组没有比较信号；要判断是坍塌还是数据太简单，得看它随时间怎么变、以及全对/全错各占多少。
  • 单样本组 → 没有组基线。rollout.n=1 时 verl 走 len(id2score[idx]) == 1 分支，mean=0、std=1（core_algos.py:316-317），advantage 就是原始 reward。GRPO 文档明确要求把 rollout.n 设成大于 1（docs/algo/grpo.md:29）。
  • σ 归一化可以关。norm_adv_by_std_in_grpo 默认 True（verl/trainer/config/algorithm.py:737）；Dr. GRPO 把它设为 False（docs/algo/grpo.md:62）。关掉只减均值，advantage 落在原始 reward 差的范围内；这不是「修复」，是换一种权重结构。

自己动手：G 和 p 怎么改变「零方差组」的自然占比

DAPO §3.2 要过滤 accuracy 为 0/1 的组（Eq.11）；全对组 advantage 为 0 是原文点名的例子，全错组由同一公式同样为 0。§4.1 用 G=16、每批 512 个 prompt。把二值 reward 近似成「每条回答独立、以概率 p 正确」，一组全同的概率就是 pG + (1−p)G。默认 G=16、p=0.90 时：全对组 18.53%，全错组 0.0000%，零方差合计 18.53%；512 个 prompt 中约 417.1 个仍有组内比较信号。

公式：全对 pG，全错 (1−p)G，零方差为两者之和；有效 prompts = 512 × (1 − 零方差)。512 是 DAPO §4.1 的 prompt batch size；G=16 也来自 §4.1。

组 1：G=16，p=0.90。

  • 全对：0.916 = 0.1853020189 → 18.53%
  • 全错：0.116 = 0.0000000000000001 → 0.0000%
  • 零方差：0.1853020189 + 0.0000000000000001 = 0.1853020189 → 18.53%
  • 有效 prompts：512 × (1 − 0.1853020189) = 417.125366 → 417.1

组 2：G=8，p=0.75。

  • 全对：0.758 = 0.1001129150 → 10.01%
  • 全错：0.258 = 0.0000152588 → 0.0015%
  • 零方差：0.1001129150 + 0.0000152588 = 0.1001281738 → 10.01%
  • 有效 prompts：512 × (1 − 0.1001281738) = 460.734375 → 460.7

覆盖与未覆盖：这个模型覆盖「二值 reward、同组独立同分布」下的零方差比例；它不覆盖连续 reward 的近似相等、同组回答之间的相关性、题目难度异质，也不模拟动态采样后的分布变化。它是本页的概率模型，不是论文测量；真实训练要以自己的题集难度分布做基线。分项按四舍五入显示、合计按未舍入值计算，所以显示的分项相加可能与合计差 0.01 个百分点。

为什么不是固定 50%：同一个 p，G 从 8 变到 16，零方差占比会变；同一个 G，p 从 0.9 变到 0.99，全对组会明显变多。固定百分比无法跨 G、跨题集使用。verl 的过滤条件是精确 std==0（verl/trainer/ppo/v1/replay_buffer.py:312），不是百分比阈值。

别误读

指标 NaN 不一定来自 exp 爆炸

compute_data_metrics 在整批样本都 abort（response length 为 0）时，会把 score、reward、advantage 直接设成 NaN 并打 warning（score/reward：metric_utils.py:468-488；advantage：:490-499）。看到 NaN 先看 response/aborted_ratio，再沿计算图找第一个非有限值；不要一上来就收紧 log-ratio clamp。

顺序

先问「这一组还有没有比较信号」

全对组和全错组的 advantage 都是 0，但处置方向不同：全对多说明数据对当前模型太简单；全错多可能是验证器过严或模型能力不够。DAPO §3.2 的动态采样把两类都过滤；实际排查要先拆构成，再决定换数据、查 verifier，还是开过滤。

04

verl 的曲线有明确来源：先确认你看的是哪个前向、哪个默认值

actor/entropy、actor/ppo_kl、actor/grad_norm 各自来自不同阶段；默认配置还会让某些检查静默失效。

verl 一个 step 的顺序是：rollout 生成（ray_trainer.py:1508-1526）→ reward（:1560-1567）→ old_log_prob 前向并算 entropy（:1584-1600）→ ref_log_prob（:1620-1622）→ advantage（:1627-1667）→ update_actor（:1689-1690）→ update_weights（:1715-1716）。这决定了每个指标对应哪一版策略。

容易读错

actor/entropy 是更新前旧策略的熵

在默认 recompute 路径下，_compute_old_log_prob 把 calculate_entropy=True 固定传给 worker（ray_trainer.py:1300），返回值在 :1590-1600 聚合成 actor/entropy。它衡量的是这一批 rollout 所对应的旧策略，不是 update 之后的新策略。actor.calculate_entropy 默认 false（actor.yaml:96）只控制 update 前向是否返回 entropy（ray_trainer.py:1336-1338），不影响上面这条曲线。注意 algorithm.rollout_correction.bypass_mode=True 时 _compute_old_log_prob 会被跳过（ray_trainer.py:1571-1584），该曲线不产生。

actor/ppo_kl 不是到 reference 的 KL：它是 mean(-(log_prob - old_log_prob))，且 log-ratio 在 exp 前被 clamp 到 [-20,20]（core_algos.py:1254-1258）。到 reference 的 KL 有两条路：algorithm.use_kl_in_reward=True 时记 actor/reward_kl_penalty（ray_trainer.py:100-115）；actor.use_kl_loss=True 时记 kl_loss（verl/workers/utils/losses.py:181-182）。三个名字不能混着读。

actor/grad_norm 是裁剪前的 norm（transformer_impl.py:735 的 docstring；:748-752 调 clip 函数并拿到返回值），由 trainer 在 ray_trainer.py:1788 读取。非有限时 FSDP engine 会 zero_grad 并跳过 optimizer.step（:765-769）——进程不一定挂，但这一步没有更新。日志里只出现一次 WARN 和连续出现 WARN，含义完全不同。

工程起手

先保存三态，再谈任何曲线

最后一个正常 step、第一个异常 step、异常之后的一个 step。每个 step 落盘 rollout 原文、reward 分项、old/current logprob、ratio 分位数、attention/loss mask、clip fraction、裁剪前后 grad norm、batch ID 与随机种子。没有这个最小故障窗口，后面的「改一个变量重放」都是噪音。这是笔记的工程流程，不是论文实验设计。

05

先工程后算法：前一层不通过，后一层的曲线没有解释意义

一张图把症状分流：先读 rollout 原文，再验概率一致性与数值路径，最后才动 clip、采样和学习率。

图上的 0/1 检查顺序可以展开成：概率一致性（同一批 token 在训练侧两次、推理侧一次）→ 梯度累积等价性 → 逐 token mask → 数值路径的第一个 NaN/Inf → optimizer / reward。这个顺序的关键不是「优雅」，而是每一层都有通过条件：ratio 的分子分母不是同一套概率口径时，后面的 clip fraction、KL、lr 扫描都失去原义。

如果只能做一件事，先做权重没变时的 ratio 检查（笔记的 A/B/C 检查）：冻结权重、关 dropout、固定 RNG，同一批 token 在训练侧前向两次、在推理侧前向一次。训练侧两次不一致，查训练框架自身的可重复性；训练侧和推理侧不一致，查两套实现的概率口径。权重没动但大量 token 已经撞 PPO clip，说明训练目标把实现差异误读成了策略更新 工程判断——这时应先停训修口径，而不是调 clip。

RL 提升 Maj@K，但没有提升 Pass@K

DeepSeekMath §5.2.2 / Figure 7 报告：RL 后的模型在 GSM8K 和 MATH 上 Maj@K 提升，Pass@K 没有提升（原文措辞是 not Pass@K）。原文的解释是 RL 让输出分布更稳、把正确回答从 TopK 里抬出来，而不是提升基础能力。对排查的含义是：训练 reward 或 Maj@K 上涨，不能单独证明分布没有变窄；如果 Pass@K 相对基线变差，才更像坍塌方向的证据（这是本页对 Figure 7 的延伸解读，不是原文的 collapse 判据）。

DAPO

entropy 要维持在合适区间，不是越低越好

DAPO §4.3 把 response length、reward、generation entropy、mean probability 列为监控指标：entropy 过低表示分布过尖、失去探索；过高常伴随 gibberish 和重复生成。Figure 7(c) 是 generation entropy，Figure 7(d) 是 mean probability。原文没有给一个跨模型通用的 entropy 数值，只给了方向性判断。

代码侧还有两个反直觉的「效果」：非有限 grad 不一定让训练挂掉——FSDP engine 会跳过这一步的 optimizer update（transformer_impl.py:765-769），所以日志里可能只有一行 WARN，曲线表现为「少更新了一步」；指标 NaN 不一定是数值爆炸——整批 abort 时 compute_data_metrics 会主动返回 NaN（score/reward：metric_utils.py:468-488；advantage：:490-499）。这两种情况都应该先看原始日志和 aborted ratio，再决定是否改算法。

07

判据能分流，不能确诊：没有通用阈值，症状还会互相转化

什么时候别用这套二分：只有一条曲线、无法重放、或者把 OOM / 全 abort 当成算法坍塌。

适用

能读 rollout、能重放、能对齐概率口径

你有原始 rollout 和 reward 分项，能保存最后正常/首个异常/异常后一步，能在冻结权重下重放同一批 token。此时二分法能快速决定先查工程还是先查算法，零方差计算能给出题集难度的自然基线。

不适用

只有看板截图，或 reward 本身就不可验证

只有 reward / entropy 两条曲线、没有 rollout 原文，无法区分「输出变窄」和「验证器坏了」；reward 是学习出来的 RM 且没有独立复核时，reward 上涨可能只是 hacking。多轮 agent 的工具 token / loss mask 也是高发点，不能只用 GRPO 的组内公式解释。

  • 没有通用的 entropy / 零方差百分比阈值。DAPO §4.3 只说 entropy 要维持在合适区间；verl 的过滤条件是精确 std==0（replay_buffer.py:312），不是「超过多少就报警」。先在自己的干净配置上量 baseline，再比较故障 run。
  • DAPO 的四件套有明确条件。Qwen2.5-32B、长 CoT 数学、规则 reward、G=16、无 KL、prompt batch 512、εlow=0.2 / εhigh=0.28（§4.1；无 KL 见 §2.3；规则 reward 见 §2.4）。搬到 RLHF、agent 或不同模型规模前，要重新验证；Table 1 的 +8 也不是「开动态采样就一定 +8」。
  • DeepSeekMath 的设置不同。G=64、KL 系数 0.04、max length 1024、batch 1024、每个探索阶段只更新一次（§4.2）。它的 Figure 7 是 Maj@K / Pass@K 的诊断，不是 collapse 的判定表；两篇论文的数字不能直接拼成同一组对照。
  • OOM 不是算法坍塌。verl 文档把 micro batch 配置描述为「避免 GPU OOM」且「不应改变算法 / 收敛行为」（docs/algo/grpo.md:23；docs/start/quickstart.rst:157-162）。修 OOM 是恢复可训练性，不会修掉分布变窄。工程判断
  • 全同组不一定是病。全对组通常说明这批题对当前模型太简单，或采样温度太低推断；DAPO §3.2 的动态采样会过滤它，代价是额外生成；过滤还会改变有效 prompt 分布（笔记的工程观察，不是 §3.2 原文结论）工程判断。DAPO 在其设置下报告收敛更快（Figure 6），这不等于所有数据分布都免费。
  • 跳过 NaN 步不是修复。transformer_impl.py:765-769 的 zero_grad 只是防止坏更新写进参数；如果 WARN 连续出现，根因仍在概率口径、mask 或数值路径上。
  • 两类会互相转化。Entropy collapse 的末端可能表现为 reward 断崖；训练崩溃也可能渐进（例如异步数据陈旧）。二分法是工作分类，不是定理；复杂情况按信号链一层层过 推断（依据：DAPO §3.1 的 collapse 现象与 verl 的工程故障点并不共享同一个时间尺度）。
一句话

先找第一个坏掉的张量，再解释最后一条异常的曲线

如果组内还有 reward 方差，就先看 advantage 和 clip；如果组内已经全同，就先统计全对/全错；如果出现 NaN / Inf / 非有限 grad，就先沿计算图找第一个非有限值。顺序对了，降 lr 才不会变成把 bug 推迟到视野之外的稀释手段。
