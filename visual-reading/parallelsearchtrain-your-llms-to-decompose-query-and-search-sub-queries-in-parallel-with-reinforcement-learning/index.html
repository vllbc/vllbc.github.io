ParallelSearch：用一个 ## 把独立子查询压进同一轮检索

现有 search agent 每一步只发一个查询，哪怕两个子查询在逻辑上互不依赖。 论文用 RL 训练模型在 <search> 里用 ## 拆分可并行子查询， 一次动作里并发检索，再用四项奖励约束「该拆的拆、不该拆的不拆」。 代价是：只验证了 Qwen2.5-7B + E5 + 2018 Wikipedia，且 α 与 λf 的数值未在原文给出。

Shu Zhao, Tan Yu, Anbang Xu, Japinder Singh, Aaditya Shukla, Rama Akkiraju · NVIDIA / Pennsylvania State University arXiv 2508.09303v1 ↗ 博客笔记 ↗
TL;DR · 30 秒抓住核心

问题不是「搜索次数不够」，而是独立的比较子查询被当成有依赖： Search-R1 这类代理严格串行，Monet / Pissarro 的例子要 3 次 LLM 调用、2 轮 search（§1）。

论文的并行扩展只有一条语法约定：在 <search> 内用 ## 分隔子查询； Algorithm 1 解析后并行检索，把结果拼进同一个 <information>。 学习信号是四项奖励之和：结果、分解、搜索次数、格式（Eq. 3–7）。

七个基准上，Qwen2.5-7B-Base 的平均 EM 为 0.458， 比 Search-R1 的 0.434 高 2.4 个百分点； Instruct 为 0.425，比 ZeroSearch 的 0.391 高 3.4 个百分点；两档平均 +2.9 个百分点（Table 2）。 并行子集六行平均 #Turns 从 3.36 降到 2.34，对应 LLM 调用相对减少 30.4%（Table 3）。

边界：MultihopRAG-par 的 Base 行 EM 只从 0.569 到 0.573（+0.4 个百分点）， 且低于 Search-R1+Parallel Prompt 的 0.598；可并行 / 不可并行的标签来自数据集问题类型， 不是模型在线判断的真实依赖。

01

独立子查询被当成有依赖：两轮搜索、三次 LLM 调用

先建立共同认知：串行不是「慢一点」，而是把本可并行的比较题拆成多轮 LLM 调用。

Search-R1 这类 search agent 用 RL 训练 LLM 在多轮里交替推理与检索： 每轮先生成 <think>，再生成 <search> 查询， 拿到 <information> 后继续推理，直到写出 <answer>（§3.1）。 这个循环默认「后一个查询依赖前一个查询的结果」，即使两个子查询在逻辑上互不依赖。

论文在 §1 给的例子：问「Who is older, Claude Monet or Camille Pissarro?」， 代理必须先查 Monet 的生日、分析结果，再查 Pissarro 的生日，最后比较。

Current search agents must first generate and execute a query for Claude Monet's birth date, analyze the results, then separately query for Camille Pissarro's birth date, before finally synthesizing both results. This workflow requires three LLM calls and two sequential search operations.

这段话把成本拆得很清楚：3 次 LLM 调用、 2 轮串行 search。生产环境服务大量查询时， 这些轮次会累积成延迟与调用成本（§1）。

论文的关键观察是：很多复杂查询天然包含逻辑上独立、可并发的子组件， 并发检索并不会牺牲推理质量（§1）。上面的 Monet / Pissarro 例子就是两个实体各查一次生日， 两次检索之间没有依赖。

可并行

comparison：两个实体各查各的

§3.3 的定义：comparison 查询比较两个实体，可以拆成两个子查询，每个实体一个。 Table 7 的案例就是这种结构：<search> location of Laleli Mosque ## location of Esma Sultan Mansion </search>。

不可并行

bridge：后一步依赖前一步的答案

§3.3 的定义：bridge 查询需要在桥接段落上推理，因此不可分解。 例如先查「2014 S/S 是哪个组合的专辑」，再查「谁创立了这个组合」； 第二问的查询词依赖第一问的答案（Table 9 的案例）。

所以问题不是「检索不够多」，而是执行图被固定成一条链： 能并行的边也被排成串行。论文要学的是「什么时候可以并行、什么时候必须串行」， 而不是简单地让模型多搜几次。

02

Search-R1 只会串行；加一句并行提示，轮次并没有稳定下降

两条现有路线：端到端 RL 搜索代理，和 prompt 式并行提示；后者的轮次收益在 Table 3 里并不整齐。

Search-R1

多轮 RL，但严格串行

Search-R1 用 RLVR 训练 LLM 交替 think / search，轨迹写成 (t0, s0, c0, …, tn, a)（Eq. 1）。 奖励主要看最终答案是否正确，不约束检索的执行顺序（§2.1、§3.1）。

卡在哪：每一步 search 都等上一步的 information；比较类问题也要两轮检索。

Search-R1 + Parallel Prompt

只改提示，不改训练

把 Table 1 的模板（含 ## 示例）直接给 Search-R1，模型可以输出分解后的查询， 但策略没有经过「分解是否正确、轮次是否该降」的奖励训练。

卡在哪：Table 3 里它的 #Turns 并不稳定下降，Base 三行甚至从 4.00 升到 4.98 / 4.97 / 4.95。

其他基线

优化检索，不优化并行

ZeroSearch 用模拟搜索引擎降低训练成本；StepSearch 做 step-wise PPO； OTC 用奖励函数惩罚更长的交互轨迹（§4.2：OTC proposes a reward function to give a penalty to trajectories with longer interactions.）。 它们改进的是检索质量或轨迹长度，不是「把独立子查询放进同一轮」。

论文在 §2.1 的总结是：Despite these advances, existing search agents execute queries in a strictly sequential manner. 这句话把已有方案的范围划得很清楚：检索质量可以继续提升，但执行图仍然是一条链。

原文与表格并列

「轮次没有下降」这句话，Table 3 有一行例外

§4.3 的原句是：However, the number of turns is not reduced, and we believe that Search-R1 cannot correctly follow the parallel instruction. 但 Table 3 的 2wiki-par / Instruct 行，Search-R1+Parallel Prompt 的 #Turns 是 2.64，低于 Search-R1 的 3.05；同一张表的另外五行则高于 Search-R1 （HotpotQA-par Instruct 2.46 vs 2.37；Base 4.98 vs 4.00；2wiki-par Base 4.97 vs 4.00；MultihopRAG-par Instruct 3.37 vs 2.73；Base 4.95 vs 4.00）。

页面把原句和表格并列，不替原文做概括。能确认的是：prompt 式并行在 Table 3 的多数行没有降低轮次， 但 2wiki-par / Instruct 这一行确实降低了。

03

一个 ## 分隔符 + 四项奖励：该拆的拆，不该拆的不拆

并行扩展只有一条语法约定；学习信号靠四项奖励拼出来。

并行动作：一次 <search> 里提交多个子查询

Table 1 的模板要求模型在 <search> 与 </search> 之间写查询， 多个子查询用 ## 分隔：

<search> sub-question 1 ## sub-question 2 </search>
Table 1 的模板示例；模型在一次 search 动作里可以提交多个子查询。

Table 1 的完整模板未转录；这里只引用 <search> 与 ## 的语法示例。

Algorithm 1 的执行顺序是：先从 <search> / </search> 之间取出拼接查询， 按 ## 拆成 {qi}，并行调用搜索引擎得到 {di = R(qi)}，再把所有结果拼进同一个 <information>[d1, …, dn]</information>（Algorithm 1 第 15–18 行）。 如果模型既没输出 search 也没输出 answer，算法会追加一句 「My action is not correct. Let me rethink.」继续 rollout（Algorithm 1 第 22 行）。

四项奖励：结果、分解、搜索次数、格式

最终奖励是四项之和：r = ro + rd + rs + rf（Eq. 7）。 下面按 Eq. 3–6 逐项拆开。

结果奖励

答案对错，EM 二值

ro = EM(agold, apred)（Eq. 3）。 精确字符串匹配为 1，否则为 0。它只看最终答案，不看过程。

分解奖励

该拆的拆、不该拆的不拆

rd 按查询是否可并行 q ∈ P 和模型是否分解 D(q) 分三种情况（Eq. 4）；α > 1 让可并行查询的分解奖励高于 λd，因为训练集里可分解查询明显更少。

Eq. 4 · §3.3 · 分解奖励 · P = 可并行查询；D(q) = 模型是否分解；λd 为正、α > 1。

条件含义rd
q ∉ P 且未分解不该拆，也没拆λd
q ∈ P 且已分解该拆，拆了α λd
其它该拆却没拆，或不该拆却拆了0

按 Eq. 4 逐项读：「不该拆却拆了」拿的是 0，不是负值； 它相对「不拆」少拿了 λd。真正的负值来自 rs 的轮次惩罚，或 rf 在「答对但格式错」时的扣分； ro 答错只是 0。

搜索次数奖励

可并行与单跳要 1 轮，不可分解多跳要 2 轮

rs 对 q ∈ P ∨ q ∈ S 用 −λs|count<search> − 1|； 对其它查询（不可分解的多跳）用 −λs|min(count<search>, 2) − 2|（Eq. 5）。 count = 0 时两项都为负，用来抑制「不检索、直接凭参数记忆作答」（§3.3）。

格式奖励

格式与答案交叉奖惩

rf：答案对但格式错，扣 λf； 答案错但格式对，加 λf；其它为 0（Eq. 6）。 论文只要求 λf 为正，正文与 Appendix A.4 都没有给具体数值。

Eq. 5 · 搜索次数奖励 · S = 单跳查询；count<search> 是轨迹里 search 动作的个数。

反直觉 1

Instruct 的提升更大，但 Base 的最终平均分更高

§4.2 的原句是：The improvement of the instruct model is larger than the base model. We achieve absolute improvements of 3.4% and 2.4% using the Instruct and Base models, respectively. 实验范围

一个模型家族、一个检索器、一个语料

  • 只测 Qwen2.5-7B 的 Base / Instruct 两档（§4.1、A.4）；没有更大模型或其他模型家族。
  • 检索器固定 E5，语料固定 2018 Wikipedia dump（MultihopRAG 用自带 corpus），每问 3 段（§4.1、A.4）。
  • 全部实验在 8×H100 上完成（§4.1）；没有报告训练总时长或美元成本。
  • 答案质量指标只有 EM；另有 DR、推理时间与 #Turns 等过程指标；没有 F1、LLM-as-judge 或人工评测。
可并行性定义

来自数据集的问题类型，不是在线依赖判断

  • HotpotQA 用 comparison 构造 parallel 子集、bridge 构造 sequential 子集；2WikiMultiHopQA 用 comparison 构造 parallel、inference / compositional 构造 sequential；MultihopRAG 用 comparison_query 构造 parallel、inference_query 构造 sequential（§A.2）。
  • 论文没有测试「弱依赖」「部分可并行」或依赖关系模糊的查询；这些情况不在 Table 3 的范围内。
  • 模型在测试时自行决定是否并行（§4.3），但训练和评测的标签仍来自数据集类型。

什么时候别用

依赖关系强、上下文预算紧、需要统计显著性时

  • 查询之间有强依赖：按 §3.3 的 bridge 定义，后一问依赖前一问答案，强行并行的子查询会拿不到正确检索词 推断（依据：§3.3 与 Table 9 的 sequential 案例）。
  • 上下文预算紧：一次并行 N 个子查询会把 N 份检索结果塞进同一轮上下文；论文只给了 retrieved content max 500 tokens，没有给 N 增大时的压力测试。
  • 需要统计结论：表格只给点估计，没有方差、置信区间或多 seed 结果；不能据此判断差异是否稳定 推断（依据：Table 2–4 只列点估计）。
  • 需要真实 Web 检索：实验用 2018 Wikipedia / benchmark corpus，不是实时搜索引擎；真实 Web 的延迟、失败率和文档长度分布不同。
