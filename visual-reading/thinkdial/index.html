ThinkDial：给开源推理模型装一个 High / Medium / Low 的三档旋钮

gpt-oss 系模型让用户用「低 / 中 / 高」选择思考投入，但这套做法一直是闭源的。ThinkDial 把配方拆成三步公开：先用 SFT 教会模型「同一道题按三种深度各写一遍」，再先用 RL 把 High 档推到性能上限，最后才加长度奖励压中、低两档。 代价是：压缩目标一旦进奖励，模型会学会把推理藏进答案区——论文为此加了一个关键词惩罚。

Qianyu He, Siyu Yuan, Xuefeng Li, Mingxuan Wang, Jiangjie Chen · ByteDance Seed / Fudan / SJTU arXiv 2508.18773v1 ↗
TL;DR · 30 秒抓住核心

三档模式的目标写在摘要里：High 完整推理；Medium 思考 token 减少 50%、性能损失 <10%；Low 减少 75%、损失 <15%。论文在 Qwen-2.5-Instruct-32B 上按这三个目标训练并在 AIME 2024/2025、GSM8K、GPQA 上评测。

关键是顺序不能反：先做预算模式 SFT（同一题生成三份截断到 100%/50%/25% 的思考链并重写答案），再 95 步 High 档 RL 预热到峰值，最后 40 步带长度奖励的 RL。消融显示，跳过任一步，High 档都会掉到峰值以下（Table 1）。

最反直觉的一处是 Reasoning Length Hacking：没有泄漏惩罚时，模型把思考截短、却把推理搬进答案区，总 token 不降反升。惩罚项就是在答案区里检测 「Wait」这类词并给 −0.5。

01

同一个模型，要同时做到「想得深」和「想得快」

这一节要建立的认识：问题不是「推理太长」本身，而是「长度没法按需调节」——同一份权重，面对简单题和难题该给出两种行为。

长 CoT 模型在难题上有效，但会生成大量冗余步骤、循环推理；这些 token 既是实打实的算力与延迟，也把错误沿着链条放大（§1）。对部署方来说，客服问答和科研推演对「想多久」的要求完全不同。

论文把可用性要求拆成三条（§1）：

  • 不需要懂 token 经济学：用户只表达偏好，不填精确预算；
  • 按题目难度分配：而不是所有题都被一刀切；
  • 同一道题要有多档：而非「想 / 不想」二元开关。
为什么难

压缩目标和正确性奖励天然打架

一旦在奖励里加「越短越好」，最省力的达标方式不是少想，而是把想的东西挪到评分只看得到「正确」的地方。论文观察到的 Length Hacking 就是这条捷径——这决定了方法里必须有一个防挪移的机制。

02

两条已有路线：一条要用户报预算，一条只给二元开关

这一节要建立的认识：现有可控制推理的工作，要么「不可用」，要么「不可分级」；三档模式目前只有闭源实现。

路线 A

显式 token 预算

训练或推理时直接指定思考 token 上限（§2 引 [4, 6–8]）。

卡点：很难为不同难度的题给出合适预算——GSM8K 和 AIME 该给多少，用户根本判断不了。

路线 B

自适应 CoT

让模型自己决定要不要思考（§2 引 [5, 9, 10]）。

卡点：只有「思考 / 不思考」二元档，同一道题给不出多种效率优先级的中间档。

第三类做法是 gpt-oss 式的三档离散模式：低 / 中 / 高，用户按偏好选。论文的判断是它在可用性和分级性上同时占优，但「existing three-mode implementations remain proprietary」（§2）。ThinkDial 的目标就是在开源模型上把这套行为复现出来，并把它称为首个 open-recipe 的三档方案（原文用词，见摘要与 §2）。

03

一个模式一句话：奖励 = 正确性 + 模式缩放 × 长度项 + 泄漏项

这一节要读懂的：三档差别只落在两个地方——数据里的截断比例 r，和奖励里长度项的权重 α。

第二阶段 RL 对第 i 条输出在模式 m 下的总奖励是（Eq. 3）：

Ri(m) = Rtask(oi) + α(m) · Rlength(oi) + Rleak(oi)
Eq. 3 · Rtask ∈ {0,1}（精确答案匹配）；Rleak ∈ {−0.5, +0.5}

长度项本身按同组内的相对长短给分（Eq. 4）：

Rlength(oi) = λi  若 Rtask=1,   min(0, λi)  若 Rtask=0
λi = 0.5 − ( len(oi) − lenmin ) / ( lenmax − lenmin )
Eq. 4 · len 含 <think> 内外全部 token；lenmin / lenmax 取当前 rollout 组内的最小 / 最大长度，所以 λ 落在 [−0.5, 0.5]

三档的区别全部在 α 上（§4.1）：α(high)=0.0、α(med)=0.5、α(low)=1.0。High 档长度项权重为 0，等价于纯正确性训练；Low 档长度项的幅度是 Medium 的两倍。SFT 数据端的对应旋钮是截断比例 r：High 1.0、Medium 0.5、Low 0.25。

Length Hacking

答题对了，但想法被搬进了答案区

Rtask 只看最终答案，长度项只看总 token 数。模型于是可以在 <think> 里草草收尾，把真正的推演挪到 </think> 之后、最终答案之前——正确率保住，思考段变短。论文指出，这个模式来自 SFT 数据本身：Low 档样本因激进截断，推理常常溢出进答案区，RL 又把它强化了（§3.2.3）。

应对是 Eq. 5 的二值泄漏惩罚：答案区出现「Wait」「Let me think」「Actually」等过渡词得 −0.5，没有得 +0.5。Appendix C 给了对照案例（Table 7 / Table 8）。

组 2：lenmin=2000, len=3500, lenmax=8000，Medium（α=0.5），任务正确，无泄漏（Rleak=+0.5）。

λ = 0.5 − (3500−2000)/(8000−2000) = 0.5 − 0.25 = 0.25
Rlength = 0.25
R = 1 + 0.5 × 0.25 + 0.5 = 1 + 0.125 + 0.5 = 1.625

若同一组参数任务错误：Rlength=min(0, 0.25)=0，R = 0 + 0.5 × 0 + 0.5 = 0.5——错误答案拿不到长度加成，但也不会被长度项倒贴。

组 3（Low 档拉开差距的例子）：len=7000、其余同上、正确、无泄漏。λ = 0.5 − (7000−2000)/6000 = 0.5 − 0.8333… = −0.3333…；Low：R = 1 + 1.0 × (−0.3333…) + 0.5 = 1.1667；Medium：R = 1 + 0.5 × (−0.3333…) + 0.5 = 1.3333；High：R = 1.5。同一组长输出，Low 档被压得最低——这就是 α 控制压缩强度的直接体现。

页面显示的 λ、Rlength 保留 4 位小数，总奖励保留 4 位小数；上式结果按同一舍入显示。DAPO 的组内标准化 Ai 不属于本交互范围，这里只看原始奖励。

04

训练分三步，顺序本身就是设计

这一节要知道：每一步的数据量、步数、超参各是多少，以及为什么 SFT 和预热都不能省。

第一步：预算模式 SFT（Budget-Mode SFT）

从高质量完整推理链出发，在约 rmed=0.5、rlow=0.25 处截断思考段，在 </think> 前补一句模式相关的衔接语，再重写答案段，只保留逻辑连贯且答案正确的样本（§3.1、Appendix B）。每个模式配一段独立的 system prompt（Table 2）。SFT 目标是三档负对数似然（Eq. 1），三档样本量均衡（high:medium:low = 1:1:1）。

第二步：High 档预热 RL（95 步）

不加任何压缩项，先把模型推到峰值，作为后面压缩的参照线。消融里跳过这一步的 w/o Warmup 在 Table 1 的三档平均分全部低于 ours（AIME 2024 69.6 对 80.0）。推断（依据：Table 1 末列；但 w/o Warmup 在 GSM8K 的低档反而略高，见 06 节）

第三步：带长度奖励的 RL（40 步）

基于 DAPO：组大小 G=16，clip 下界 0.2、上界 0.28，学习率 1×10⁻⁶、20 步线性 warm-up，温度 τ=1.0（Appendix D）。总步数 95+40=135 步，与 Appendix D 的「135 steps」一致。预热阶段用 Dynamic Sampling，长度奖励阶段关掉它——论文的解释是长度奖励本身就能在全员全对或全错的组里提供梯度（Appendix D）。

06

三档平均分全部第一，但「消融哪个」的结论并不整齐

这一节要读懂的：ACT 分数怎么算、Table 1 里谁赢谁输，以及论文没在正文给出的原始准确率 / token 数。

ACT 分数是怎么合成的

对每个模式 m，准确率保留比 Am = Accm / Accbase，压缩率 Cm = 1 − Costm / Costbase，base 取峰值 checkpoint（Eq. 6）：

SACT = Σm ( β(m) · Am + (1 − β(m)) · Cm ) / |M|    β(m) = 1（High）或 0.5（Medium / Low）
Eq. 6–7 · High 只看保留准确率，中低档准确率与压缩各占一半

表中数值以「×100」的形式给出。因此 ACT 不是准确率，而是一个把准确率保留与 token 压缩混在一起的加权分，下面所有高分都应按这个口径读。

07

它能控档，但还不能证明「迁移、线性和防绕过」

这一节要知道：哪些结论论文没做，哪些是页面替你读出来的含义。

  • 只有一个底座：全部实验基于 Qwen-2.5-Instruct-32B（§4.1）。换到其他模型家族是否同样成立，论文未验证——「开源配方」目前只在单点上演示过。
  • 主要证据是曲线：原始准确率与思考 token 数只以 Figure 1–5 的曲线呈现，正文没有给出对应的数值表；Table 1 是合成后的 ACT 分数。想复现某条曲线的具体点，原文数据不够。
  • 防绕过是关键词检测：Rleak 只检查答案区有没有「Wait」「Let me think」等过渡词（§3.2.3，Eq. 5）。推断（依据：Eq. 5 的二值规则；论文未做换同义词后的鲁棒性实验）——改用好话术是否还能骗过它，论文没有测试。
  • 训练域 = 数学：训练数据是数学题，GPQA 用来测 OOD 迁移。论文没有在写作、代码等开放任务上评测「低档是否只是变短」。
  • 档位是离散的：只有 High / Medium / Low 三档，没有连续可调的旋钮；同一档内的长度由 RL 在组内相对长度上塑造，而不是由输入预算精确指定。
  • 压缩目标的表述要分清：摘要 / §3.3 写的是「50% / 75% token 减少」，而 Table 3 是 SFT 数据里 High:Medium:Low 的平均思考长度 9440.0 : 5125.3 : 1302.7（中档为 High 的约 54.3%，低档约 13.8%，其中低档还含空思考样本）。推断（依据：Table 3 与 §B.1 的 800 条空思考 GSM8K）——训练数据的目标比例与最终模型的实际压缩率不是同一个量，页面不把 50% / 75% 当作 Table 3 的结果。
