Tokenization：词表大小是一场压缩率与算力的交换

模型看不到文本，只看到整数 ID；tokenizer 决定一句话被切成多少个 ID。 BPE 从字符出发反复合并最高频的相邻对，WordPiece 换成似然增益，Unigram 先建大词表再按损失剪枝，byte-level BPE 则把 byte 值当底座，让任何文本都能表示。 代价写在词表上：embedding 是 V×d，输出层每 token 要 V×d 次乘加，也就是 2×V×d FLOPs。

BPE · SentencePiece · Llama 3 · Qwen2/3 · tiktoken BPE ↗ SentencePiece ↗ Unigram LM ↗ Llama 3 ↗ Qwen2 ↗ Qwen3 ↗ tiktoken @ 4e71bbe ↗
TL;DR · 30 秒抓住核心

Tokenizer 是模型的输入字母表，而且先于预训练冻结。它决定同一句话占多少 token，也就决定了上下文预算、训练语料被读多少遍，以及推理时每 token 的输出层开销。 BPE 的规则最简单：从字符或 byte 出发，反复把加权频次最高的相邻对合并成一个新符号；词表大小等于初始符号数加合并次数（BPE §3.2）。

三条路线只改「合并哪一对」：BPE 看频次，WordPiece 看似然增益，Unigram 先建大词表再按移除后的损失剪枝。 byte-level BPE 把底座换成 256 个 byte 值，任何 UTF-8 文本都能拆，不会出现 UNK；SentencePiece 则把空格转义成 ▁，直接从原始句子训练，不再依赖预分词。

词表不是越大越好。词表越宽，输入 embedding 和输出层也越宽；Llama 3 8B 的输出层在 128,000 词表下，每 token 需要 1,048,576,000 FLOPs，对应 524,288,000 次乘加（按 1 次乘加 = 2 FLOPs 计）。 换来的压缩率是：相比 Llama 2 tokenizer，Llama 3 在英语样本上的压缩率从 3.17 提到 3.94 字符/token，相对提高 24.3%（(3.94 − 3.17) / 3.17）。

证据并不整齐：独立 BPE-60k 在德语 newstest2013 上把 UNK 从 1,079 压到 0；8 模型集成下，它的稀有词 F1 比 WDict 高 4.1 个百分点，joint BPE-J90k 高 5.0 个百分点。 但 BPE-60k 的单模型 BLEU 比字典基线低 0.5 分（BPE Table 2）。 SentencePiece 的 8k 共享词表在 KFTT 两个方向都高于 80k/80k 词模型，预分词却只在一个方向帮忙（SentencePiece Table 1）。

01

词表一冻结，文本长度和模型成本就跟着定死

先建立共同认知：tokenizer 定义模型的输入字母表，词表大小同时决定序列长度、embedding 参数量与输出层算力。

神经网络只接受固定形状的整数张量。文本要先经过一张词表，把每个切分单位映射成一个整数 ID；这张词表在预训练开始前训练好，之后不再变化。 同一个模型、同一段文本，换一套 tokenizer，token 数会变，能塞进上下文的字符数会变，训练时同一批算力读到的文本量也会变。 所以 tokenizer 不是预处理细节，它是模型设计的一部分。

两个极端都已被论文量化。词级模型把每个词当一个 token：BPE 论文的德语训练语料有 1,750,000 个词类型，newstest2013 上有 1,079 个 UNK；词表大，稀有词仍然会掉到词表外。 字符级模型把每个字符当一个 token：词表只有 3,000 个类型、UNK 为 0，但同一份 100m 词的语料膨胀到 550m 个 token，也就是每词 5.50 个 token，序列长度和注意力开销一起上升。

词表 V ↑ → 每词 token 数 ↓，但 embedding 参数 V×d ↑ 与 输出层 FLOPs 2×V×d ↑
词表大小同时出现在压缩率和参数/算力两侧；子词方法是在这条曲线上选一个工作点

子词方法选了中间点。BPE 用 59,500 次合并，把德语词表压到 63,000 个类型，UNK 为 0，token 数 112m，每词 1.12 个 token。 这组数字说明子词不是「更聪明的词表」，而是用更多类型换掉了 UNK，同时把序列长度压在词级附近。

难的地方不在「把词拆小」这件事本身，而在四个约束同时成立： 切分要可逆，解码后能还原原文；要能处理训练时没见过的字符和语言；要给定一个全局词表，不能按任务临时改；还要让合并规则在同一份语料上可复现。 后面的 BPE、WordPiece、Unigram、SentencePiece 和 byte-level BPE，都是在回答「合并哪一对、底座是什么、要不要预分词」。

02

词级和字符级各走极端，子词方法只改合并单位

词级词表大且 UNK 多，字符级零 UNK 但序列长；BPE、WordPiece、Unigram 的差别在于「合并哪一对」。

词级 + 回退字典

保留词边界，代价是 UNK 和巨大词表

BPE 论文的 WDict 基线用 300k 源语言词表、500k 目标语言词表，再加一个回退字典处理词表外的词； newstest2015 的英德翻译上，单模型 BLEU 是 22.0，八模型集成是 24.2（BPE Table 2）。 回退字典能救回一部分稀有词，但词表仍然是开放的：德语训练语料里 1,750,000 个词类型，newstest2013 上仍有 1,079 个 UNK。

词级模型还有一个固定成本：每个词都要在 embedding 里占一行，词表随语料里的词形增长，模型参数也跟着长。 这条路把「词」当成不可再分的最小单位，遇到新词就只能回退。

字符级 / 字符 n-gram

零 UNK，但序列长度翻几倍

字符级把底座缩到字符：德语语料只有 3,000 个类型， newstest2013 的 UNK 为 0；但 100m 词的语料变成 550m 个 token，每词 5.50 个 token。 字符 bigram 把序列压到 306m 个 token、每词 3.06 个 token，但仍有 34 个 UNK，因为测试集里出现了训练时没见过的 bigram。

字符 n-gram 用 n 调压缩率：n 越大，序列越短，词表越大；n 越小，词表越小，序列越长。 这条曲线说明「零 UNK」不是免费的，它把成本从词表转移到了序列长度。

03

BPE 反复合并最高频相邻对，词表大小 = 初始符号 + 合并次数

记住三件事：按词频加权数对、每次合并所有出现、词表只增不减；编码时只按学到的顺序套用。

count(A,B) = Σw freq(w) · 1[(A,B) ∈ w]
(A,B)* = argmax(A,B) count(A,B)
V = V0 + M
BPE 的合并规则（BPE §3.2, Algorithm 1）：数对不跨词边界，词频作为权重；M 是合并次数，也是这套算法最直接的控制量

初始符号是字符（或 byte），每个词末尾加一个词尾符号 </w>，这样解码时能知道词在哪里结束。 每轮统计所有相邻对的加权频次，取最高的那一对，把语料里所有出现都替换成新符号；新符号进入词表，原来的两个符号仍然保留。 因此词表大小从 V0 单调增加到 V0+M，不会先增后减。 编码时不再看频次，只按训练得到的合并顺序依次套用。

    因此它是简化模拟，不是源码还原。原文 Algorithm 1 用 Python 的 max(pairs, key=pairs.get) 取最高频对，并列时的行为依赖 dict 顺序；页面把并列规则显式写成「先遇到」， 以便 JS 与手算可复现。Figure 1 的图注用的是另一份字典 {low, lowest, newer, wider}，与 Algorithm 1 代码块里的 {low, lower, newest, widest} 不同；Figure 1 的图注没有给词频，页面无法按同一套规则复现， 所以交互与手算只使用 Algorithm 1 的字典，Figure 1 只作为原文示例提及。

    WordPiece：把「频次最高」换成「似然增益最大」

    WordPiece 和 BPE 一样自底向上合并，但打分不是频次，而是合并后训练数据似然的增益。 HF 文档给出的分数是 freq(ab) / (freq(a) × freq(b))： 两个符号一起出现的次数，比它们各自独立出现时的期望高出越多，越值得合并（HF 文档 §WordPiece）。 BERT 家族使用这套规则；它仍然产出确定性的合并序列，编码时按最长匹配切分。

    Unigram：先建大词表，再按损失剪枝

    Unigram 语言模型假设每个子词出现独立，句子概率是所有子词概率的乘积；给定词表，用 EM 最大化边际似然。 词表本身也从数据里学：先造一个足够大的 seed 词表，重复「EM 估概率 → 算每个子词的 loss → 保留 top η%」， 直到词表达到目标大小；单字符子词始终保留，保证任何词都能被切出来（Kudo §3.2）。 编码时用 Viterbi 找概率最高的切分（Kudo §3.2），所以同一句话只有一条最优路径，但训练时可以按概率采样多条（Kudo §3.3）。

    Byte-level BPE：底座换成 byte，UNK 消失

    byte-level BPE 把初始词表换成 byte 值域，任何 UTF-8 文本都能拆成 byte 序列，因此不存在「词表外字符」。 GPT-2 的词表是 256 个 byte token 加 50,000 次合并，再加 1 个 end-of-text 特殊 token，总计 50,257（tiktoken 的 gpt2 条目）。 tiktoken 的 byte_pair_encode 直接接收 &[u8]，在 byte 序列上按 merge rank 合并 （src/lib.rs:198）。

    「无 UNK」不等于「无成本」。byte 底座让稀有文字也变成多个 byte token，序列可能变长； 要压回来，就得在词表里给这些语言留位置。Llama 3 的做法是 100K tiktoken token 加 28K 非英语 token（Llama 3 §3.2）， Qwen2 与 Qwen3 则直接用十几万级的词表（Qwen2 §2.1 / Qwen3 §2）。

    SentencePiece：不预分词，空格变成 ▁

    SentencePiece 把输入当成 Unicode 字符流，空格也当普通符号，先用 meta symbol ▁（U+2581）转义， 再在原始句子上训练 BPE 或 Unigram，不需要语言相关的预分词（SentencePiece §2、SentencePiece §3.1）。 它的目标是 lossless tokenization：

    Decode(Encode(Normalize(text))) = Normalize(text)
    规范化后的文本必须能从 token 序列完整还原（SentencePiece §3.1）；连续空格也能保留，这是 subword-nmt 的 @@ 表示做不到的

    代价是分词器要自己处理归一化。SentencePiece 的 Normalizer 做 Unicode 规范化，Trainer 学子词模型， Encoder 在编码时先归一化再切分，Decoder 反向还原（SentencePiece §2）。 对没有空格分词的语言（日语、中文）来说，这一步把「预分词」这个语言相关的强约束去掉了； 代价是归一化规则也进了模型文件，换规则就要重新训练。推断（由 SentencePiece §3.5 说 Normalizer 编译进模型文件推出）。

    04

    训练是一次性开销，编码和词表宽度是长期账单

    BPE 训练要反复扫描语料，编码要逐块合并；真正的长期成本是 V×d 的 embedding 和 2×V×d 的输出层 FLOPs。

    三笔账

    数对、合并、查表

    • 训练：每轮重新统计相邻对，再合并所有出现。BPE 原文说实现上用索引和增量更新，避免每轮全量重扫（BPE §3.2）；SentencePiece 则把分段做成 O(N log N)：朴素 BPE 分段要 O(N²)，它用二叉堆管理合并（SentencePiece §3.2）。
    • 编码：tiktoken 先按正则把文本切成 piece，再对每个 piece 做 BPE；源码注释写明，n 个部分、m 次合并的朴素实现是 O(mn)，piece 通常很小，所以缓存局部性比堆的渐进复杂度更重要（src/lib.rs:174-176）。
    • 查表：每个 token 一次词表查找；special token 先按字符串匹配，命中后直接取固定 ID，不经过 BPE（src/lib.rs:390-431）。
    • 吞吐：SentencePiece §4.2 报告的分段速度约为英语 21k 句/秒、日语 74k 句/秒；tiktoken README 自述比同类开源 tokenizer 快 3-6 倍，页面没有独立复现这个数字。

    词表大小的账更直接。输入 embedding 是一张 V×d 的表；输出层要把 d 维隐状态投到 V 个 logits，每个 token 需要 V×d 次乘加，按 1 次乘加 = 2 FLOPs 计就是 2×V×d。 下面三行用论文里的 V 和 d 直接相乘：

    词表账本怎么乘：两组手算点开看分解

    组 A：Llama 3 8B，V = 128,000，d = 4,096

    1. 128,000 × 4,096：128,000 × 4,000 = 512,000,000；128,000 × 96 = 12,288,000；合计 524,288,000。
    2. 输出层每 token 的 FLOPs：2 × 524,288,000 = 1,048,576,000，即 1.05 GFLOPs/token。

    组 B：Qwen2-7B，V = 151,646，d = 3,584

    1. 151,646 × 3,584：151,646 × 3,500 = 530,761,000；151,646 × 84 = 12,738,264；合计 543,499,264。
    2. 输出层每 token 的 FLOPs：2 × 543,499,264 = 1,086,998,528，即 1.087 GFLOPs/token。

    JS 只做整数乘法和加法，没有浮点误差；页面上显示的分组数字与这两组逐位一致。 1.05 保留两位小数，1.087 保留三位小数，表里保留完整整数。

    压缩率的账要和模型成本一起看。相比 Llama 2 tokenizer，Llama 3 在英语样本上的压缩率从 3.17 字符/token 提到 3.94 字符/token，绝对增加 0.77 字符/token， 相对提高 24.3%（(3.94 − 3.17) / 3.17）。 这意味着同样 8K 的上下文窗口（Llama 3 405B 的原始窗口是 8K，后扩到 128K；8K）能放更多字符，也意味着同样的训练 token 预算能读更多文本。 但 char/token 是语料相关的：英语、代码、中文的同一套词表会给出完全不同的数，不能把 3.94 当成所有语言的代表。

    05

    一条文本过六步，special token 从旁路进入

    原始文本、规范化、预切分、子词切分、查表、模板拼接；每一步都可能改变 token 数，special token 不经过 BPE。

    图里是六个步骤；下面按切分动作拆成五条——原始文本和进入模型不作为切分动作单列。

    1. 规范化：SentencePiece 的 Normalizer 把语义等价的 Unicode 字符归一化，文本、词表和模型文件放在一起，保证可复现（SentencePiece §2、SentencePiece §3.5）。tiktoken 的 encode_ordinary 直接对输入文本跑正则，没有单独的 Normalizer 调用（src/lib.rs:360-372）。
    2. 预切分：tiktoken 用 pat_str 把文本切成 piece；cl100k 的数字规则是 \p{N}{1,3}，也就是每 1–3 位数字切一块（openai_public.py:89）。这一步决定了 BPE 能看到哪些相邻关系，数字、标点和空白的边界都在这里定下。
    3. 子词切分：BPE 按 merge rank 从低到高合并；Unigram 用 Viterbi 取最高概率路径；WordPiece 用最长匹配。三者的输出都是 token 字符串序列。
    4. 查表：每个 token 在词表里查到整数 ID。tiktoken 的 max_token_value 取 mergeable ranks 和 special tokens 的最大值，n_vocab = max_token_value + 1（core.py:47-52、:373-375）。
    5. special token / 模板：special token 是固定字符串，匹配到后直接取 ID，不经过 BPE（src/lib.rs:390-431）。chat template 决定这些 token 放在哪里。

    special token 与 chat template：BPE 之外的第二个词表

    tiktoken 的 encode 先找允许的 special token，找到就把它的固定 ID 直接推进结果，再对两段普通文本做正则切分和 BPE （src/lib.rs:375-431）。所以 <|im_start|> 这类字符串不会被拆成 <、|、im…… 而是整体一个 ID。 encode_ordinary 则完全不碰 special token，只做普通文本编码（src/lib.rs:360-372）。

    Qwen3 的 chat template 是一个具体例子。Qwen3 Table 9 的非思考模式模板是： 

    <|im_start|>user
{query} /no_think<|im_end|>
<|im_start|>assistant
<think>
</think>
{response}<|im_end|>

    这里 <|im_start|> 和 <|im_end|> 是 special token， /no_think 和空的 <think> 块是模板文本；Qwen3 用它们在同一模型里切换思考和直答模式（Qwen3 §4.3、Qwen3 Table 9）。 模板本身不是 BPE 学出来的，它是推理侧的字符串拼接规则；模板改了，同一段对话的 token 序列也会变。

    反直觉

    词表更小，BLEU 反而更高

    SentencePiece 用 8k 共享词表，词表规模比 80k/80k 词模型小得多，却在 KFTT 两个方向都拿到更高 BLEU（SentencePiece Table 1）。 这不是「小词表一定更好」，而是同一份数据、同一个 NMT 配置下，子词把稀有词拆成可复用的片段，减少了 UNK 和稀疏词表带来的损失。 推断（由 SentencePiece Table 1 的 BLEU 与 SentencePiece §4.1 对预分词的讨论推出；原文没有给出这一机制的直接解释）。 换成英语到日语、或者换一个语料，预分词和词表大小的最优组合会变；表 5 的 20.86 就是预分词拖后腿的样本。

    07

    它不解决语义，也不保证跨语言覆盖，词表还改不动

    把失败模式写清楚：贪心合并、词表冻结、special token 注入、多语言证据缺口，以及原文自身的不一致。

    • 贪心且确定：BPE 每轮只取一个最高频对，产出确定的合并序列， 不能像 Unigram 那样给出多条带概率的切分。Kudo §3.1 把这列为 BPE 用于 subword regularization 的障碍； Unigram 的 EM + 采样就是为补这个缺口。
    • 词表冻结：预训练后词表不再变。新领域、新语言、新代码库里的符号只能拆成已有片段； 片段越碎，序列越长。Llama 3 用 28K 非英语 token 是训练前的主动干预（Llama 3 §3.2），不是训练后的补丁。 这也意味着换 tokenizer 不是改配置：输入 embedding 和输出层都要换形状，通常要重训。 推断（由 V×d 的 embedding 与 2×V×d 的输出层结构推出）。
    • 大词表有第二笔账：V 翻倍，输出层每 token 的乘加量也翻倍； 如果输出层与输入 embedding 不共享，embedding 侧同样翻倍。 稀有 token 在训练里出现的次数少，能不能学好是另一个问题；本节不给「大词表一定更好」的结论。
    • special token 是字符串旁路：它不经过 BPE，靠精确匹配取固定 ID （src/lib.rs:390-431）。用户文本里如果出现同名字符串，是否被当成 special token 取决于 allowed_special 的设置（src/lib.rs:378-398）；模板拼接也会改变 token 序列， 但模板不是模型学出来的。
    • 数字和代码会被切碎：cl100k 的数字正则 \p{N}{1,3} 把连续数字按 1–3 位切块 （openai_public.py:89）。这对算术、版本号、长 ID 不利：同一个数换一种写法，token 序列可能完全不同。 这是预切分规则的选择，不是 BPE 合并本身能修的。
    • 多语言证据不齐：BPE Table 1 是德语，SentencePiece Table 1 是日英，Llama 3 报告（Llama 3 §3.2）只列出英语样本上相对 Llama 2 tokenizer 的压缩率 3.17 → 3.94；非英语只描述方向性改善。 把英语的 3.94 当成所有语言的代表，是没有依据的外推。 这些来源的可比指标是 BLEU、压缩率与 UNK，不是统一的公平性分数。
    • 无损不等于无歧义：SentencePiece 保证 Decode(Encode(Normalize(x))) = Normalize(x) （SentencePiece §3.1），但归一化本身会改变文本；subword-nmt 的 @@ 表示无法编码连续空格（SentencePiece §3.1）。 需要逐字节还原原始输入时，byte-level BPE 直接在 byte 上工作；「先归一化再切分」会先改变文本，token 数也会变。

    什么时候别用子词 BPE：需要严格字符级对齐（比如逐字符标注、某些代码编辑任务），或者输入是固定字母表、 词表外字符极少时，字符级更直接；需要多语言覆盖又不想维护语言相关预分词时，byte-level BPE 或 SentencePiece 更合适。反过来，如果词表已经冻结、模型已经训好，换 tokenizer 不会「免费提升」——它会把 embedding 和输出层一起换掉。 推断（由 embedding 与输出层的形状推出）。
