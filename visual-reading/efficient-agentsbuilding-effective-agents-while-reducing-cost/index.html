Efficient Agents：智能体不是越复杂越好，是可以逐项标价的

LLM agent 的成本会随步数、搜索源和重试次数一起膨胀。论文把「成功一次要花多少钱」写成 cost-of-pass，在 GAIA 上每次只改一个组件，给 backbone、BoN、planning、tool、memory 逐项标价；最后以 1.81 pp 的准确率为代价，换掉 0.20 的 cost-of-pass。

Ningning Wang 等 · 2025 arXiv 2508.02694v1 ↗ 代码 ↗
TL;DR · 30 秒抓住核心

LLM agent 的成本不是线性的：前沿产品一次任务要几百次 API 调用，成本随步数、搜索次数、重试次数一起膨胀。论文把这个问题压成一个指标——成功一次要花多少钱。

cost-of-pass = 单次尝试成本 ÷ 成功率。它同时惩罚贵和不准：便宜但成功率低的模型不会自动赢，强但贵的模型也要付溢价。低 CoP 只代表「期望花费低」，不代表模型可用。

论文在 GAIA 上把 agent 拆成五个组件，每次只动一个：backbone、Best-of-N、planning、tool using、memory。结论不是「越简单越好」，而是每个组件都要按它对成本和准确率的实际贡献来选。

最终配置是 GPT-4.1 + 8 步 + Multi 搜索源 + Simple Memory：准确率 51.52%，CoP 0.55；OWL 是 53.33% / 0.75。准确率少 1.81 pp，CoP 低 0.20（相对 26.7%）。摘要里的 28.4% 与 CoP 的 26.7% 对不上；它恰好等于成本降幅——第 06 节对账。

01

智能体先撞上的不是能力墙，是账单

这一节只建立一件事：为什么「更复杂的 agent」在真实部署里越来越难成立。

论文开篇把矛盾说得很直接：DeepResearch、Manus 这类产品展示了很强的多步任务能力，但 suffer from exorbitant operating costs due to explosive LLM call overhead；有的系统一个任务要几百次 API 调用。

GAIA 把任务分成 L1–L3 三档。难度上去，成本不是缓慢上升，而是成倍地跳。下表只取 Table 1 里两个推理模型的 L1 / L3 列：

同一模型在 L3 的 CoP 是 L1 的 5–6 倍；与此同时，Claude 3.7 的准确率从 L1 的 73.58% 掉到 L3 的 42.31%。难任务既更贵、又更不准，两个方向一起把成本推高。

这时候只看准确率会误判。Table 1 里 Qwen3-30B-A3B 的 CoP 只有 0.13，是全表最低；但它的准确率只有 17.58%。按定义，CoP 0.13 只说明「在这套任务分布下，得到一次正确答案的期望花费是 $0.13」——它不是一个能直接拿去跑 GAIA 的通用 agent。推断（依据：Table 1 的 CoP 0.13 与 Acc 17.58% 同行；C = 0.023 美元时 0.023 / 0.1758 ≈ 0.131）。

问题定义

要优化的是「每次成功」的成本，不是「每次调用」的单价

单次调用便宜，可能只是模型在乱答；单次调用贵，也可能一次就答对。把两者压成一个比值，才能比较「花多少钱办成一件事」。这就是下一节两条现成路线都没有回答的问题。

02

两条现成路线，各把一半问题留给了账单

一条堆能力，一条压单价；两者都能拿出漂亮的单项数字，但都没回答「哪个模块值这个钱」。

路线 A

堆能力：更强的框架

OWL 在 GAIA 上 53.33%、CoP 0.75；Smolagents 同样 53.33%，CoP 却高达 5.82。两者准确率一样，CoP 差 7.76 倍——框架设计本身就能把成本拉开一个数量级。

盲区：它告诉你「谁更强」，不告诉你多出来的每一步、每一次工具调用值不值。

路线 B

压单价：更便宜的 backbone

Qwen3-30B-A3B 的 CoP 0.13、Qwen3-235B-A22B 0.22；Claude 3.7 Sonnet 准确率 61.82%，但 CoP 3.54，是 GPT-4.1 0.98 的 3.61 倍。

盲区：便宜和强之间没有免费的选择；只压单价会把任务成功率一起压下去。

03

把 agent 拆成五个能单独计价的旋钮

cost-of-pass 是标尺；固定其余组件、每次只动一个，是方法。切换标签，看每组选项的价目表。

v(m, p) = Cm(p) / Rm(p)
Cm(p) = nin(m, p) · cin(m) + nout(m, p) · cout(m)
§2.2 · 单次尝试成本除以成功率；成功率 R 为 0 时 CoP 记为 ∞（Table 1 的 Qwen3-30B-A3B L3 列即为此例）

论文固定一套默认配置（Table 8：GPT-4.1、12 步、plan interval 1、Simple 搜索源、10 次查询、BoN 1、Simple Memory），然后每次只改一个组件。这样每个组件的成本变化可以单独归因，而不是混在整体账单里。

04

成本怎么算：输入输出分开计价，成功率做分母

论文的账本口径，以及一个可以自己拨的 C / R 计算器。

成本不是简单地「token 数 × 一个单价」。论文按官方定价把输入和输出分开算：C = nin · cin + nout · cout。很多闭源模型输出 token 的单价明显高于输入，因而输出长度对账单的影响更大；价格锚定在 2025 年 5 月的官方文档。

把 C 再除以成功率 R，就得到 cost-of-pass。注意 C 是「一次尝试」的成本，R 是「一次尝试答对」的概率；两者相除才是「成功一次」的期望成本。R=0 时 CoP 无定义，论文记为 ∞。

cost-of-pass · C ÷ R
手算校验：两组参数，逐位对账成功率先除以 100，再作分母

口径：本页不涉及标准差；成功率按百分比输入，JS 中除以 100 后作为分母。计算器只演示 v = C / R 这一层，不复现原表把逐题结果聚合成 all / L1 / L2 / L3 的过程。

  • OWL：C = 0.398，R = 53.33% → 0.398 / 0.5333 = 0.7463 → 显示 0.746；Table 7 写 0.75。
  • Efficient Agents：C = 0.285，R = 51.52% → 0.285 / 0.5152 = 0.5532 → 显示 0.553；Table 7 写 0.55。
  • Qwen3-30B-A3B：0.023 / 0.1758 = 0.1308 → 显示 0.131；Table 1 写 0.13。
  • Smolagents：3.104 / 0.5333 = 5.8204 → 显示 5.820；Table 7 写 5.82。

计算器在同样参数下输出上述四个值，与手算逐位一致。原表的 CoP 是逐题计算后再汇总，和「总成本 ÷ 总准确率」不要求逐位相等；上面几组恰好落在原表舍入范围内。

成本口径只覆盖 API 调用：论文没有把自托管算力、向量数据库、工具 API 费用和工程重试成本计入。这些会在第 07 节作为边界展开。

Efficient Agents 的准确率比 OWL 低 1.81 pp（53.33 − 51.52），CoP 低 0.20（0.75 − 0.55），相对降幅 26.7%（0.20 / 0.75）。成本从 $0.398 降到 $0.285，绝对少 $0.113，相对降幅 28.4%（0.113 / 0.398）。准确率保留 96.6%（51.52 / 53.33）；论文取整写作 96.7%。

收益不是均匀分布的。L1 上 Efficient Agents 的 CoP 是 0.37，比 OWL 的 0.35 还高 0.02；L2 上是 0.54 对 0.80，低 0.26；L3 上是 1.71 对 2.10，低 0.39，相对降幅 18.6%。优势出现在 L2 和 L3——这正是简单配置最容易被复杂框架拖垮的地方。推断（依据：Table 7 的 L1 / L2 / L3 三列；L2 差 0.26、L3 差 0.39，L1 差 +0.02）。

三个反直觉的组件结论

Memory

简单记忆反而最好

Simple Memory 只保留观察与动作：56.36%、CoP 0.74。Summarized Memory 反而 51.52%、CoP 1.52；extra hybrid 是 54.55%、CoP 1.29。

比 w/o extra 基线高 3.03 pp，CoP 低 0.24（相对 -24.5%）。复杂摘要会引入额外 LLM 调用，还可能把关键历史压掉。

Best-of-N

采样 4 次，只多 0.61 pp

N 从 1 到 4：准确率 53.33%→53.94%（+0.61 pp），CoP 0.98→1.28（+0.30），token 243K→325K（+82K）。

PRM 是 GPT-4o，候选越多，评审本身也越贵；边际收益被采样成本吃掉。

Planning

8 步是甜点，12 步是空转

4→8 步：准确率 41.82%→52.73%（+10.91 pp），CoP 0.48→0.70（+0.22）。8→12 步：准确率只 +0.60 pp，CoP 却 +0.28。

超过 8 步后，更多步数没有带来新的有效信息，只是在重复搜索和重规划。

Tool using

多搜索源是少数「两头都赚」的改动

Simple → Multi：准确率 53.33%→59.39%（+6.06 pp），CoP 1.32→0.81（-0.51，相对 -38.6%）。更多来源既提高了命中率，也减少了无效重试，所以成本和准确率同向改善。

浏览器复杂度则不是：Browser-Complex 的 CoP 0.88 低于 Browser-Simple 的 1.59 和 Crawler 的 1.32，但准确率 49.09% 也最低。正文对「简化浏览器在效率上也更好」的说法，与 Table 4 的这组数字对不上——详见下面的对账。

原文里几处正文与表格对不上并列呈现，不替原文改数
  • 28.4% 的口径：摘要与引言写 28.4% improvement in cost-of-pass。按 Table 7，CoP 0.75→0.55 的相对降幅是 26.7%（0.20 / 0.75）；28.4% 恰好等于成本 $0.398→$0.285 的相对降幅（0.113 / 0.398）。摘要同时写成本降到 $0.228，而 Table 7 的 all 列是 $0.285，$0.228 是 l1 列。

07

这套配方不能直接搬去的四个地方

论文的结论有明确的 benchmark、价格和时间边界；越过这些边界，配置要重新测。

边界一

只有 GAIA 一个 benchmark

GAIA 主要是基于网络的问答、检索和多步推理。论文没有测代码生成、科学发现、长程软件工程。Simple Memory 在几百步的超长任务里是否仍然够用，论文没有数据；8 步上限也是按 GAIA 的难度分布选的。换任务分布，这些「甜点」都要重新扫。

边界二

成本模型是 2025 年 5 月的 API 价格

论文按官方文档的 per-token 价格计算，只覆盖 API 调用。自托管算力、向量数据库运维、工具 API、失败重试和工程人力都没有计入。价格变动或改用自托管，Table 1 的排序可能直接翻转。

边界三

组件是单变量测的，组合没有消融

Table 1–5 每次只改一个组件，其余保持默认。最终 Table 6 的 Multi + 5 在 Table 4 里没有单独一行；Table 7 只报告组合后的整体结果。组件之间的交互（例如多搜索源是否放大了 Simple Memory 的优势）没有拆开测。

边界四

模型与策略的覆盖范围有限

backbone 只测了 6 个（GPT-4.1、Claude 3.7、o1、Qwen3-235B/30B、QwQ-32B）；Table 1 未列出针对 agent 任务微调过的开源小模型。BoN 只测到 N=4，PRM 固定为 GPT-4o。memory 和 tool 的结论是在 GPT-4.1 上得到的；换 backbone 后，最优记忆和工具配置未必不变。

还有一个范围问题：论文称其在 GAIA 的 cost-of-pass 上达到新的最优；但同一篇的 Table 1 里，Qwen3-30B-A3B 的 0.13 比 Efficient Agents 的 0.55 更低，代价是准确率只有 17.58%。这个「最优」是在高准确率 agent 框架的语境里说的，论文没有把它写成跨所有模型的绝对最优。

一句话总结：这套方法最值得带走的不是「GPT-4.1 + 8 步 + Simple Memory」这串固定配置，而是「固定其余变量，给每个组件单独算 cost-of-pass」的实验设计。换 benchmark、换价格、换模型，配置要重扫，方法可以复用。
