MCPVerse：把 552 个真实工具一次性塞给模型，多数人掉分，强 Agent 反而涨

现有工具调用基准要么用模拟工具、只校验「选对没选对」，要么靠检索器只挂几十个工具。 论文用 65 个 MCP 服务器、552 个真实可执行工具拼出约 147k token 的工具 schema，再用三种挂载模式控制工具规模。 结果：12 个模型里只有 3 个在工具更多时反而更准，其余全部下滑——尤其那些被 API 工具数上限逼着改用「提示词式函数调用」的模型。

Fei Lei, Yibo Yang, Wenxiu Sun, Dahua Lin · SenseTime Research arXiv 2508.16260 ↗ 代码 ↗
TL;DR · 30 秒抓住核心

工具调用评测长期卡在「假工具」和「小工具箱」两个问题上：模拟计算器、模拟购物车只校验函数名和参数；就算工具库很大，也得靠检索器缩水到几十个。两者都测不出真实世界里「在几百个真 API 里找路」的能力。

论文的做法很直接：把 65 个真实 MCP 服务器、552 个工具全部挂上，schema 合计超过 147k token，并且刻意不放检索器；三种模式（Oracle 只给最少工具、Standard 给 32 个 MCP、Max-Scale 全给）作为变量控制。

评分只看最终结果：文本答案由 LLM 裁判判定语义一致，文件改动由脚本校验状态；时效性问题用脚本实时抓 ground truth。

最反直觉的发现：工具变多时 9 个模型下降，但 Claude-4-Sonnet、Qwen3-235B-2507、GLM-4.5 在 Standard 模式超过 Oracle——它们会把被卡住的路径换成工具箱里的另一条路。

01

工具调用评测失真在两个地方：工具是假的，动作空间是小的

读完这节应明白：为什么「函数调用准确率」不等于「Agent 真的会干活」。

论文在引言里把现有基准的短板归为两类。

问题一

人工合成工具让「背模式」就能过关

很多基准模拟计算器、简化版天气服务、假购物车，数据格式和交互方式跟生产系统差得很远。模型只要识别出表面套路就能拿分，而不是真的学会了规划与协调。

另一类虽然声称接入真实 API，但因为线上集成麻烦，并不真正执行，只校验「选中的工具名和参数对不对」，而不是交互的实际结果。

问题二

上下文限制逼出「检索器 + 几十个工具」

就算列出了大量 API，受上下文长度所限，设计者一次只能挂一小部分，常常靠检索模块每次挑几十个相关工具。

这保证了 prompt 不爆，但也绕开了「在庞大复杂的解空间里导航」这个能力本身。

这里的核心区分是：「能在给定 5 个工具里挑对的」和「能在 552 个工具里自己找到路」是两种能力。前者可以被检索器、迷你工具箱保护住，后者只有在真实规模和真实失败（认证错误、返回格式异常、路由被堵）下才会暴露。MCPVerse 想测的是后者。

MCP（Model Context Protocol）在 2024 年作为开放标准由 Anthropic 提出，统一了工具接入方式，工业界快速出现大量 MCP 服务器——这给了「挂几百个真实工具」一个工程前提。

03

三层设计：真实工具池、人工任务、结果导向评分

MCPVerse 没有新式子，它的「方法」是三个互相咬合的设计决定。

第一层

工具池：65 MCP / 552 工具

从 Smithery、mcp.so、ModelScope 等平台收集，按三条标准筛选：鼓励长期稳定的服务；尽量少依赖 API key；可自动评估（Gmail、Notion 这类难以自动判定的，可以只放进池里当干扰项）。

论文同时提醒：工具数会随时间波动，提供方可增删工具。

第二层

任务：250 个，2 类型 × 3 难度

类型为信息检索（地理、金融、学术、热点新闻）与系统操作（命令行、数据库、文件）；难度 L1 = 1–2 步单工具，L2 ≈ 5 步，L3 > 5 步、需多工具协作。

标注者（本科及以上）须保证：存在有效解、答案客观无歧义、贴合真实场景、不调工具解不出来。

第三层

评分：只看结果，分两种对齐

不罚「偏离标准路径」。文本答案由 LLM 裁判判断语义等价；文件修改等状态变化由专用脚本校验（附录 D 给出 Q101 的脚本示例）。

评分函数：一条二值判定

Ê = G(Q, D | T)     E(Ê, O) ∈ {0, 1}
任务 Q、候选数据文件 D、可用工具池 T；Agent G 产出结果 Ê 或文件状态改动；与 ground truth O 一致记 1

E(·) 的两种实例化：

  • 文本类：把问题、参考答案、模型输出一起交给裁判模型，问「语义是否一致」，输出 {"score": 1} 或 {"score": 0}（附录 D 的 prompt 原文）。
  • 状态类：直接跑脚本检查环境。比如 Q101 要求目录里有 alpha.txt（内容 Hello Alpha）和 beta.txt（内容 Hello Beta），任何一项不符返回 False。
容易被忽略的细节

裁判模型是 QwQ-32B，不是 GPT-4o

论文主实验用开源 QwQ-32B 做判定，附录 F 用 GPT-4o 复判：具体分数有差异（例如 Standard 模式 Claude-4-Sonnet 为 62.36 vs 61.26），但12 个模型的名次完全一致。这条是判断分数可信度的关键证据。

评测管线刻意从简

论文没有引入 ReAct、RolePlaying 之类复杂框架，理由是这些框架依赖大量 prompt 工程，会遮蔽模型自身能力。管线就是一个朴素的 agentic loop（见第 05 节），目标是测模型本身，而不是测某个框架。

04

三种挂载模式是整篇论文的自变量

同一个任务、同一套评分，唯一变化的是工具箱有多大——这就是「广阔动作空间是福是祸」的实验设计。

Oracle Mode

只挂最少工具

由标注者核实过的、解该题所需的最小工具集合。上下文长度随题而异。相当于传统评测的「喂到嘴边」。

Standard Mode

32 MCP / 220+ 工具 / ≈44k token

所有题的 Oracle 最小集取并集，目标是适配主流模型 64k 上下文，留约 20k 给提问与回答。

Max-Scale Mode

全部 65 MCP / 550+ 工具 / ≈140k token

在 Standard 基础上加入全部 MCP。论文报告只有 Claude-4-Sonnet 与 Gemini-2.5-Pro 能完整跑完——但 Table 2 显示 Gemini-2.5-Pro 在 Max-Scale 用的是提示词式函数调用（带 ∗），而且它的 31.4 恰好等于 GPT-4o 在 Max-Scale 列中残留的那个数字，疑似排版错位，见第 06 节脚注。

还有两个现实约束也必须写进设计：API 工具数上限（GPT-4o / GPT-5 为 128，Gemini 为 512）和上下文长度（DeepSeek-V3 仅 64k）。工具数超限但上下文够的模型，被迫改用「提示词式函数调用」：把整份工具 schema 塞进 system prompt，让模型以 JSON 列表形式输出调用（附录 E 给出模板，并特别叮嘱「不要伪造函数返回」）。

05

评测流程：从 MCP 池到二值得分

论文 Figure 1 的结构，加上附录 B 的循环伪代码；记住「先接工具、再按模式挂载、最后裁判」这三步即可。

附录 B 给出的管线核心就是一个 while 循环，没有额外规划模块：

toolset = [connect_to(mcp).get_tools() for mcp in mcp_list]
history = [task]
while True:
    resp = LLM(history, toolset);  history.append(resp)
    if not resp.tool_calls: return
    for call in resp.tool_calls: history.append(call_tool(call))
附录 B 评测管线的等价伪代码；真实代码中逐 MCP 连接后再进入循环

这个设计意味着：MCPVerse 测的是模型在「工具一旦挂上去、上下文一旦满了」时的自主性，而不是某个 Agent 框架的工程技巧。

检索模式补充实验

论文同样检验了「传统做法」：用 text-embedding-3-large 对模型自述的服务器需求做嵌入，余弦相似度取 top-5 服务器挂载。结果（Table 4）在四个模型上全部低于 Oracle 与 Standard——检索器在真实工具池上不够精确，反而比直接给全部工具更差。

反直觉发现：三条向上，九条向下

从 Oracle 到 Standard，Claude-4-Sonnet（+4.1）、GLM-4.5（+4.1）、Qwen3-235B-2507（+8.4）上升；其余全部下降。论文按下降幅度把后九者分成三类：

  • 断崖式下降与 API 工具数上限有关：GPT-4o、GPT-5、Kimi-K2-0711 都卡在 128 个工具上限，Standard 模式只能用提示词式函数调用。Table 3 直接证明这种替换本身代价极大：Claude-4-Sonnet 在 Oracle 下从 62.28 掉到 35.55，而且它的幻觉率超过 70%（模型会在明确禁止的情况下虚构工具返回）。
  • 温和下降反映上下文负担：剩余模型（如 Gemini-2.5-Pro −3.4、DeepSeek-V3.1-Terminus −4.5）在更大的 schema 下要更难地选工具。
  • Max-Scale 继续下降：能评的三个模型从 Standard 到 Max-Scale 全部下滑，Claude-4-Sonnet 也从 62.4 → 44.2。

为什么强 Agent 会涨：Figure 4 的案例

Oracle 路径Standard 路径被卡住的接口

同一个任务，Claude-4-Sonnet 在 Oracle 模式按标注路线调用 dataviewer 的 validate 与 filter，但把 auth_token 从布尔值错填成字符串，触发鉴权错误后放弃。

在 Standard 模式，它遇到同样的初始失败后，转而调用工具池里的 fetch 绕过被堵的路，完成任务。论文称之为 emergent solution path / “hacking” behavior：模型不是学会了某条标准路线，而是学会了在被堵时换路。

想想看
当工具很少时，模型没有「备胎」可用，一次失败就是整体失败；工具多时，备胎也是干扰。MCPVerse 能区分两种模型：被干扰拖垮的，和被备胎救下来的。
07

什么时候 MCPVerse 的分数不可信

论文自己的数据与设计里，至少能读出五条限制。

边界一

实时服务会漂移，可复现性天然打折

552 个工具是真实在线 MCP，提供方可随时增删工具（论文自己说明「这个数会波动」）；线上答案也会改变。时效性问题虽用脚本抓实时 ground truth，但依赖外部网络的服务一旦下线，任务就不可复现。

边界二

「大掉分」可能是评测方式而非模型能力的问题

GPT-4o、GPT-5、Kimi-K2-0711 的 Standard 分数是通过 提示词式函数调用得来的。Table 3 显示：在同一个 Claude-4-Sonnet 上，同一套 prompt 就能让分数砍半。因此它们的断崖式下降与模型能力有多少因果关系，论文没有做完整的解耦；作者自己措辞是 “likely accounts for”。

边界三

评分依赖 LLM 裁判

文本类答案由 QwQ-32B 判语义一致性。附录 F 用 GPT-4o 复判，12 个模型的名次完全一致，说明排名方向稳定；但分数并非「客观真值」，裁判本身也没有逐题人工核验。

边界四

管线刻意简化，不能代表工程化 Agent

论文不跑 ReAct 等框架，理由是测「模型本身」。这意味着 MCPVerse 分数衡量的是裸模型 + 简单循环，不反映带规划、记忆、多 Agent 组装的真实产品表现。

边界五

工具数会变、Max-Scale 覆盖模型极少

Max-Scale 只有 3 个模型有可读分数（其中 Gemini 为 ∗），其余全是「—」。Max-Scale 的排名与结论证据量远小于 Standard。

一句话：MCPVerse 最有说服力的不是绝对分，而是「Oracle → Standard」的增减号——它在多大工具集里还能稳定选择与换路，这个方向性结论比任何单个百分数都更稳。
