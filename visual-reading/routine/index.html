Routine：把专家写好的流程塞进提示词，小模型也能稳跑多步工具调用

通用大模型在企业里最常犯的错不是不会调工具，而是挑错工具：面对 25 个功能相近的工具和一条有依赖关系的多步任务，它既不懂公司流程，也没人给它一张明确的路线图。 Routine 把任务写成「第几步、做什么、用哪个工具」的结构化脚本，交给一个专职执行的小模型；流程知识还可以被蒸馏进权重。

TL;DR · 30 秒抓住核心

企业多步任务的瓶颈是工具选择：无 Routine 时所有基线模型整体准确率都不到 50%，工具选择错误占全部错误的 85% 以上。规划能力不够的模型，塞进一张明确路线图就能补齐大半。

Routine 就是那张路线图：每步给出编号、名称、描述、输入输出和唯一一个工具名，分支写成「Branch X-n Step i」。规划与执行解耦——高能力模型把专家草稿整理成 Routine，轻量执行模型只管「调哪个工具、传什么参数」。

三种增强互相叠加：提示词里的 Routine 补外部流程知识，通用 Routine 跟随微调 练服从格式的肌肉记忆，场景蒸馏 把流程知识烘焙进权重。Qwen3-14B 三步走下来 32.6 → 83.3 → 92.7 → 98.0（Routine w/o Branch），在蒸馏测试集上到 95.5%，逼近 GPT-4o 的 96.3%。

01

企业里的多步任务，卡的往往不是推理，而是工具选择

先分清「不会规划」和「不会选工具」——论文的数据说，后者才是主因。

实验场景是一家员工超过 8,000 人的大企业里真实部署的 HR Agent：员工向它查询人员与部门信息。场景拆成 7 个子场景、7 条人工标注的 Routine，每条 4–7 个工具调用步骤，每步 1–3 个输入参数；参数之间有依赖，所以顺序不能乱。可用工具来自一个 MCP server，共 25 个功能各异的工具，覆盖数据查询、权限校验、模型生成等。

不提供任何计划时，模型必须自己从这 25 个工具里选、自己排顺序、自己填参数。论文 Table 2 的结果是：8 个基线模型（4 个闭源、4 个开源）整体准确率没有一个超过 50%。拆开看错误构成，结构错误很少（GPT-4o 的结构准确率是 100），参数准确率也有 97.3，唯独工具选择只有 42.2。

核心判断

85% 以上的错误出在「选哪个工具」

论文明确写道：工具选择错误占全部错误的 85% 以上。也就是说，模型知道怎么输出合法 JSON、知道参数大概该填什么，但它在 25 个工具里挑不出一条正确的调用链——这恰恰是领域流程知识，不是通用推理。

另一层难点是流程本身：权限校验步骤不能漏、模型生成步骤要走专用工具、分支要看中间结果再决定。通用模型没有这些 SOP，规划自然写得七零八落。

于是问题可以写得很具体：能不能把流程知识从规划这一步剥出来，变成一份执行模型必须照做的结构化脚本？ 这正是 Routine 要回答的，也是前面几类做法卡住的地方。

02

前三类方案各差一口气：太自由、太中间、太贵

论文 Related Work 把 2023–2025 年的智能体实践归纳成这样几路，Routine 瞄准的是它们的交汇处。

第一波

完全自主

AutoGPT 的任务列表、BabyAGI 的自动目标生成、AutoGen 的工具调用 DAG。证明了 LLM 能自主拆解与编排，但暴露出上下文管理低效、执行流程碎片化、步骤爆炸和循环调用导致的成本波动。

第二波

plan-then-act

先出高层计划、再逐子任务选工具，例如 Manus 的 Planner / Executor / Verifier 三段式。保留了灵活性也约束了规划，但计划仍以非结构化或半结构化自然语言呈现，难以校验、调试和复用。

替代路

低代码平台

流程天然稳定，但严重依赖人工搭建，工作流开发效率低，难以扩展到成百上千的业务流程；而且工具与模型之间的边界是写死的。

还有一路是「模型侧」的努力：IFEval、ComplexBench、IOPO / TRACE、GuideBench 都在压测指令跟随。论文引用 ComplexBench 的发现——GPT-4 在链式结构与深层嵌套选择上准确率明显下降，结构感知和分布外泛化是短板。单纯加大模型或换更强的 prompt 工程，不能解决「它不知道公司第 3 步要调权限工具」这件事。

Routine 这个名字并非凭空而来：它最早出现在 OpenAI Cookbook，用来把指令拆成更小、可管理的任务以降低幻觉。论文在此基础上补齐了组件（输入输出、工具名、分支房号），并把重心放在「执行模型能不能稳定照做」上——它把 Routine 当作 LLM 规划与执行引擎之间的中间表示。

03

六个组件、一套分支编号：让执行模型知道自己「现在在哪一步」

Routine 的全部「方法」就是一份格式约定；它的价值在于把这几个字段位置固定死，让每一步都能被追踪与校验。

Table 1 列出一个完整 Routine 的组件，带 * 的是可选项：

组件含义必填
Step Number该步骤在主流程中的序号是
Step Name步骤目的的精简概括是
Step Description详细指令、执行条件与目标是
Input Description执行本步所需参数说明可选 *
Output Description成功执行后产生的输出参数可选 *
Step Tool本步对应的函数工具，每步只调一个可选 *

分支不是另起一张表，而是编号

相似场景的 Routine 常有重叠步骤，只在某一段分叉。论文的做法是在主流程里开分支步骤，用 Branch X-n Step i 命名——第 X 个主步骤的第 n 条分支里的第 i 步。执行模型据此判断自己在哪条分支、走到第几步；工作流在某步结束后要以「终止」描述出来。修改流程时，开发者可以快速插入、删除或编辑某一步。

Step X. <条件检查>:   Branch X-1 Step 1. <名称> — 若 <条件>，用 <工具> 执行 <描述>
  Branch X-2 Step 1. <名称> — 若 <另一条件>，用 <工具> 执行 <描述>
Step Y. <名称> — <描述>，用 <工具>   Step Z. <名称> — <描述>，用 <工具>，终止工作流
论文 §3.1.1 给出的分支写法；Appendix B.1 是一条 4 步的自然语言 Routine 实例（获取公告 → 下载手册 → 读 PDF → 比对文本）

自然语言 Routine 只是外显形式。Appendix A.1 的生成 prompt 让规划模型先输出 JSON 列表（step / name / description / tool / type，type 取 node、branch、branchnode 或 finish），再转写成人可读的执行步骤。同一条 Routine 有两种形态，前者便于机器校验与入库，后者交给人审和模型阅读。

另一处结构性设计是「谁来收尾」：最后一步不让执行模型自己用自然语言回答，而是调用一个专用的汇总工具，该工具配有场景专属模板。这样汇总 prompt 与工具调用 prompt 互不干扰，执行模型始终只做一件事。

04

两条训练管线叠加：练「照做」，再把流程烘焙进权重

Routine 是外部提示；要让小模型即使没有提示也稳，还需要数据合成与蒸馏。

管线一：通用 Routine 跟随（练格式）

底料是 BUTTON 开源数据集：8,000 条单轮多步工具调用实例，覆盖多种常见任务。用 GPT-4o 按专门模板为每条实例生成结构化 Routine，再按标准执行 prompt 重新拼系统提示，随后做三步过滤：

  • 文本校验：丢弃空回复或输出异常条目；
  • 删掉自然语言总结步：汇总交给专用工具，训练样本只保留用户查询、工具调用和观察；
  • 长度与结构过滤：超过 8 个工具调用步骤的丢弃，含嵌套列表、字典等复杂结构的也丢弃。

过滤后留下 4,209 条。这一步只教模型「读懂 Routine 语法并照做」，不教任何 HR 场景知识。

管线二：场景蒸馏（把流程写进权重）

对 10 个无分支子场景各设计 5–6 个用户查询模板，用部门与员工信息填空，每个子场景约 50–60 条；清洗后得到 537 条用户查询，再用 LLM 生成语义等价的改写做数据增强。然后由 GPT-4o + Routine 作教师，对每一条蒸馏出完整的多步调用记录：每条 4–7 步，共 3,108 条标注的工具调用指令。另蒸馏 200 条用户查询（共 1,148 次工具调用）作为测试集。

教师执行时，Routine 在系统提示的 <routines> 标签里；工具返回的长结果不进上下文，只留一个键，由 <variables> 记账（见 05 节的变量内存）。学生模型因此看到的每条轨迹都是「专家流程 + 强模型执行」的干净样本。

评测：BFCL 的 AST 三级判定

所有模型用 Berkeley Function-Calling Leaderboard（BFCL）的 FC 模式，按 AST 层级判定错误，再把 1,148 条样本拆成逐步的独立测试样本（每条带截至当前步的历史与当时的最新系统提示），并打乱工具列表顺序以排除位置偏置。三种配置对应 Routine 的有无与是否带分支：

No Routine

只给用户查询，模型自己规划。基线。

Routine w/o Branch

给一条线性自然语言 Routine，考验指令跟随。

Routine w/ Branch

同一 Routine 但含条件分支，考验按中间结果选路。

评测用的 Routine 只含编号、名称、描述、工具四件，不含输入输出描述；组件影响见 06 节 Table 3。整体准确率 = 所有步骤结构、工具、参数全部正确的样本比例，是最严的口径。

这个模拟简化了什么？点开看与真实实验的差异

示例流程取自论文 Appendix B 的 4 步自然语言 Routine（获取公告、下载手册、读 PDF、比对文本），页面多加了一个「生成公告摘要」步骤来演示变量内存的键。真实场景每条 Routine 4–7 步。

「上下文账单」是估算，不是论文数字：基线 3,000 token（角色规则 + 25 个工具描述 + 输出模板），Routine 每步约 9 token，变量键约 8 token，PDF 全文按 20k token、模型自写汇总按 1.2k token 计。论文明说减少 token 消耗，但没有报告这条流程的具体数字，所以页面只比较同一帧下三种模式的相对差值，并随当前步变化。

「丢掉工具名」几乎不省长度，但 Table 3 里它是单点掉分最大的改动（GPT-3.5 52.7 → 42.8，Qwen3-14B 83.3 → 71.9）：去掉的是信息，不是 token。GPT-4o 是唯一不受影响的模型（96.3 → 96.7）。

真实系统里变量内存由 Memory Module 在工具调用前后自动读写，执行模型只看到 memory_xxx 这样的键；模拟里把这一步显式画出来，方便看懂「长文本从哪里离开上下文」。

图里还有一条容易被忽略的线：Procedure Memory 的检索精度是整条链路的前提。论文 Table 5 显示，哪怕只多放 1 条干扰 Routine，GPT-4o 的准确率就从 96.3 掉到 76.6，Qwen3-14B 从 83.3 掉到 63.2——这一点放到 07 节展开。

07

Routine 买的是确定性，账单写在「谁写流程」和「流程会变」上

适用边界几乎全部由论文自己的消融和局限节给出，不靠推演。

边界一

流程仍要靠人起草，新工具一上就泛化不了

论文 §6 明确承认：目前的规划模型主要依赖领域专家提供的草稿生成 Routine，执行模型主要靠指令微调与蒸馏适配。企业一旦引入新工具或流程变更，系统对新情况的泛化能力受限，自主性与适应性仍有提升空间。蒸馏带来的「无 Routine 也行」只对训过的场景成立。

边界二

程序内存的检索精度决定上限

Table 5 里，穷模型加一条干扰几乎不掉，强模型却从 96.3 掉到 76.6。原因是强模型本来能利用单一 Routine 的每一处细节，一旦上下文中出现另一条相似流程，它会被带偏。这对 Procedure Memory 提出了很高的精度要求，而论文并没有公开相似度检索的实现细节与召回表现。

边界三

分支不是白送的

对 GPT-4o、Claude-3.7、GPT-4-Turbo 这类强模型，带分支普遍低于线性（96.3 vs 97.0，99.3 vs 98.0，99.0 vs 98.3）。论文的结论是：分支逻辑应该建立在模型已有稳定工具调用能力的基础上，否则「先判断、再选路」会额外引入误差。7 条 Routine 中有 3 条带分支，拆开后可表示成 10 条无分支流程。

边界四

一个场景、一种语言、一个教师

全部实验都在一个企业 HR 场景、中文、GPT-4o 作教师。535 条蒸馏样本覆盖 10 个无分支子场景，训练只用 4 张 A10（24GB），LoRA 选择 epoch 3 按验证集定。换成流程更开放、工具接口更不规整的领域，或者换教师模型，论文没有给出可以直接外推的数字。

什么时候别用 Routine

  • 任务开放、每次路径都不同：没有可复用的流程可抽，Routine 就退化成一张写死的路线图，反而限制探索。
  • 流程频繁变动：每变一次就要重写 Routine、甚至重新蒸馏，维护成本会盖过收益。
  • Retrieval 做不准：Routine 库大到必须多路召回时，先解决「只给一条」的检索精度，再谈 Routine 本身（Table 5）。

论文自己给出的下一步是两条：把 RL 框架接进工作流（含数据蒸馏与奖励建模），让规划模型学会生成 Routine、执行模型学会调工具，用指令微调冷启动再 RL 提升泛化；以及以 Routine 为中心的多智能体框架，由上层智能体协调多个专职智能体，用结构化 Routine 流与集中式交互协议降低每条计划的复杂度。一句话：Routine 解决的是「已知流程的稳定执行」，不是「未知流程的自动发现」。
