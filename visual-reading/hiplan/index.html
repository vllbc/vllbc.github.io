HiPlan：给长任务一张里程碑地图，再在每一步递一张修正便签

长时程任务里，高层规划常常「计划定了就不改」，步进式方法又「只看下一步」。HiPlan 从专家演示里抽出里程碑这一中等粒度经验：任务级检索生成全局里程碑指南，里程碑级检索生成每步提示；提示里明确写出当前状态、与里程碑的差距、以及必要时的动作修正。

Ziyue Li, Yuan Chang, Gaihong Yu, Xiaoqiu Le · 中国科学院文献情报中心 / 中国科学院大学 arXiv 2508.19076v1 ↗ 博客笔记 ↗
TL;DR · 30 秒抓住核心

长任务的两难不是「会不会拆子目标」，而是拆完之后的执行：全局指南给方向，却不知道下一步具体做什么；步进式提示知道下一步，却容易在长序列里迷路。

HiPlan 把「经验」切成里程碑，而不是整条轨迹或单个动作。离线用 GPT-4o 把 577 条专家演示切成 3,330 条「里程碑描述 + 动作片段」；在线先检索相似任务生成里程碑指南，再在每一步检索相似里程碑生成步进提示。

提示固定包含三块：State Context、Milestone Gap、Action Correction。前者防止上下文丢失，中者把当前状态和里程碑目标对齐，后者只在动作偏离时出现。

代价是：需要专家演示；里程碑切分依赖 GPT-4o；论文没有报告 token、延迟或库规模扩大后的表现。

01

长任务不是「不会规划」，而是「全局」和「局部」总有一头掉线

读完这节你应该知道：为什么把任务拆成子目标还不够，为什么每一步都看观察也不够。

论文把问题放在部分可观测的 POMDP 里：状态 S、动作 A、观测 O、转移 T；agent 要在看不到完整环境的情况下，按自然语言指令 τ 生成一串动作。ALFWorld 的动作序列可以超过 50 步；WebShop 有 200 条测试指令、超过 118 万件商品。步数一长，局部决策的误差会累积，全局目标也容易被冲淡。

High-level Planning

先拆子目标，再按子目标执行

优点是方向清楚，全局目标不容易丢。问题是计划一旦生成就很少改：遇到执行错误或环境变化时，缺少局部修正。

论文还指出，这类方法常用完整历史轨迹做示范，任务细节太多，反而降低泛化。

Step-wise Methods

每一步看当前观察再决定

优点是反应快，能根据实时观测调整动作。问题是容易只看脚下：长序列里会重复探索、陷入局部最优。

而且它很难复用当前观察之外的历史经验，换一个任务就要重新摸索。

核心矛盾

全局指南要稳定，局部执行要灵活

两者如果分开做，就会一边僵硬、一边短视。HiPlan 的目标不是二选一，而是让两层在同一套经验上联动：用里程碑库同时支撑全局路线和局部提示。

“Top-Left: High-level planning with global subgoals lacking flexibility; Top-Right: Step-wise methods with local adaptability but limited global guidance; Bottom: HiPlan’s hierarchical approach combining milestone guidance and step-wise hints for adaptive and robust planning.”

图注把两种失败模式并列；HiPlan 的位置是底部，把里程碑指南和步进提示叠在一起。本页未转录原图，只引用图注。

02

两条路各自走到极端，检索增强也没把两层接起来

看清三类基线各自缺什么，才能理解 HiPlan 为什么要做「任务级 + 里程碑级」两次检索。

High-level

有全局，缺局部

代表作包括 Decomposed Prompting、Plan-and-Solve 等。先把任务拆成子目标，再按子目标执行。

盲区：子目标序列通常是固定的；执行中遇到意外，缺少逐动作的修正信号。

Step-wise

有局部，缺全局

ReAct 是代表：推理和动作交错，每一步根据当前观察决定下一步。

盲区：没有显式的全局结构，长序列里容易绕路；经验复用通常只来自当前观察或短期记忆。

检索增强：TRAD 把「经验」仍然停在低层动作

TRAD 按 thought-level 相似度检索轨迹片段，再对齐决策。它比纯 ReAct 多了经验复用，但检索单位仍然是动作级/轨迹片段级，没有把全局里程碑结构显式建模。论文指出，低层动作示范在 WebShop 里可能引入显著噪声。

反直觉

TRAD 在 ALFWorld 是强基线，在 WebShop Mixtral 却塌到 0.04

Table 2 的 Mixtral 块：TRAD 成功率 0.04，低于 REACT 0.19 和 REACT+Reflexion 0.24；Table 1 的 Mixtral ALFWorld 块：TRAD 的 All 是 0.78，是三个基线里最高的。

论文的解释是：WebShop 里直接提供低层动作示范，容易引入显著噪声，模型可能在 40 步内买不到目标商品；TRAD 对任务形态敏感。

HiPlan 的切口因此不是「再做一个更强的检索器」，而是换检索单位：把动作抬到里程碑，同时保留任务级和里程碑级两层。下一节拆开这两个阶段。

03

离线把轨迹切成里程碑，在线做两次检索

这一节拆开 HiPlan 的两个阶段：库怎么建、全局指南和局部提示怎么生成。

离线：专家轨迹 → 里程碑库

给定成功演示集合 D = {(τ(i), ξ(i))}，每条轨迹 ξ(i) 被切成 K(i) 个连续片段 ζk；LLM 为每个片段生成里程碑描述 mk。任务和里程碑都用 all-mpnet-base-v2 编码；库中存四元组：

(vtask(i), vmilestone(i,k), mk(i), ζk(i))
§4.2 · 里程碑库的存储单元；相似度用归一化向量的点积。§4.2 前一行还写过含 τ 的五元组，最终库定义用四元组，本页按最终定义。

切分和描述由 GPT-4o-2024-08-06 完成；库的统计见 §04 的 Table 3：577 条演示、3,330 条库记录，平均每个里程碑 1.70 个动作。这个长度很关键——它比单步动作长，比整条轨迹短。

全局指导：任务级检索 → 里程碑指南

测试任务 τ 先编码为 vτ，检索 top-M=2 个相似任务；检索分数是归一化点积，随后还按轨迹长度重排，优先更短、更通用的示范。LLM 以 τ 和检索到的 (τ(j), ξ(j), Gτ(j)) 为输入，生成里程碑指南：

Gτ = LLM(τ, {(τ(j), ξ(j), Gτ(j))j=1M})
Eq. 2 · M=2；检索用归一化点积（Eq. 7），再按轨迹长度重排（§C.1）

局部指导：里程碑级检索 → 步进提示

执行到第 t 步，当前里程碑是 mψ(t)；用它检索 top-P=2 个相似里程碑及其轨迹片段。检索时做轨迹级去重：两条命中不能来自同一条专家轨迹；每个片段还多取一个动作，作为前向上下文。LLM 结合当前里程碑、完整动作-观测历史、检索片段，生成步进提示：

ht = LLM(mk, {(os, as)s=1t}, {(ml*, ζl*)l=1P})
Eq. 4 · P=2；去重与「多取一个动作」见 §C.2
ht = {State Context, Milestone Gap, Action Correction}
§4.3 · 三块内容固定；Action Correction 只在检测到偏离时出现

最后，策略把两层指导合起来：

at = π(τ, {(os, as)s=1t}, mk, ht)
Eq. 5 · π 由同一个底层 LLM 执行，不是单独训练的策略网络（§5.1）

粒度选择器：一次检索到底该拿回多少动作？

论文的选择是「里程碑」：比单步动作长，比整条轨迹短。Table 3 给出平均每个里程碑 1.70 个动作（ALFWorld 1.78、WebShop 1.11），平均每条轨迹 5.77 个里程碑。下面把三个粒度换算成「检索 R 条经验时 LLM 看到的动作条数」。

没覆盖：检索相似度计算、任务级长度重排、里程碑级轨迹去重、每个片段多取一个动作、LLM 生成指南/提示的过程、任务成功率。R 不是论文的实验变量；论文固定 M=2（任务级）和 P=2（里程碑级）。

因此这个模拟只能说明「粒度越粗，单条经验带入的动作越多」这一算术关系，不能用来推断成功率或消融幅度。

手算校验：两组参数，逐位对上ALFWorld R=2；WebShop R=3

第 1 组：ALFWorld，R=2。Table 3 给的平均值是 5.89 个里程碑/轨迹、1.78 个动作/里程碑。按 Table 3 的平均值相乘，每条轨迹约 5.89 × 1.78 = 10.48 个动作。

  • 动作级：2 × 1 = 2.00
  • 里程碑级：2 × 1.78 = 3.56
  • 任务级：2 × (5.89 × 1.78) = 2 × 10.4842 = 20.9684 → 20.97

第 2 组：WebShop，R=3。Table 3 给的平均值是 5.00 个里程碑/轨迹、1.11 个动作/里程碑。按 Table 3 的平均值相乘，每条轨迹约 5.00 × 1.11 = 5.55 个动作。

  • 动作级：3 × 1 = 3.00
  • 里程碑级：3 × 1.11 = 3.33
  • 任务级：3 × (5.00 × 1.11) = 3 × 5.55 = 16.65

页面 JS 用 toFixed(2) 输出同样两组值。这里的「动作级 / 任务级」不是论文的实验设置，而是本页为了比较粒度做的换算；论文实际检索的是任务级 top-2 和里程碑级 top-2。

04

没有训练，成本主要花在离线建库和每步的 LLM 调用

这一节回答工程问题：库有多大、检索多深、每步要做什么、论文没有报告什么。

训练方式

不更新参数，也不训练策略网络

HiPlan 没有参数训练或微调。离线阶段只建库；执行阶段的 π 是同一个底层 LLM 的提示式决策。论文把里程碑指南生成、步进提示构造、最终动作预测都交给同一个模型。

执行时的固定设置

  • 检索深度：任务级 M=2；里程碑级 P=2。论文在 §C.2 说这两个值来自经验观察，与 in-context learning 常用的 2–3 个示例做法相符。
  • 任务级重排：按轨迹长度重排，优先更短、更通用的示范（§C.1）。
  • 里程碑级去重：两条命中不能来自同一条专家轨迹；每个片段多取一个动作作为前向上下文（§C.2）。
  • 模型：Mixtral-8x22B-Instruct-v0.1（稀疏 MoE）和 LLaMA-3.3-70B-Instruct（dense）；所有输出 temperature=0.0。
  • 步数上限：ALFWorld 每局最多 50 步；WebShop 每局最多 40 步。
成本缺口

论文没有报告 token、延迟或 API 成本

论文给出了库的规模（3,330 条）和每步的算法流程，但没有报告每次 LLM 调用的 token 数、端到端延迟、检索延迟或 API 成本；也没有报告库规模扩大后的检索开销。

从 Algorithm 1 能看到每步至少有一次 hint 生成和一次动作决策（第 17–18 行）；论文没有说明这两次调用是否合并，也没有给出延迟数字。

它依赖专家演示，也没解决「里程碑是否真的完成」

这一节列出论文自己报告的失败模式，以及论文没有回答的问题。

前提

必须有成功的专家演示

离线库来自 577 条成功演示（ALFWorld 500、WebShop 77）。论文假设能拿到这些演示；没有讨论演示稀少、质量差或新领域没有演示时怎么办。

这是方法的前提条件，不是实验结论。

切分

里程碑由 GPT-4o 切，质量没有单独评估

切分和描述由 GPT-4o-2024-08-06 完成。论文没有报告切分错误率，也没有做切分质量的消融。

如果切分把不同子目标混在一起，库里的「里程碑」就不再是中等粒度。

失败模式 1：里程碑没完成就跳下一步

Appendix D.1 的例子：任务 “put a cool tomato in the microwave”，agent 把番茄放进微波炉，但没有完成冷却步骤——尽管冷却在生成的里程碑指南里是明确的一步。论文归因于文本观测下很难判断物体状态是否真的改变。

“the agent moves the tomato into the microwave without successfully performing the cooling step—despite this being an explicitly defined milestone in the generated action guide.”

失败模式 2：语义误识别与低效重复

同一附录还列了两类 ALFWorld 错误：一是语义误识别，例如要找 “apple” 却反复找不到，最后拿成 “tomato”；二是低效重复探索，例如 “heat an egg and put it in the garbagecan” 任务里，超过 40 步反复开同一个冰箱、抽屉和不存在的 “diningtable 1”。

“over 40 steps were spent re-opening the same refrigerator, drawers, and non-existent objects like ‘diningtable 1’ before finally locating the egg in an unexpected container (the garbagecan itself).”

失败模式 3：WebShop 的规格漂移与动作循环

Appendix D.2 列了三类：规格漂移（忽略尺寸/材质/颜色，直接买默认款）、动作循环（点当前页面不存在的按钮）、信息利用不足（忽略搜索结果里已经出现的正确商品）。其中一个例子是用户明确要求 “6.76 fl oz”，agent 跳过选项选择，直接购买了默认规格。

“although the user explicitly requested a product with ‘6.76 fl oz’ volume, the agent skipped the option selection step and directly purchased the default variant.”

论文没有回答的问题

  • 库规模扩大后的检索效率与准确性：论文只有 3,330 条记录，没有 scaling 实验。
  • 跨任务迁移：论文把「总结 step-wise hints 的经验、做跨任务知识迁移」列为 future work，而不是已实现的组件。
  • 成本：没有 token、延迟、API 成本报告；也没有说明 hint 生成和动作决策是否合并成一次 LLM 调用。
  • 模型范围：只测了两个开源模型（Mixtral-8x22B、LLaMA-3.3-70B），两个基准（ALFWorld、WebShop）。
什么时候别用

三个边界

  • 没有成功演示：离线库无法构建。这是方法的硬前提。
  • 任务很短、步骤很少：建库 + 两次检索的固定开销可能不划算。推断（依据：论文只在 ALFWorld / WebShop 这类长时程任务上评测，没有短任务实验）。
  • 环境变化快到里程碑定义失效：Algorithm 1 只在开始时生成一次 Gτ，执行中只更新里程碑索引 k，不重新生成指南。推断（依据：Algorithm 1 第 12–26 行；论文没有研究动态重规划）。
