ReSearch：把搜索动作写进推理链，用最终答案的 F1 当奖励

多跳问题需要「先搜 A，看到结果再决定搜 B」。ReSearch 不标注任何推理步骤，直接把 <think>、<search>、<result>、<answer> 拼成一条 rollout，用 GRPO 优化最终答案的 F1；检索结果 token 在损失里被掩码，模型只为自己的思考与查询负责。 只在 MuSiQue 上训练；7B 模型在四个多跳基准上的平均提升为 15.81 个百分点 EM、17.56 个百分点 LJ（原文报告值；按 Table 2 复算，口径是四个基准对 Iter-RetGen 的绝对点差平均，见 §6.2）。

Mingyang Chen 等 · 百川智能 / 中国科学院大学（UCAS） / 同济 / 爱丁堡 / 浙大 arXiv 2503.19470v3 ↗ 代码 ↗
TL;DR · 30 秒抓住核心

搜索不是前置步骤，而是推理链里的动作。 模型每写一个 <search>，环境就检索一次并把结果塞进 <result>；模型基于结果继续写 <think>，直到输出 <answer>。搜索的时机、查询词、迭代次数都由模型自己决定（§2.1、Figure 2）。

奖励只有两项：答案 F1 + 格式。 F1 非 0 时奖励就是 F1；F1 为 0 但格式正确给 0.1；格式也错给 0。没有过程奖励，也没有推理步骤标注（§2.3、Eq.2）。

只在 MuSiQue 上训练，评测四个基准。 训练集 19,938 条，2 个 epoch；评测 HotpotQA、2WikiMultiHopQA、MuSiQue、Bamboogle。原文报告 7B 的平均提升是 15.81 个百分点 EM、17.56 个百分点 LJ，32B 是 14.82 / 15.46 个百分点。按 Table 2 复算，这四个数是四个基准对 Iter-RetGen 的绝对点差平均，不是相对提升，也不是对每列最强基线的差值平均（详见 §6.2）。

案例里出现了自我纠错，但只是单例。 第一次搜「Martín Ramírez Pech」搜到同名画家，模型在下一段 <think> 里说「我似乎搜错了」，把查询改成「Martín Ramírez Pech political party」，再继续搜（Table 3）。论文把它作为定性证据，不是系统性评测。

01

多跳问题的瓶颈：下一步搜什么，取决于上一步搜到了什么

传统 RAG 把检索当预处理；ReSearch 把检索当动作，让模型在推理过程中反复决定。

「《星际穿越》的导演的出生地的市长是谁？」这类问题需要三条依赖链：先找导演，再找出生地，再找市长。传统 RAG 通常在回答前检索一次或固定几次，把结果拼进上下文；它无法根据「第一次搜到了什么」动态决定「第二次搜什么」（§1）。

提示工程路线（Iter-RetGen、IRCoT）可以让模型多轮检索，但轮次与提示模板由人设计；模型是在「遵循流程」，不是在「学习策略」。监督微调路线需要标注推理步骤，成本高、规模受限。论文的切入点是：只给最终答案的对错，让模型在试错中自己学出「什么时候搜、搜什么」（§1、§2）。

缺口 1

检索与推理是割裂的

Naive RAG 先检索再生成；Iter-RetGen 与 IRCoT 虽然迭代，但迭代规则由外部提示控制。模型没有把「搜索」当成自己的动作（§1、§3.1）。

缺口 2

过程标注太贵

要监督「第几步该搜什么」，需要人工写推理链。论文选择不标注过程，只用最终答案的 F1 与格式做奖励（§2.3）。

这个设定带来一个工程问题：rollout 里既有模型生成的 token，也有检索环境返回的 token。如果损失把检索结果也算进去，策略会被「环境写的文本」带偏。ReSearch 的做法是把 <result> 内的 token 全部掩码，只对 <think> 与 <search> 计算损失（§2.1）。

02

四条对照路线：无 RAG、Naive RAG、Iter-RetGen、IRCoT

Table 2 的基线都是提示/RAG 方法；论文没有把 Search-R1 等 RL 搜索 Agent 放进同一张表。

基线 A

Naive Generation

不检索，直接用指令微调模型回答。多跳问题需要的事实往往不在参数里，因此 EM 最低（§3.1、Table 2）。

基线 B

Naive RAG

先用问题检索一次，把结果拼进上下文再生成。比不检索好，但仍然只有一轮，无法根据中间结果改写查询（§3.1）。

基线 C

Iter-RetGen / IRCoT

两者都做多轮检索与生成：Iter-RetGen 交替检索与生成，IRCoT 用思维链引导检索。轮次与提示由人设计，不是从奖励里学出来的（§3.1）。

ReSearch 与这些基线的差别不是「多搜几次」，而是「搜索策略由策略网络生成」。同一套 Qwen2.5 底座下，ReSearch 只在 MuSiQue 训练，却在 HotpotQA、2Wiki、Bamboogle 上也能用；这被论文称为泛化能力（§3.2）。

“We treat the search operation as part of the chain-like reasoning process, and the search operation will interact with text-based thinking.” §1 · 论文对 ReSearch 的核心表述
03

一条 rollout 就是「思考—搜索—结果—再思考」的循环

没有 SFT 冷启动，直接在 Qwen2.5 权重上做 GRPO；格式靠 prompt 约束，正确性靠 F1。

3.1 Rollout：遇到 </search> 就停，检索完再续写

生成过程遇到 </search> 时暂停，把最近的查询送给检索器；检索结果包进 <result> 后拼回上下文，模型继续生成。这个过程循环到模型输出结束符或 <answer>（§2.1、Figure 2b）。

x → <think> … </think> <search> q1 </search> <result> r1 </result>
→ <think> … </think> <search> q2 </search> <result> r2 </result> → … → <answer> a </answer>
§2.1 · 查询与结果交替追加；模型只为 <think> 与 <search> 内的 token 负责

检索环境是 FlashRAG + E5-base-v2，知识库是 2018 年 12 月的 Wikipedia；每次查询取 top-5。训练与评测用同一个环境（§3.1）。这意味着模型学到的是「在这个 Wikipedia 检索器上怎么搜」 推断；换到真实网页搜索是否成立，论文没有实验（依据：§3.1 的训练与评测共用同一 FlashRAG + E5-base-v2 + 2018 Wikipedia 环境，未测试其他检索器或知识库）。

3.2 GRPO：组内比较，不需要 critic

每个问题采样 5 条 rollout，用组内奖励的均值与标准差归一化出优势；目标函数带 clip 与 KL 惩罚，KL 系数 0.001，clip 比例 0.2（§2.1、Eq.1、Table 4）。相比 PPO，GRPO 不需要单独训练 critic，省一份模型与一份显存。

奖励是规则式的，没有奖励模型：

r = F1(apred, agt)  if F1 > 0
r = 0.1  if F1 = 0 and format correct
r = 0  if F1 = 0 and format incorrect
§2.3、Eq.2 · 格式检查主要看标签是否正确、答案是否放在 boxed 里

这个奖励的设计后果是：模型只要格式对，就能拿到 0.1 的「保底分」；一旦答案 F1 大于 0，奖励就变成连续的 F1，而不是 0/1。论文没有额外加长度惩罚或搜索次数惩罚；Figure 3 的搜索次数随训练上升，但论文没有给搜索次数的上限或成本约束（§3.3）。推断：奖励只来自最终答案 F1 与格式，模型可能倾向「多搜几次」而不是「更准地搜」（依据：§2.3 的 Eq.2 没有搜索次数/成本项，§3.3 未给上限）。

3.3 Prompt：base 与 instruct 两套模板

base 模型直接把模板拼在问题前；instruct 模型把模板作为 system prompt，再套 chat template。模板里给出一个完整的标签示例，要求模型用 <think>、<search>、<result>、<answer> 组织输出（§2.2、Table 1）。

论文强调模板「简单、简洁」，让模型在 RL 中自然延续，而不是靠复杂的格式约束。F1 为 0 但格式正确的 rollout 仍可拿到 0.1，这是格式保底奖励的用途（§2.2、§2.3、Eq.2）。

04

64 张 H800、全参数、2 个 epoch；训练数据只有 MuSiQue

这是论文给出的全部训练开销信息；没有报告总 GPU 小时或费用。

硬件

8×8 Nvidia H800

共 64 张 H800，全参数优化 + gradient checkpointing（Appendix B）。论文没有给单卡显存、训练时长或总 GPU 小时。

数据

MuSiQue 训练集 19,938 条

只使用 MuSiQue 训练集，训练 2 个 epoch；batch size 256，学习率 1e-6，rollout 温度 1.0（§3.1、Table 4）。

检索

top-5 Wikipedia，E5-base-v2

知识库是 2018 年 12 月的 Wikipedia，检索器 E5-base-v2，每次取 top-5；索引与 embedding 由 FlashRAG 预处理（§3.1）。

评测

四个基准，EM + GPT-4o-mini

HotpotQA 7,405 条、2Wiki 12,576 条、MuSiQue 2,417 条、Bamboogle 125 条；EM 与 LLM-as-a-Judge 并用（§3.1）。

论文没有做不同硬件、不同 batch size 或不同检索器数量的消融。推断：不能把 64 张 H800 的配置直接外推到更小或更大的集群（依据：Appendix B 只给 8×8 H800、全参数 + gradient checkpointing，未报告显存、并行策略或训练时长）。也没有报告训练总 token 数或检索调用次数。

6.3 训练曲线与案例：搜索次数上升，出现一次自我纠错

Figure 3 统计训练过程中的响应长度与搜索次数：四条曲线（7B/32B × base/instruct）的搜索次数都随训练步数上升；32B 的响应长度在前 20 步先下降，约 60 步后再上升（§3.3）。论文的解释是 32B 初始更依赖内部知识，收到奖励信号后才开始更多检索。Figure 3 没有标出每条曲线的具体数值，页面只引用趋势，不引用精确次数。

Table 3 的案例是「Martín Ramírez Pech 所属政党所在国家的 2018 年总统选举谁赢了」。第一次搜「Martín Ramírez Pech」返回同名画家的信息；模型在下一段 <think> 里说「我似乎搜错了」，把查询改成「Martín Ramírez Pech political party」，第二次搜到墨西哥工党，再搜「2018 Mexican presidential election」，最后答 Andrés Manuel López Obrador。整条轨迹用了三次 <search>（Table 3）。这是一个定性案例，论文没有统计这种自我纠错在测试集上的频率。

07

边界：只用 Wikipedia、只训 MuSiQue、只验证短答案

这些条件决定了 ReSearch 的结论能推广到哪一步。

检索环境

2018 年 Wikipedia + E5-base-v2

知识库固定为 2018 年 12 月的 Wikipedia，检索器固定 E5-base-v2，top-5。没有真实网页搜索、没有多语言、没有时效性数据；换检索器或换知识库后的表现未测（§3.1）。

训练数据

只训 MuSiQue 一个数据集

训练集 19,938 条，2 个 epoch。论文把跨 HotpotQA/2Wiki/Bamboogle 的结果称为泛化，但这些都是英文多跳 QA，任务形态接近；不能据此推断开放域研究或长文写作也能泛化 推断（§3.1、§3.2）。

奖励

短答案 + F1，不适合长回答

奖励要求答案能被 F1 比较，适合事实型短答案；论文在 Appendix C 明确说，更长、更微妙的回答需要更复杂的奖励建模（Appendix C）。

对照

没有 RL 搜索 Agent 基线

Table 2 的基线是 Naive Generation、Naive RAG、Iter-RetGen、IRCoT，都是提示/RAG 方法；没有把 Search-R1 等 RL 训练方法放进同一张表。跨论文比较受底座、数据、检索环境影响，不能直接下结论（§3.1、Table 2）。

结果层面还有三条边界。第一，不是每个单元格都随 instruct 提升：7B-Instruct 的 Bamboogle EM 42.40 低于 7B 的 43.20。第二，论文的「8.9%–22.4% 绝对提升」与 Table 2 的 Bamboogle 差值 25.60 不一致：正文这句话对应 Figure 1，而 Table 2 的 32B-Instruct 56.80 对 IRCoT 31.20 差 25.60；页面把两处并列，不替作者消解。第三，训练曲线只给趋势：Figure 3 没有标出搜索次数的具体值，不能引用「从 1.5 涨到 3.5」这类读数。

方法层面最值得记住的是「检索结果掩码」：它让策略只为自己的思考与查询负责，不被环境文本带偏。代价是模型学不到「如何改写检索结果」，也不直接优化检索质量 推断；检索器的召回上限就是策略的上限（依据：§2.1 的损失掩码让 <result> token 不参与梯度，§2.3 的奖励只来自最终答案 F1 与格式，没有检索质量项）。

  • 「和 Search-R1 的区别就是多了个格式奖励」不完整：Search-R1 论文（arXiv 2503.09516）用 EM 作答案奖励、每次检索 top-3、训练集是 NQ + HotpotQA；ReSearch 改成 F1、top-5、只训 MuSiQue（§2.3、§3.1）。另外 Search-R1 论文 §3.4 明确写 “we do not incorporate format rewards”，其官方仓库的 format 变体才设置 reward_model.structure_format_score=0.2、final_format_score=0.1；所以格式奖励也不是 ReSearch 独有。
  • 「平均提升 15.81%」是绝对点差，不是相对提升：原文 §3.2 写的是 “the average improvement of ReSearch over the best baseline is 15.81% in exact match and 17.56% in LLM-as-a-judge”；但按 Table 2 复算，四个数是四个基准对 Iter-RetGen 的绝对点差平均（7B EM 加数 9.16 / 19.67 / 13.61 / 20.80），不是相对提升，也不是对每列最强基线的差值平均（Bamboogle 若用 IRCoT 24.80，差值是 17.60）。页面统一写成 15.81 个百分点，并另列逐基准差值。
  • 「Bamboogle 31.20→56.80」正确，但「提升幅度巨大」要限定：31.20 是 IRCoT 的 EM，56.80 是 32B-Instruct 的 EM；这是 EM 口径，LJ 是 47.20→67.20。两者不能混着说。
  • 「Figure 3 搜索次数稳步上升」正确，但没有具体数值：图里只有曲线，没有标注每次训练步的平均搜索次数；不能从图上读出一个精确的起止值。
  • 「只在 MuSiQue 上训练」正确，但评测也是英文多跳 QA：HotpotQA、2Wiki、MuSiQue、Bamboogle 都是英文多跳问答；「泛化」不能外推到开放域网页研究或长文任务。
