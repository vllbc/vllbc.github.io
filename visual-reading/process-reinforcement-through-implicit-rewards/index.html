PRIME：只用结果标签，训出 token 级过程奖励

过程奖励能把信用分配做细，但每一步都要标签，成本高到无法在线更新。 PRIME 把奖励模型写成 causal LM，用最终对错做交叉熵训练，推理时取 β log(πφ/πref) 得到每个 token 的隐式奖励；PRM 因此可以和策略一起在线更新。 代价是仍然依赖结果验证器，实验只覆盖数学与代码。

TL;DR · 30 秒抓住核心

结果奖励只在序列末尾给一个信号，所有 token 共享同一个 advantage；过程奖励能细分信用，但人工标注每一步的成本让它无法跟着策略在线更新。

PRIME 的关键替换：奖励模型 πφ 仍是 causal LM，训练时只用 r_o(y) 做序列级交叉熵；推理时把同一模型在 token 上的 log 概率比拿出来，rφ(y_t)=β log[πφ(y_t|y<t)/πref(y_t|y<t)]。结果标签负责「对错」，语言模型负责「每一步有多像会通向对错的续写」。

在线更新是重点：PRM 用策略自己采出的 rollout 更新，分布跟得上策略、缓解漂移（§5.1）；SFT 模型直接当 PRM 初始化，省掉独立 RM 训练阶段。代价是相对 RLOO 每步多一次 PRM 更新（Table 2：150.9 秒），相对传统 ORM 的 token 级奖励不额外收费（§3.1），且必须有一个可靠的结果验证器。

01

答案对了，不代表每一步都对

结果奖励把所有信用压到最后一个 token；这是信用分配问题，不是训练技巧问题。

策略梯度的通用形式里，advantage 是「从第 t 步开始的折扣回报减去基线」：

At = Σs=tT γs−t r(ys) − b
Eq. 2 · Monte-Carlo advantage；γ 是折扣因子，b 是基线

如果只有结果奖励，r(yt)=0（t<T），只有最后一个 token 拿到 r(yT)。Eq. 2 退化成 A = r(yT) − b：一条回复里所有 token 共享同一个 advantage，模型无法知道哪一步写对了、哪一步写歪了。

§2.1

稀疏奖励的三个直接后果

  • 奖励侥幸：答案对、过程错也能拿高分，策略可能强化这种「蒙对」的路径。
  • 样本效率低：反馈只在序列末尾出现，中间步骤没有梯度信号。
  • 信用分配难：责任无法落到具体 token 或步骤，长链条推理尤其严重。

稠密过程奖励本来是对症药：每个 token 或每一步都给分，advantage 就能按位置拆开。但第一步就卡住了——过程标签怎么定义？推理步骤不像 token 那样有天然边界；人工标每一步成本高；而且「这一步错了」不一定等于「对最终答案没有贡献」，有些错误步骤反而通过剪枝搜索空间帮到了最终结果（§2.2 C1）。

所以真正的问题不是「要不要稠密奖励」，而是「稠密奖励的标签从哪来，怎么在策略变化时持续更新」。这引出了 02 的两条现有路线。

02

两条现有路线：一条太稀疏，一条太贵

结果奖励便宜但粗；显式 PRM 细但需要步级标签，离线训练还会被策略分布甩开。

路线 A

只用结果奖励的 RL

做法：RLOO、GRPO、PPO 等只接一个规则验证器：数学题比对最终答案，代码跑测试用例。

优点：验证器便宜、可扩展，奖励不容易被策略直接 hack。

卡点：信号稀疏。所有 token 共享同一个 outcome advantage，过程质量没有被单独评价；长推理链上，信用分配仍然靠猜（§2.1）。

路线 B

显式过程奖励模型（PRM）

做法：给每一步或每个 token 打过程标签，训练一个独立的 PRM，再把它接进 RL。

优点：信号稠密，理论上能更细地分配信用。

卡点：步级标签要么靠人工流水线（Lightman et al. 2023），要么靠估计方法——论文引用后者需要约 10× 的 rollout（§1）。离线 PRM 还会因策略分布漂移被 overoptimize，出现 reward hacking（Gao et al. 2022；§5.1）。

C1

过程奖励难定义

推理步骤没有天然边界；某些「错步」也可能通过剪枝搜索空间贡献最终答案（§2.2）。

C2

在线更新不可扩展

要防 reward hacking，PRM 得跟着策略在线更新；但传统 PRM 每轮都要新的步级标注，成本不可行（§2.2）。

C3

显式奖励建模有额外成本

独立 RM 需要额外数据与训练。论文的对照 EurusPRM 就用了额外 500K 数据（§5.1）。

PRIME 的选择不是「再训一个更好的 PRM」，而是换一种奖励参数化：让 PRM 本身就是一个语言模型，用结果标签训练，却能在推理时输出 token 级奖励。这样 C1 的步级标签、C2 的在线更新、C3 的独立 RM 阶段可以一起绕开。

03

过程奖励不必标注：从结果标签里推出来

把 PRM 写成语言模型，序列级奖励是 log 概率比；到 token 级，同一个比值就是过程奖励。

序列级：隐式 PRM πφ 和参考模型 πref 都是 causal LM。奖励定义为两个模型对整条回复的 log 概率比：

rφ(y) := β · log [ πφ(y) / πref(y) ]

Token 级：把整条概率拆成逐 token 条件概率，就得到 Eq. 3：

rφ(yt) := β · log [ πφ(yt | y<t) / πref(yt | y<t) ]
Eq. 3 · 陶土红是待训练的隐式 PRM，青灰是固定参考模型；β 是奖励缩放

训练阶段和普通 ORM 一样：只拿最终结果 ro(y) ∈ {0,1}，对序列级奖励做交叉熵：

LCE(φ) = −E(x,y,ro(y))~T [ ro(y) · log σ(rφ(y)) + (1 − ro(y)) · log(1 − σ(rφ(y))) ]
Algorithm 1 第 8 行 · T 是经过准确率过滤后的 rollout 集合

关键在于：训练时只用了结果标签，推理时却拿到了 token 级信号。论文强调同一个 πφ 既用于在线更新，也用于算 token 级奖励，因此相对传统 ORM 不引入额外的奖励建模阶段与过程标注开销（§3.1）。因此 PRM 可以在线更新：每轮用策略新采的 rollout 和结果标签更新 πφ，奖励分布跟得上策略，而不是停在一个离线快照上。

核心机制

结果标签负责对错，语言模型负责「每一步有多像会通向对错的续写」

rφ(yt) 为正，说明 πφ 比 πref 更倾向生成这个 token；为负则相反。它衡量的是「这个 token 在多大程度上把模型推向高结果奖励的分布」，不是对这一步逻辑的绝对正确性判断。

怎么把稠密奖励接进 RL：PRIME 把过程回报和结果回报分开算，再相加。论文的理由是直接混合两者可能导致数值不稳定（§3.2）。对过程奖励，先用平均隐式奖励算 leave-one-out 基线，再对每个 token 做折扣回报；对结果奖励，直接做 LOO。合起来是 Eq. 5：

Ati = Σs=t|yi| γs−t [ rφ(ysi) − (1/(K−1)) Σj≠i rφ(yj) ] + [ ro(yi) − (1/(K−1)) Σj≠i ro(yj) ]
Eq. 5 · 前一项是 implicit process reward 的 RLOO 回报，后一项是 outcome reward 的 RLOO 回报

策略更新用 PPO clip surrogate loss（Eq. 6），把重要性采样比限制在 [1−ε, 1+ε]。论文默认 K=4、β=0.05、KL 系数 0（§4.1）。

CE 损失的最优点带一个偏置，为什么 PRIME 不受影响？附录 C.2

因为 πφ 和 πref 都是自归一化的语言模型，CE 的最小损失 0 达不到；最优解满足 β log(πφ*/πref) = ro + c，多出一个与 prompt 有关的常数 c（§C.2）。PRIME 用的是相对奖励 rφ(yi) − LOO，同一个 prompt 内的 c 会被减掉，所以不影响 advantage。论文也用 DPO 损失做了对照：Table 8（96 步）的 Avg 为 32.4（DPO）vs 32.3（CE），两者接近，作者选 CE 是因为更省显存。

04

训练循环：PRM 与策略同步更新，PRM 更新占 150.9 秒/步

Algorithm 1 的工程版本：采样 K 条、验证、过滤、算隐式奖励、更新 PRM、算 advantage、PPO 更新策略。

把 Algorithm 1 展开成一轮循环：

  1. 初始化：策略 πθ、旧策略 πθold、隐式 PRM πφ、参考模型 πref 全部从同一个起点 πinit 复制（第 1 行）。
  2. 采样：每个 prompt 采 K 条回复，默认 K=4（第 4 行）。
  3. 结果验证：数学用 exact match，代码用通过测试用例的比例，得到 r_o(y)（§4.1）。
  4. 过滤：只保留准确率落在中间区间的 prompt，平衡难度与数据分布（§3.3；Figure 2）。
  5. 隐式奖励：对过滤后的样本前向 πφ 和 πref，用 Eq. 3 算每个 token 的奖励（第 7 行）。
  6. 更新 PRM：用 r_o(y) 做 CE 更新 πφ（第 8 行）。
  7. 算 advantage：按 Eq. 5 把过程回报和结果回报相加（第 9 行）。
  8. 更新策略：用 PPO clip loss 更新 πθ，然后 θold ← θ（第 10–11 行）。

两个实现细节：单次前向与参考模型

单次 vs 双次前向：默认单次前向，直接用旧 PRM 的过程奖励；双次前向先更新 PRM 再重算奖励，PRM 准确率更高，但训练奖励与单次接近（§B.2；Figure 11）。

参考模型：可以用初始 SFT 模型（SFT ref），也可以用运行策略的旧 logprob（policy ref）；两者训练奖励接近，但只有保留初始 SFT 模型才能算 KL（§B.1；Figure 9–10）。

在线 prompt 过滤：论文用「只接结果奖励的 RLOO」做消融，过滤后训练奖励方差明显下降（§3.3；Figure 2）。

反直觉 1

SFT 初始化胜过 500K 数据的 PRM

EurusPRM 用额外 500K 数据训练，Figure 4 里却被直接用 Eurus-2-7B-SFT 初始化的在线 PRM 超过。论文的猜测是：策略与 PRM 同源初始化，减轻了分布漂移；PRM 只在线训练策略自己的 rollout（§5.1）。

反直觉 2

离线 PRM 的准确率会往下掉

离线 PRM 一开始准确率高，但随着策略漂移逐渐被 overoptimize；在线更新的 PRM 则持续上升（Figure 5；§5.1）。这是「必须在线」的直接证据。

反直觉 3

奖励模型比价值模型更合适

同一个隐式 PRM，当 reward model 用（RLOO w/ PRIME）平均 41.0；当 value model 用只有 36.6（Table 4）。论文的解释是 value 形式没有把 token 级奖励直接变成 return（§5.4）。

换一个训练设置：DeepScaleR 的 1.5B 模型

在 DeepScaleR 的设置下（1.5B 模型、8k 阶段），PRIME-DeepScaleR-1.5B-Stage1 跑 330 步，平均 52.0；DeepSeek-R1-Distill-Qwen-1.5B 是 48.9，差 3.1 个百分点（52.0 − 48.9，Table 7）。GPU 时间 446.7 小时，DeepScaleR stage 1 约 600 小时（§B.7）。

07

它依赖一个可验证的终点

方法把「过程标签」换成了「结果验证器 + 在线更新」；这解决了标注成本，但没有解决所有任务。

边界一

结果验证器是前提

论文的验证器只覆盖数学（exact match）与代码（测试用例通过率）（§4.1）。没有廉价、可靠结果验证器的任务——开放写作、策略规划、主观咨询——这套奖励没有落脚点。推断（依据：§4.1 只定义 math/code 两类 OV；§4.2 与 Appendix B 的实验也只覆盖数学与代码。）

边界二

规模只验证到 32B

Appendix A 明确写：“we only conducted experiments on models up to 32B”。其他消融还只跑了较少步数；论文说主实验之外的对比在相同步数下进行，但没有给出更大模型的结果。

边界三

PRIME-Zero 会早饱和

从 base model 直接 RL 的 “Zero” 设置收敛很快，7B 与 32B 都能在早期超过 instruct 版本；但论文报告约 50 步后就快速饱和，作者猜测可能归因于 response diversity 下降（原文 “This is possibly attributed to...”），留作未来工作（§B.4）。

边界四

critic 的额外收益有限

PPO w/ PRIME 的 39.4 低于 RLOO w/ PRIME 的 41.0（Table 4）；§B.3 称 critic 的额外计算冗余，但同表 PPO 从 35.8 升到 39.4（+3.6），按表内数值仍受益。奖励模型规模也不是越大越好：固定策略为 Qwen2.5-7B-Base，奖励模型 3B / 7B / 14B 的 Avg 分别为 32.0 / 32.6 / 31.8（Table 5）；论文只测了这三个规模。

使用建议

先问三个问题，再决定是否套 PRIME

  • 终点可验证吗？数学答案、代码测试可以；开放式任务需要先有可靠的 judge 或人工反馈，否则隐式奖励没有结果标签可学。
  • 愿意付每步一次 PRM 更新吗？Table 2 的 PRM update 是 150.9 秒/步；步数效率 2.5×，但 wall-clock 只有约 2×（§4.3）。如果 rollout 很短、PRM 开销占比更高，收益会被进一步压缩。
  • 需要的是 reward 还是 value？论文的证据支持把隐式 PRM 当 reward model；当 value model 用时，Table 4 的 36.6 明显低于 41.0。

还有两点技术边界：CE 损失的最优点带一个 prompt 级偏置，PRIME 靠相对奖励把它消掉（§C.2）；在线更新只是 mitigate reward hacking，论文的措辞没有说消除（§5.1）。β 在正文只报了 0.05（§4.1），没有展开敏感性实验。

一句话：PRIME 把「过程监督」的成本转嫁给了「结果验证器 + 在线 PRM 更新」。终点可验证、且愿意付每步一次 PRM 更新时，这套账算得过来；终点本身无法验证时，它没有落脚点。
