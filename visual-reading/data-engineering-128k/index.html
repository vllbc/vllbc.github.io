Data Engineering for 128K Context：80K 长度上训 5B token，再外推到 128K 精确检索

论文的赌注是：在任意位置使用长上下文信息的能力，在 4K 预训练时就已经基本具备，持续预训练只需要把它「解锁」出来。做法不改架构，只调 RoPE base，改的是数据——在保持领域比例不变的前提下，按领域把长文档挑出来上采样，再训 1–5B token。注意长度口径：7B 实际在 80K 上训练、在 128K 文档上测试；Figure 3/§5.2 显示 100–500M token 时模型在 80K 内检索尚可，但泛化不到 80K–128K，需训到 5B 才能外推到 128K。

TL;DR · 30 秒抓住核心

开源模型号称支持 100K，但在 Needle-in-a-Haystack（NIAH）上塌掉：LongLoRA 100K 70.0、YaRN Mistral 128K 57.4，而 GPT-4-Turbo 128K 是 87.1（Table 3）。论文认为差距主要不在架构；数据量也只要 1–5B token，远低于前人动辄数百 B 的持续预训练。

关键在「喂什么样的数据」，而非堆数据量：Figure 3 里 token 从 100M（NIAH 37.8）加到 500M（81.1）就解锁了 80K 内的大部分检索，但未能外推到 80K–128K；5B 达到峰值 88.0 并泛化到 128K，10B 反而回落到 84.0（Figure 3）。推断（Figure 3、§5.2 明确说 500M–1B 不泛化到 80K–128K，故「解锁 128K」这一结论需 5B 才成立）。

数据质量 = 领域平衡 × 长度上采样：在各领域内部把长于 4K 的序列占比从约 30% 提到约 70%，领域比例沿用 SlimPajama（网页 82%、代码 4.5%、Wikipedia 4.5%、书 4.5%、Arxiv 2.5%、StackExchange 2.0%）。

代价很直白：全参数持续预训练，7B 训 80K 长度（13B 训 64K），8×80G A100 上约 5 天。短上下文能力用 MMLU 兜底：7B 43.3、13B 52.4。

01

128K 窗要解决的不是「装不装得下」，而是「中间那一段找不找得到」

读完后你应该知道：为什么业界的共识是用几百 B token 去「注入」长上下文能力，以及论文为什么认为这是花错了力气。

NIAH 把一句话（needle）随机插进一篇长文（haystack）的任意位置，要求模型原样复述（Kamradt, 2023）。Figure 1 把结果画成网格：横轴是文档长度 1K→128K，纵轴是针所在深度 0%→100%，绿格=找到，红格=没找到，胜利条件几乎是全绿。

2023 年底的现实是：LongLoRA 100K 的 NIAH 只有 70.0，YaRN Mistral 128K 只有 57.4，LongChat v1.5 32K 只有 18.0（Table 3），前沿级别的表现只见于 GPT-4 128K（87.1）。同时，LLaMA Long 与并行的 XVERSE 采用约 5000 亿 token（§1 原文 500 billion）做持续预训练，成本接近从头预训练。

论文的出发点是一个可证伪的假设：在 128K 内任意位置使用信息的能力，大部分在 4K 的大规模预训练里已经获得，持续预训练只是把它「解锁」（原文 unlock，§1、§5.2）。如果假设成立，需要的不是 5000 亿 token，而是一小份能把这个能力接出来的数据。

这个网格是怎么画出来的？换算规则与它不代表什么

论文在 Figure 3 的每张网格上方只给一个总体准确率（37.8 / 59.0 / 81.1 / 85.3 / 88.0 / 84.0），没有逐格数值。本页的示意规则：

  • 网格共 3 行（针深度 0% / 50% / 100%）× 12 列（长度刻度 1K → 128K），共 36 格。
  • 每行失败格数 r = round(100 − 准确率)（取整、封顶 12）；失败格总数 = 3r，每行成功格 = 12 − r，读数里的「成功格 / 36」= (12 − r) × 3。
  • 失败格从最右（128K）往左整列填充（近似论文的「文档越长越难」），所以每行右侧恒为灰、左侧染成强调色。

各档 round(100 − acc)：100M 62、300M 41、500M 19、1B 15、5B 12、10B 16；封顶后 r 全部为 12。推断（由 Figure 3 顶部准确率换算）。因此本页网格在六档下形状相同，只作趋势示意，不映射准确率；各档差异请看读数里的真实准确率与第二组交互。

「成功格 / 36」是示意图内部计数的结果，不等于论文网格顶部的准确率（后者是论文自己统计的，本页不重算）。失败格落在哪几列是构造的。推断（失败格位置按论文「文档越长越难」的一般现象布置，图中并未逐格核对）。

口径：相对上一档的差 = acc[i] − acc[i−1]（单位：百分点）；Δ vs 5B = acc[i] − 88.0。两项都是差值，不是速率；因为起始几档等距（各差 200M），前三个 Δ 才恰好等于「每 200M」的斜率。保留 2 位小数，JS 与这里逐位一致。

  • 500M → 1B：85.3 − 81.1 = +4.20 个百分点；相对 5B：85.3 − 88.0 = −2.70。
  • 5B → 10B：84.0 − 88.0 = −4.00 个百分点；相对 5B 同样是 −4.00（上一档就是 5B）。

标准差：本交互只做加减，不涉及均值或标准差，故不涉及 ÷N 与 ÷(N−1) 的口径选择。

04

80K 的「暴力」训练只比 4K 慢约 3 倍，学术级资源就能跑

读完后你应该知道：为什么二次复杂度的注意力没让 80K 训练变得不可承受，以及论文给出的完整训练配置。

注意力是二次复杂度，直觉上 80K 该比 4K 慢约 400 倍。论文的解释是：训练时间的大头是 IO——CPU→GPU（offloading）、GPU→GPU（NVLink）、HBM→SM（FlashAttention 式分块）——这些都与序列长度线性相关；真正的二次注意力计算在 SM 上高度并行，被线性 IO 成本掩盖，于是「训 80K 只比训 4K 慢 3x」（§4）。

代价落在显存上：这套 HuggingFace Transformers + DeepSpeed Zero3 的配置已是框架上限，再长就 OOM；Zero 优化器是数据并行，加 GPU 也换不来更长上下文，显存主要被 KV cache 吃掉。要上 200K 得换序列并行（§4）。

训练本身很朴素：数据无视文档边界打包成 80K 块（跨文档拼接），batch 固定 4M token——原文强调这与 4K 训练的 batch 相同，靠「每块更长、每 batch 块数更少」保证一致；7B 在 80K 下训 5B token；恒定学习率 2e-5；唯一的架构改动是调 RoPE base（沿用 Xiong et al., 2023）。13B 只训 64K。

步数口径（§4）：原文写「5B（数据量）/ 4M（batch size）= 2000 optimization steps」，这个算式本身在算术上不成立——5B / 4M = 1250，要得到 2000 步需 5B / 2.5M。页面不改写原文的 2000，但也不把 1250 硬说成论文口径，两组数并列标注。若按 7B 80K 的实际配置（batch 4M token ÷ 80K/块 = 50 块）计，1250 步对应的正是 5B token：4M × 1250 = 5B。推断（2000 可能来自 batch 2.5M 或含其他行的统计；v1 §4 未给 2000 的解释，Figure 3 的 token 分档按比例换算与 1250 步/5B 自洽：100M ≈ 125 步、300M ≈ 375 步、500M ≈ 625 步、1B = 250 步、10B = 2500 步，见折叠）。

数据量：先快后慢，5B 见顶

Figure 3 固定配方、只改训练 token 数：100M → 500M 把 NIAH 从 37.8 拉到 81.1（+43.3 个百分点）；500M → 5B 只再多 6.9（到 88.0）；5B → 10B 反而降 4.0 到 84.0。论文据此判定 500M 就「解锁了大部分能力」，5B 是饱和点，10B 开始在 80K 训练区间上过拟合。

但 Figure 3 的 loss 不配合这个叙事：10B 那一格的 loss 在 1K–128K 为 1.79 / 1.55 / 1.40 / 1.31 / 1.35，5B 是 1.80 / 1.56 / 1.41 / 1.32 / 1.36，几乎逐列相同，NIAH 却从 88.0 掉到 84.0——又一次「loss 看不出差别」。

BookQA：同一张表里的越级

Ours 7B（27.4）高于 LongLoRA 7B（24.3，+3.1 个百分点）与 YaRN Mistral 7B（26.3，+1.1 个百分点），而 YaRN 的基底 Mistral 7B 本身比 LLaMA-2 7B 强（§5 的说法）；Ours 13B（31.1）比 YaRN（26.3）高 4.8 个百分点，相对 +18.3%。

07

它能「解锁」检索，不代表能「推理」长文

读完后你应该知道：这套方案的适用条件是什么，哪些场景不宜直接套用它的结论。

边界一

评测主力是 NIAH，考的是复述不是理解

主结论建立在单句检索上，真实长文任务只报了 BookQA。论文自己把 100K 级指令微调列为未解问题（§6），并指出目前还没有开源的 100K 指令微调模型。把 88.0 外推到长文档推理、多文档问答，超出了原文的范围。

边界二

只在 LLaMA-2 7B/13B 上验证

「能力已在预训练中获得」是针对这个基座的假设，论文没有证明它对 Mistral、MoE 或更大模型同样成立。数据量结论（500M 解锁、5B 饱和、10B 过拟合）也只在 80K 训练长度、4M batch、lr 2e-5 这组设定下得到，换尺度未必复现。

边界三

结构上限卡在 80K

训练长度受限于 HF+DeepSpeed Zero3 的显存，论文明确说更长会 OOM，且加 GPU 无法延长上下文（§4）。所谓「128K 能力」实际是 80K 训练 + 长度外推，Figure 1 的网格也显示 100K 之后开始变红。

边界四

代价小，但不是零

按源上采样把 0–4K 的 Wiki（−0.040）与 Book（−0.065）loss 压下去了，但 C4 与 CC 各 +0.008、Stack −0.001、Github −0.008——都贴着 ±0.01 的门槛。这组数说明的是「不破坏领域平衡」，而不是「短上下文毫无代价」推断（由 Table 5 中 0–4K 段 Per-source 行的符号与门槛反推）。

一句话收束：这篇工作的贡献是证明「长上下文是一条数据工程问题」，而不是给出长上下文能力本身的上限。
