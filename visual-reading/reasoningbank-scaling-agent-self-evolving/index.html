ReasoningBank：把成功与失败都炼成可检索的推理策略

流式任务里，Agent 没有 ground truth，也不能重训；如果只存原始的成功轨迹，或只把成功轨迹压成 workflow，经验很难迁移。 论文提出 ReasoningBank：把每条轨迹蒸馏成「标题 + 描述 + 内容」的策略条目，成功写可复用做法，失败写预防性教训，再用检索到的 top-k 条指导下一步。 它还把测试时扩展改造成 MaTTS：并行做 self-contrast、串行做 self-refinement，让多出来的 rollout 反过来产出更好的记忆。

Siru Ouyang 等 · UIUC / Google Cloud AI Research / Yale · Mahsan Rofouei、Hangfei Lin：Google Cloud AI arXiv 2509.25140v2 ↗ 代码 ↗
TL;DR · 30 秒抓住核心

问题不是单步能力，而是经验无法积累。 论文把设定放在 test-time learning：查询按流式到达，Agent 完成后才能看到下一条，过程中没有外部标签；它必须靠自己的成功与失败轨迹持续更新记忆（§3.1）。

记忆的单位是策略，不是轨迹。 每条记忆条目由 title、description、content 三部分组成；成功轨迹提炼「为什么有效」，失败轨迹提炼「下次怎么避开」。检索用 embedding 余弦相似度，默认只取 top-1 条经验（§3.2、Appendix A.2）。

MaTTS 让扩展与记忆互相供料。 并行扩展对同一任务的 k 条轨迹做 self-contrast；串行扩展对一条轨迹做多轮 self-refinement，并把中间笔记也当作记忆信号。扩展因子 k 越大，rollout 越多，但只有配上好记忆才能把多样性转成收益（§3.3、§4.3）。

结果有亮点，也有明确边界。 WebArena 总体在三个 backbone 上分别高 8.3、7.2、4.6 个百分点；SWE-Bench-Verified（Gemini-2.5-pro）高 3.4 个百分点。代价是依赖 LLM-as-a-judge，且检索条数超过 1 后成功率反而下降（Figure 13）。

01

每道题都从零开始，失败与成功都不会变成下一次的经验

先建立共同认知：在流式、无标签的设定里，「记住」本身就是一个学习问题。

论文研究的不是训练一个更大的模型，而是让一个已经部署的 Agent 在连续任务中变强。设定是 test-time learning：任务 q1, q2, … 按流式到达，每条查询只有在被处理时才可见；完成当前任务前，Agent 不能偷看后面的任务，也没有 ground-truth 标签可用（§3.1）。

“By approaching each new task in isolation, they are doomed to (i) repeat similar errors observed in the past, (ii) discard valuable insights gained from related problems, and, most importantly, (iii) lack self-evolving capabilities that make the agent system more capable over time.”— §1

这句话把问题拆成两层。第一层是存什么：原始轨迹太长、太吵，直接塞回上下文会淹没当前任务；只存成功 workflow 又会丢掉失败里的预防性信息。第二层是怎么用：检索到的记忆必须能指导下一步动作，而不是只作为「相似案例」摆在那里。论文把这两层合起来称为 memory-aware agent 的核心缺口（§1、§3.2）。

设定 1

没有外部标签，成败由 Agent 自己判断

论文用 LLM-as-a-judge 对轨迹做二分类，判断任务是 Success 还是 Failure；judge 的输入是用户意图、动作历史、最终网页状态和 Agent 回复，不需要标准答案（Appendix A.1、Figure 10）。

这意味着记忆的质量上限受 judge 影响：judge 把失败判成成功，错误策略就会进入记忆库。

设定 2

不训练参数，记忆是上下文的一部分

ReasoningBank 不更新模型权重；检索到的条目被拼进 system prompt，作为额外的决策依据（§3.2）。因此它可以直接换 backbone，但每次任务都要付检索与记忆注入的 token 成本。

论文的基线也都在同一套 ReAct 循环里跑；WebArena 用 BrowserGym，SWE 用 bash-only 环境（§4.1）。

评测覆盖三类任务：WebArena 的 5 个子集共 684 题（Shopping 187、Admin 182、Gitlab 180、Reddit 106、Multi 29）；Mind2Web 的 cross-task / cross-website / cross-domain；以及仓库级 issue 修复的 SWE-Bench-Verified（§4.1、Table 1）。这三个 benchmark 的共同点是：单步动作空间不大，但多步组合很长，早期的一个错误会沿轨迹放大。

02

两条现成路线：存原始成功轨迹，或把成功轨迹压成 workflow

论文的对照很集中：一条路线保留成功轨迹的具体细节，另一条把成功轨迹压成 workflow；两者都没有把失败转成可复用策略。

路线 A · 轨迹记忆

Synapse：把成功任务的完整轨迹放进上下文

Synapse 检索与当前任务最相关的历史成功轨迹，让 Agent 模仿其中的动作序列。优点是信息完整、具体；缺点是轨迹里混着大量示例特有的元素、页面状态和无关步骤，迁移到新任务时容易「照着旧页面找新按钮」（§2、§4.2、§5）。

论文在 Related Work 里的判断是：这类方法没有把经验抽象成更高层的推理模式，因此仍然停留在被动记录，而不是可执行的指导（§2）。

路线 B · 工作流记忆

AWM：把成功轨迹压成固定 workflow

AWM 把成功轨迹抽象成可复用的 workflow；Appendix B.1 的原话是 “abstracts common patterns from trajectories into reusable workflows”，没有给出「描述 + 泛化后的动作序列」这一细节。它比原始轨迹更结构化，也更省上下文；但它同样只从成功轨迹里构建记忆，失败轨迹被排除在外（§2、§4.2、§5、Appendix B.1）。

论文的批评原句是：prior work “by over-emphasizing successful experiences, they leave the valuable lessons from an agent’s own failures largely underexplored”（§1）。这句话同时适用于轨迹记忆和 workflow 记忆。

共同缺口

两条路线都没有把失败转成可复用的策略

Synapse 只保存原始成功轨迹，AWM 只把成功轨迹压成 workflow；两者都没有把失败轨迹转成可复用的策略条目。ReasoningBank 的切入点不是换一个检索器，而是换记忆的内容单位：每条经验都先被判定成败，再按成败走不同的提取提示，最后统一成结构化的策略条目（§3.2、§4.2、§5）。

这也解释了为什么论文把「加入失败轨迹」做成单独的消融，而不是当作附带的实现细节。Figure 7 在 WebArena-Shopping、Gemini-2.5-flash 上比较了「仅成功」与「成功 + 失败」两种记忆来源：ReasoningBank 从 46.5 升到 49.7（+3.2 个百分点，相对 +6.9%）；Synapse 只从 40.6 升到 41.7（+1.1 个百分点）；AWM 反而从 44.4 降到 42.2（下降 2.2 个百分点）。同样是「多给失败轨迹」，三种记忆设计的反应并不一样。

03

一条记忆 = 标题 + 描述 + 内容；成败走两套提取提示

核心不是「记住答案」，而是把轨迹里可迁移的推理模式抽出来，并让失败轨迹产出预防性规则。

论文把记忆库记作 M，初始为空。对第 t 个任务 qt，Agent 先用当前查询检索相关经验，再执行动作、得到轨迹 τt；任务结束后，judge 给出二值结果 yt，提取器从轨迹中产出新条目，最后并回记忆库。整个闭环可以写成：

Rt = TopKcos(qt, M, k)   →   τt = πL(qt, Rt)
yt = Judge(qt, τt)   →   M ← M ∪ E(qt, τt, yt)
§3.2 · 检索、执行、判定、提取、巩固；E 每条轨迹最多产出 3 条记忆（Appendix A.2）

每条记忆条目的结构是固定的三件套（§3.2）：

title

一句话标识策略

例如「先检查分页模式，再决定是否滚动」；它让条目可以被快速检索、去重和人工检查。

description

一句话概括适用范围

说明这条策略解决哪类问题，而不是复述某一次任务的具体页面或字符串。

content

可执行的推理步骤

记录决策理由、操作顺序、需要警惕的坑；提取提示明确要求「不要提具体网站、查询或字符串内容」（Appendix A.1）。

成败的差异体现在提取提示里。成功轨迹的提示要求先想「为什么成功」，再总结可迁移的策略；失败轨迹的提示要求先反思「为什么失败」，再写出今后避免同类失败的教训（Appendix A.1 的 Figure 9）。两条提示都限制每条轨迹最多 3 条记忆，且不能重复或重叠。提取器与 Agent 使用同一个 backbone，温度设为 1.0；judge 的温度设为 0.0 以保证判定可复现（Appendix A.2）。

检索侧刻意保持简单：用 gemini-embedding-001 编码查询，在记忆池上做余弦相似度搜索，默认 k=1；检索到的条目按「标题 + 内容」拼进 system prompt（Appendix A.2）。巩固也只是简单并集，没有遗忘、合并或置信度更新。论文在 Limitations 里明确说，这是为了把变量隔离在「记忆内容」上，而不是主张这套检索/巩固已经最优。

04

不训练参数，但每次任务要多付一次 judge 和一次提取

把「记忆」当成推理时的额外调用：增加的主要是 LLM-as-a-judge 与记忆提取，不是梯度更新。

论文在 Appendix C.2 统计了每条轨迹的平均 token 消耗，拆成 action generation、LLM-as-a-judge、memory extraction 三部分。ReasoningBank 的总量是 53,054.5，No Memory 是 50,847.4；净增 2,207.1，相对 +4.3%。有趣的是，ReasoningBank 的 action generation 反而比 No Memory 少 1,541.3 token：记忆让轨迹更短，部分抵消了 judge 与提取的开销。

固定开销

judge 与提取各一次

每条轨迹完成后，judge 调一次（温度 0.0），提取器调一次（温度 1.0，最多 3 条）。Appendix A.2 只给了这些调用设置，没有给出这两次调用的成本模型。

可变开销

rollout 数由 MaTTS 的 k 决定

MaTTS 并行要生成 k 条轨迹，串行要做 k 轮 refinement；论文的 scaling 实验用 k=5（§4.3）。因此 Table 5 的 +4.3% 不能直接外推到 MaTTS 的部署成本。

还有一个实现层面的约束：judge 和提取器都用与 Agent 相同的 backbone，而不是单独训练的模型（Appendix A.2）。这让方法容易复现，但也意味着「记忆质量」与「Agent 能力」推断绑定：换一个更弱的 backbone，judge 和提取器也会一起变弱。论文在 Appendix C.4 用 Gemma-3-12B-Instruct 做了小模型验证：WebArena-Shopping 从 17.1 升到 24.1（+7.0 个百分点，相对 +40.9%）；同一张表里 Synapse 为 16.0、AWM 为 21.4，ReasoningBank 的平均步数也最少（11.8）。这说明收益不限于专有前沿模型，在 Gemma-3-12B 上也能获得收益；但 24.1% 仍明显低于 WebArena 主实验中 Gemini-2.5-flash 的 48.8%。

05

一个闭环，两种扩展：并行做对比，串行做反思

ReasoningBank 负责「把经验变成条目」，MaTTS 负责「让更多 rollout 产出更好的条目」。

下面的流程图按 §3.2 重绘，不是论文原图。它只覆盖检索、执行、judge、提取、巩固这条主闭环，没有画出 MaTTS 的并行/串行分支，也没有画出 prompt 的具体模板与 Best-of-N 的聚合细节。

MaTTS 的两种扩展都建立在这条闭环上，但「多出来的轨迹」怎么用不同。并行扩展对同一个查询生成 k 条轨迹，让它们互相比较，提炼在多条轨迹里都成立的模式，过滤偶发的伪解；串行扩展在同一条轨迹上多轮 self-refinement，把中间笔记、纠错和反思也当作记忆信号（§3.3）。前者强调跨轨迹的对比，后者强调轨迹内部的修正。

并行扩展

self-contrast：k 条轨迹互相校验

同一任务生成多条轨迹，模型比较它们的共同推理模式与分歧点，把稳定成立的部分写进记忆，把只在某条轨迹里成立的伪解过滤掉。最终指标用 Best-of-N 聚合（§4.3、Appendix A.3）。

WebArena-Shopping、Gemini-2.5-flash：k=1 的 49.7 升到 k=5 的 55.1（+5.4 个百分点，相对 +10.9%）。

串行扩展

self-refinement：中间笔记也进记忆

一条轨迹先完成，再迭代修正；修正过程中的中间笔记记录了「原本怎么想、后来为什么改」，这些信号可能不会出现在最终答案里，但对提炼策略很有价值（§3.3）。

同一设置：k=1 的 49.7 升到 k=5 的 54.5（+4.8 个百分点，相对 +9.7%）。

扩展不是无条件有效。论文同时给了两条对照：无记忆的 MaTTS 从 39.0 只升到 42.2（+3.2 个百分点，相对 +8.2%）；在 k=5，ReasoningBank 的 MaTTS 并行是 55.1，vanilla TTS（MaTTS w/o aggregation）是 52.4，差 2.7 个百分点；串行是 54.5 对 51.9，差 2.6 个百分点。论文的解释是：没有好记忆时，多出来的 rollout 只是重复探索，甚至把噪声带进记忆；有了 ReasoningBank，rollout 的多样性才会变成可对比的信号。

口径提醒

Table 1 的 +MaTTS 是 pass@1，Figure 4 是 BoN

Table 1 的题注把 +MaTTS 行标为 “parallel scaling, k=5, pass@1”；§4.3 又说并行扩展 “compute Best-of-N (BoN) as the final metric”。页面不把两处数字当成同一口径：引用 55.1 时标 Figure 4 / BoN，引用 Table 1 的 51.8 时标 pass@1。原文没有说明 Table 1 的 +MaTTS 行与 Figure 4 的 BoN 如何对应。

06

三个 backbone 都涨，但检索更多经验反而更差

反直觉 1

失败经验对 ReasoningBank 有益，对 AWM 有害

同样是加入失败轨迹，ReasoningBank 从 46.5 升到 49.7（+3.2 个百分点），Synapse 从 40.6 升到 41.7（+1.1 个百分点），AWM 从 44.4 降到 42.2（下降 2.2 个百分点）。论文的解释是：ReasoningBank 的提取提示会把失败转成「预防性教训」，而只存成功 workflow 的 AWM 没有处理失败信号的结构（§5、Figure 7）。

反直觉 2

judge 只有 72.7% 准确率，70%–90% 区间内波动不大

论文在 WebArena-Shopping 上先测了 judge 与 ground truth 的一致率，为 72.7%；然后模拟 100% 到 50% 的不同 judge 准确率。论文的结论是：在 70%–90% 的合理区间内，ReasoningBank 的成功率差异不大；100% 准确率的设置最好（§5、Figure 8）。这说明方法对 judge 噪声有一定容忍度，但不等于 judge 可以被忽略。

07

它解决的是记忆内容，不是记忆架构；小样本和弱 backbone 上要谨慎

把论文明确写出的边界、以及页面对表格条件的观察放在一起，避免把「总体领先」外推成「每个子集都领先」。

边界 1

增益随 backbone 变小，Claude 上只有 +4.6 个百分点

同一个 WebArena，Gemini-2.5-flash 的总体增益是 +8.3 个百分点，Gemini-2.5-pro 是 +7.2，Claude-3.7-sonnet 只有 +4.6（Table 1）。Claude 的 Multi 子集在 ReasoningBank 未加 MaTTS 时从 0.0 到 3.4，仍然很低；+MaTTS 行为 10.3（Table 1）。论文没有给出「为什么 Claude 收益更小」的解释，页面也不替它补原因。

边界 2

Multi 子集只有 29 题，单题约 3.4 个百分点

Table 1 的 Multi 列标注 29 题；按 100 / 29 计算，单题约 推断（由题目数反推）3.4 个百分点。论文在 §4.2 说 Multi 上「achieves a notable gain of +4.6 averaged SR over the strongest baseline」，但这个小样本上的均值需要谨慎解读；逐行差值见 Table 1。

边界 3

WebArena 的 Map 域被排除

论文脚注 3 写明：因为网站问题，参照 Miyai et al. (2025) 排除了 Map 域，以保证公平比较。因此 Table 1 的 5 个子集不是 WebArena 的全部域；页面不把 684 题说成「整个 WebArena」。

边界 4

只优化记忆内容，检索与巩固刻意简单

Limitations 明确说：论文没有广泛比较 episodic / hierarchical memory，也没有做复杂的自适应检索或分层巩固；这些是正交的记忆架构问题。当前的巩固是简单并集，没有遗忘、合并、冲突消解或置信度更新（Appendix A.2、Limitations）。

什么时候别用

没有可靠 judge、任务高度模糊、或无法承受长期记忆增长时

ReasoningBank 的前提是 judge 能把成败分开；在任务目标模糊、最终状态难以判定的场景，judge 的 72.7% 一致率推断可能成为瓶颈（依据 Appendix E 对 judge 噪声的讨论与 §5 的校准结果）。它也没有解决记忆库持续增长的问题：推断长期流式任务会不断累积条目、需要关注容量管理（依据：Appendix A.2 说新条目直接加入、无额外剪枝；原文没有讨论长期容量管理，这一判断是页面推断）。提取上限分两种设置：单轨迹最多新增 3 条（Appendix A.1、A.2），MaTTS 并行把多条轨迹合并提取时最多 5 条（Appendix A.3）。MaTTS 的 k=5 需要更多 rollout；原文没有给出 MaTTS 的成本模型（§4.3 只说明 k=5 的规模设置），推断按每条轨迹一次 rollout 的朴素估计，成本会随 k 放大（依据：§3.3 对缩放因子 k 的定义；Table 5 的 +4.3% 为单轨迹口径，不含这部分）。

论文的未来方向也印证了这些边界：它建议做组合式记忆（把多个条目组合成更高层策略）、分层记忆架构（episodic / working / long-term）、以及更强的检索控制器；这些都没有在当前实现里（Appendix D）。所以更准确的定位是：ReasoningBank 提供了一个「记忆内容」的强基线，而不是一个完整的长期记忆系统。
