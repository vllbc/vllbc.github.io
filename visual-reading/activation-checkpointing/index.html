Activation Checkpointing：
丢掉激活，反向再算一遍

训练显存里最先爆的往往不是参数，而是每层都要留到反向的激活。论文把 n 层切成若干段，只保存段边界，反向时从边界重放前向——峰值从 O(n) 降到 O(n/k + k)，代价是每步多一次前向。 PyTorch 的 use_reentrant 又决定这次重放是整段执行还是算够即停。

Tianqi Chen, Bing Xu, Chiyuan Zhang, Carlos Guestrin arXiv 1604.06174v2 ↗ PyTorch 源码 @2ee7a63 ↗
TL;DR · 30 秒抓住核心

反向要用的输入张量必须活到反向。矩阵乘 y = Wx 算 ∂L/∂W 要用 x，所以每层至少留一份激活；层数、batch 线性增长，seq 的 attention 项按 s² 增长（5bs²a），而参数和优化器状态不随 batch 变。

Full checkpointing 只保存每个段的入口，段内激活全部丢掉；反向从入口重算。段数 s、段长 k，峰值约为 (s + k)·A；k ≈ √L 时最小，约 2√L·A，代价是一次额外前向。

Selective checkpointing 只重算计算便宜的算子。Transformer 里典型做法是保留 MLP 激活、重算 attention 的 s² 矩阵（本页类比，推断）：显存省得比 full 少一点，算力几乎不涨。PyTorch 的 SAC（selective activation checkpointing）只支持 use_reentrant=False。

01

激活不是参数：层数、batch 线性涨，attention 项按 seq² 涨

先算清楚反向到底要留什么，才知道 checkpoint 能省哪一块。

参数、梯度、优化器状态的大小只跟模型参数量有关；激活不一样。以最普通的矩阵乘为例：

y = W·x   →   ∂L/∂W = (∂L/∂y)·x⊤     ∂L/∂x = (∂L/∂y)·W⊤
算 W 的梯度要用输入 x，算 x 的梯度要用 W；x 必须留到反向。这就是激活显存的来源

所以每层的输入不能算完就释放。序列越长、batch 越大，这份“留给反向的张量”就越大。按 Transformer 的逐项估算，每层激活可以写成：

mact ≈ L · seq · bs · h · (34 + 5 · nheads · seq / h) bytes
按笔记《显存占用计算》§训练时的逐项相加：attention 11bsh + 5bs²a，MLP 19bsh，两层 LayerNorm 4bsh；表中单位是 bytes

取一个参考配置：bs=1、seq=2048、h=4096、heads=32。代入 Table 1（本页推导）后每层约 956 MB（≈912 MiB），32 层约 30.6 GB（28.5 GiB）——还没算参数、梯度和优化器状态。长上下文训练里，激活经常先于参数把显存吃满。

核心矛盾

反向要的是“每层的输入”，而不是“每层的输出”

如果只是把输出丢掉，反向就算不出梯度；如果把每层输入都留着，显存就是 O(L)。checkpoint 的做法是：只留少数几个入口，其他输入在反向时重新算出来。它不是减少计算，而是把“存”换成“再算一遍”。

论文给出的数量级是：1000 层 ResNet 从 48G 降到 7G，运行时间多 30%（Abstract、§5.4）。这两个数字是本页后面所有讨论的锚点，但它们有明确条件——ImageNet、batch 32、224×224、Titan X（§5.1、§5.2、§5.4）。

02

全存、全查、查一部分：三种 checkpoint 粒度

Full 把整段丢掉，selective 只丢重算便宜的那部分；两者的显存下限不一样。

none

全部保留

每层输入都留到反向。显存 M = L·A，没有重算，训练最快，但 O(L) 随层数线性涨。

卡在：长上下文、大 batch 时直接 OOM；加模型并行或 offload 又会引入通信/PCIe 开销。

full

按段丢弃

每 k 层为一段，只存段入口。反向从入口重放整段，峰值约 (s + k)·A，s = ceil(L/k)。

卡在：重算粒度粗。段内每个算子都被重放，哪怕其中很多算子的激活又小又便宜。

selective

按算子丢弃

保留重算昂贵的算子（MLP），只丢重算便宜的算子（attention 的 s² 矩阵）。显存有下限，但算力开销小（本页对 Transformer 的类比，推断）。

卡在：要先知道哪些算子值得丢；策略错了会既没省多少显存、又增加重算。

粒度还可以再分一层：checkpoint(fn, ...) 由调用者手写边界；checkpoint_sequential 按层数均分成 segments 段；checkpoint_wrapper 以 module 为单位；apply_activation_checkpointing 用谓词选子模块；SAC 则细到 ATen 算子。粒度越细，越能贴近“只丢便宜货”，但实现和调参也越复杂。

论文的 §4.2 给的是同一原则：保留计算昂贵的算子，丢掉计算便宜的算子。原文的例子是 Conv-BatchNorm-Activation：保留 convolution 的结果，丢掉 batch norm、activation、pooling 的结果。把它套到 Transformer 上，就是保留 MLP、重算 attention——这是本页的类比，论文没有给 Transformer 的这张表（推断，依据 §4.2 的原则）。

03

切成 s 段，峰值从 L 降到 s + k

论文 Eq.1 的全部内容；k ≈ √L 时最优，两端都退化到 L + 1 个单位。

论文把 n 层网络切成 k 段，每段只保留段输出，段内激活丢掉。用本页的记号重写（L 层、段长 k、段数 s = ceil(L/k)）：

cost-total = maxi=1…s cost-of-segment(i) + O(s)  =  O(k) + O(s)   →   k ≈ √L 时 O(2√L)
论文 §4.3 Eq.1。原文的 n 是本页的 L，原文的 k（段数）是本页的 s；段内激活 O(L/s)≈O(k)，段边界 O(s)

把常数项也写出来：峰值约为 (s + k)·A，其中 A 是每层一份激活的字节数。对 s + k 求最小，s = L/k 时得到 k = √L，峰值 2√L·A。这是论文 Eq.1 的计法：段输出和段内激活分开算；精确到单个张量时，段输出会在两边各算一次，差 1 个单位，不影响 O(√L)。两端的退化也值得记住：

  • k = 1：每层一段，s = L，按论文计法峰值 L + 1 个单位；精确计法减掉重叠后就是 L。两种计法都说明：逐层 checkpoint 不比全存省。
  • k = L：只有一段，s = 1，论文计法 1 + L；精确计法同样是 L。没有边界可省，只剩重算。
  • k ≈ √L：段数和段长平衡，峰值最小。L=1000 时是 2√1000 ≈ 63 个单位，而不是 1000。

计算侧：每个段在反向被重放一次，段长合计 L 层，所以额外计算约等于一次完整前向。论文说 backward 本身接近 forward 的两倍，因此总训练算力的增量约为 1/(1+2) = 33.3%；实测运行时间多 30%（§5.4）。这两个口径不同：33.3% 是按 §4.3 的时间比例折算（本页估算），30% 是论文的实测 runtime。

手算：两组参数，三种模式 与 JS 输出逐位一致

组 1：L=32，A=912 MB，k=4。 s=ceil(32/4)=8。

  • none：M=48×512=24,576 MB=24.6 GB；无重算。

  • selective：Munits=48×(1−40/57)+(8+6)×(40/57)=816/57+560/57=1376/57=24.140351；M=24.140351×512=12,359.9 MB=12.4 GB；显存节省 1−24.140351/48=49.7%；额外前向 (1/13)×48=3.692308 层，即 7.7% 次前向；总算力 3.692308/(3×48)=2.6%。

selective 的常数怎么来的：m=5·2048²·32/(34·2048·4096+5·2048²·32)=40/57=0.701754，f=4·2048²·4096/(24·2048·4096²+4·2048²·4096)=2/26=1/13=0.076923。这组数字对应 Table 1 的参考配置；换 seq/h 要重算。

这个模型简化了什么：它按论文 Eq.1 的段模型计账，假设各层激活相同、每个段都被完整重放；段输出和段内激活分开计数，精确到张量时会重叠 1 个单位（k=1 或 k=L 时正好等于全存）。没有计入参数/梯度/优化器状态、显存碎片、通信和 allocator 开销。PyTorch non-reentrant 的 early_stop 可能让重算提前停止，checkpoint_sequential 又会让最后一段不做 checkpoint——真实值会和这里略有出入。selective 的“只丢 s² 矩阵、只重算 attention core”是按 §4.2 原则做的类比，不是论文测量。

04

PyTorch 里真正要选的是 reentrant 还是 non-reentrant

两者不是性能开关，而是 autograd 语义不同；选错会直接报错，或者得不到想要的梯度。

容易写错

直接调 checkpoint() 时，省略 use_reentrant 仍会走 True

在 pytorch@2ee7a63 里，use_reentrant=None 会先发 warning，然后赋值 True（torch/utils/checkpoint.py:650-660）。所以“推荐 False”不等于“默认 False”：要么显式传 False，要么用 checkpoint_wrapper（它默认 NO_REENTRANT，见 checkpoint_wrapper.py:120-135）。源码还说明未来会对省略参数直接报错。

early_stop

non-reentrant 不会把整段无条件重算完

non-reentrant 的重算钩子在“反向需要的张量都已重建”时抛出 _StopRecomputationError（checkpoint.py:1328-1331）。所以论文的“一次额外前向”是段级模型的上界；PyTorch 的实际重算量取决于这段反向到底要多少中间张量。reentrant 没有这个早停，early_stop 参数在 True 下被忽略（checkpoint.py:563-567）。

RNG

dropout 的重放要回到原来的随机状态

preserve_rng_state 默认 True：重算前恢复 forward 时的 CPU/device RNG 状态（checkpoint.py:1975-2018）。否则 dropout 的 mask 会变，重算出的激活和原来不一致，梯度就错了。源码还注明：在 torch.compile 下这个 flag 不生效，始终保留 RNG 状态（checkpoint.py:533-535）。

FSDP

重算的 forward 不能再触发一次 unshard/reshard

FSDP 在 HandleTrainingState.BACKWARD_PRE 状态下直接跳过 _pre_forward 的 unshard/注册逻辑（fsdp/_runtime_utils.py:373-380），_post_forward 也跳过 reshard/注册（:468-471）。反向重算发生在这个状态里，参数已经 unshard，跳过才能避免把同一套 forward 逻辑再走一遍。

DeepSpeed

自己的 CheckpointFunction，多了分区和 CPU offload

DeepSpeed 的 CheckpointFunction 是从 torch.utils.checkpoint 改的，docstring 列了额外能力：RNG tracker、model parallel tracker、activation partitioning、contiguous memory、CPU checkpointing（deepspeed/runtime/activation_checkpointing/checkpointing.py:568-575）。配置键包括 partition_activations、number_checkpoints、contiguous_memory_optimization、cpu_checkpointing（config.py:27-43）；partition_activations 把激活按模型并行 rank 切开（checkpointing.py:1171-1175）。它在 torch.no_grad() 下跑前向（:626-627），不要把它和 PyTorch 的 non-reentrant 语义混为一谈。

还有一个实现细节：checkpoint_sequential 的 docstring 写明“除最后一段外都不保存中间激活”（checkpoint.py:720-723），代码里最后一段确实直接跑普通前向（:795-805）。最后一段不 checkpoint 不会增加峰值——反正反向第一步就要用它的激活——但会少一次重算。这也是为什么真实框架的“额外一次前向”通常略小于论文的段级上界。

05

前向只留段边界，反向从边界重放

12 层、每 4 层一段的例子：3 个检查点 + 4 层段内激活 = 7 个单位，而不是 12 个。

这张图也解释了为什么 k 不能随便取：段太长，段内激活 k 变大；段太短，检查点数量 s 变大。两者相加在 k≈√L 处最小。图里 L=12，√12≈3.46，所以 k=4 已经接近最优；k=3 或 k=4 都是 7 个单位。

反直觉的地方在于“多一次前向”并没有让运行时间翻倍：论文的解释是 backward 本身接近 forward 的两倍，所以多一次 forward 只多约 1/3 的算力，实测是 30%。这也是为什么在显存受限的 GPU 上，重算常常比“省显存但增加 memory traffic”的方案更划算——但论文只报告了 ResNet/LSTM 的这组设置，不能把它当成所有模型的固定比例。

07

它只省激活；参数、优化器状态和通信一分不少

什么时候别用：激活不是瓶颈、前向不可重复、或者框架已经把 attention 重算掉了。

适合

激活是主瓶颈，前向可重复

长上下文、大 batch、深层网络；参数/优化器状态已经通过 ZeRO、FSDP 或量化处理过，剩下的显存大头是激活；前向没有不可重放的副作用，或者 RNG 状态能被正确恢复。

不适合

激活很小，或算力已经卡死

短序列、小 batch、浅层模型：激活本来就不是大头，重算只会白花时间。训练已经 compute-bound、GPU 利用率打满时，再增加一次前向会直接拖慢吞吐。

  • 不省参数和优化器状态。checkpoint 只处理“留给反向的激活”。7B 模型的 bf16 参数、fp32 master weights、Adam 的 m/v 仍然照占；参数显存要靠 ZeRO/FSDP/量化，不是 checkpoint。
  • 前向必须可重复。源码明确警告：如果反向时的 function 调用和 forward 不同（比如依赖全局变量），checkpoint 版本可能不等价，轻则报错，重则静默给出错误梯度（checkpoint.py:466-471）。dropout 的 RNG 由 preserve_rng_state 处理，但自定义随机源、数据依赖的全局状态不在保护范围内。
  • reentrant 的限制是硬限制。use_reentrant=True 不记录 autograd 图、只支持不带 inputs 的 torch.autograd.backward、要求至少一个输入/输出有梯度、不处理嵌套结构、段内不能有 detach 张量。需要 autograd.grad、kwargs、嵌套结构或 selective 策略时，必须用 False。
  • SAC 需要策略，不是免费开关。create_selective_checkpoint_contexts 要给出每个算子的 MUST_SAVE / PREFER_RECOMPUTE 决策；策略错了可能既没省多少显存，又把重算成本加上去。而且 SAC 通过 context_fn 实现，context_fn 仅在 use_reentrant=False 下支持（checkpoint.py:550、674-675、1829）。
  • FSDP/DeepSpeed 的封装各有前提。FSDP 在重算时跳过 pre/post forward 的 unshard/reshard（fsdp/_runtime_utils.py:373-380、468-471）；DeepSpeed 的 partition_activations 依赖模型并行，cpu_checkpointing 则把激活挪到 CPU，换来 PCIe 传输。两者都不是“打开就变快”。
  • 最后一段和 early_stop 会让真实值偏离公式。checkpoint_sequential 不 checkpoint 最后一段（checkpoint.py:720-723、795-805）；non-reentrant 的 early_stop 可能提前停止重算（:1328-1331）。本页的 (s+k)·A 是论文 Eq.1 的段模型，不是每个框架的精确记账。
  • FlashAttention 已经在做一部分。笔记提到 FlashAttention 的反向会重算 attention 矩阵，而不是存下来；对同一段再套 full checkpoint 可能重复劳动。这一点论文没有讨论，使用前先确认框架的 attention 实现是否已经内置重算（工程判断，不是论文结论）。
  • offload 是另一条路。PyTorch 有 offload_wrapper（checkpoint_wrapper.py:106-109、174-193），DeepSpeed 有 cpu_checkpointing（config.py:42-43）。它把激活放到 CPU，省 HBM 但吃 PCIe 带宽；和重算是正交的取舍，不是谁替代谁。
一句话

checkpoint 是显存换时间，不是显存变魔术

当激活是主瓶颈、前向可重复、算力还有余量时，它是把 O(L) 压到 O(√L) 的最直接手段。先算清楚 (s+k)·A 和 1/(1+2) 这两个数，再决定 k 取多少、要不要上 selective——不要先打开开关再找原因。
