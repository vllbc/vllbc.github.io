ZeroSearch：训练时用一个 LLM 假装成搜索引擎

用 RL 教 LLM 搜索，要反复调用真实搜索 API：费用高、返回文档质量又不可控。 这篇论文把搜索引擎换成一个用 SFT 微调过的小模型，在训练里生成「有用」或「噪声」文档， 再用课程式 rollout 让难度由易到难。推理时照样接真实 Google。

Tongyi Lab, Alibaba Group · arXiv 2505.04588 v3 arXiv 2505.04588v3 ↗
TL;DR · 30 秒抓住核心

训练一个「会搜索的智能体」，最贵的一环是环境：每次 rollout 都要真的去问搜索引擎。 论文把它换成一个 SFT 微调的 LLM——提示词里写 useful 就生成能答对的文档，写 noisy 就生成「相关但答不上」的文档，文档质量因此变成可编程的旋钮。

在这个旋钮上，论文加了课程式 rollout：训练步数越往后，生成噪声文档的概率 pi 越高（Eq. 1）。模型先学会输出格式和基本搜索，再被逐步推入能吵的检索环境。

默认模拟器是 SFT 过的 Qwen-2.5-14B-Instruct。在 Table 3 里，六对「同骨干、同算法」的对比中，ZeroSearch 的平均 EM 都高于真实搜索的 Search-R1。 代价是模拟器要占 GPU：Table 8 里 14B 模拟器约 $70.8 GPU 成本，换掉 Google 约 $586.7 的 API 成本。

01

难的不是让 LLM 会搜，而是让它「练得起」搜索

读完你应该知道：把搜索引擎放进 RL 训练循环，会同时炸掉预算和训练稳定性。

给 LLM 接搜索，常见路线有三代：提示词工程（拆查询、多轮检索）、SFT（让小模型模仿搜索轨迹）、测试时扩展（推理时做 MCTS 之类的搜索树）。论文认为前两者太依赖提示与模型本身能力，后者推理开销大§1。

更近的一步是直接拿 RL 去训「什么时候搜、搜什么、拿到结果怎么用」。Search-R1、R1-Searcher、ReSearch 都走这条路；DeepResearcher 和 WebThinker 则直接与 Google 这类商业引擎交互，训练环境最接近真实§1。问题就出在这一步：

成本

rollout 是反复发生的

RL 要多次采样、多次 rollout，训练过程可能涉及数十万次搜索请求。每次都要付 API 钱，规模一上去费用就不可控§1。Table 8 给了一个小规模的账：约 64,000 次查询、约 12 小时，Google 路线的 API 成本是 $586.7。

质量

返回什么，你说了不算

真实引擎返回的文档质量不可预测，给训练注入噪声。文档太差，模型学不会正确理解任务；文档太好，后段训练又缺乏挑战Appendix A。这种「忽好忽坏」是 RL 不稳定的来源之一。

所以问题的真正形状是：能不能把「搜索环境」从外部服务搬进训练循环内部，让它的成本接近零、质量由训练者调节？

02

前人两条路：静态语料够稳定但不够真，真实引擎够真但不够稳

论文把相关工作切成两格，每一格各有一个结构性短板；ZeroSearch 要同时拿到两边的长处。

A 路

Search-R1 / R1-Searcher / ReSearch：本地静态语料

做法：在 Wikipedia 之类的静态本地语料上做检索，RL 只训搜索与推理行为§2.2。

长处：语料固定，环境可控。

短板：抓不住真实世界交互的复杂性——返回的是「检索到的片段」，而不是引擎在实时场景里给你的那套东西。

B 路

DeepResearcher / WebThinker：接真实商业引擎

做法：训练时直接与商业搜索引擎交互，环境最接近真实网页搜索§2.2。

长处：分布最真实。

短板：文档质量不可控 + API 成本高、受限流，系统规模被卡住。

论文的定位很明确：保留 B 路的「文档长什么样」的文本风格，但把生成方换成自己可控的模型。作者给的判断是——真实引擎和模拟 LLM 的主要差别只在返回内容的文本风格，而这种风格可以靠轻量 SFT 补上§1。

这也决定了论文只拿 Search-R1 做 RL 类基线：理由是不需要复杂奖励设计、数据筛选或复杂训练流水线，可以和模拟引擎做直接对等的比较§4.2。

03

核心方法：把「生成什么质量的文档」变成一个提示词开关

读完你应该知道：模拟器怎么被造出来、「useful / noisy」两个词到底控制了什么、以及为什么少了 SFT 就退化。

3.1 三步造出模拟器（Search Simulation Tuning）

  • 收轨迹：让 LLM 以多轮方式和真实引擎交互，直到给出答案，从中抽成「查询—文档」对§3.3。
  • 打标签：用 LLM 作裁判，逐条判断文档是否包含足够信息回答对应查询：够 → useful，不够 → noisy§3.3。
  • 轻量 SFT：让模型学会按查询生成两类文档。提示词里还会带上问题和标准答案，用来拓宽模拟器的知识边界；微调后它就能在 rollout 时动态控制质量§3.3。

3.2 模拟模板（Table 2）

Table 2 的模板里，中括号中的 useful / noisy 是可替换的词，其余是固定上下文。

You are the Google search engine. Given a query, you need to generate five [useful / noisy] documents for the query. The user is trying to answer the question: [question] whose answer is [ground truth]. Each document should contain about 30 words, and these documents should contain [useful / noisy] information. Query: [query] [Useful / Noisy] Output:

Table 2：每次生成五篇约 30 词的文档；问题与标准答案也放进提示，帮助扩展模拟器的知识覆盖

策略模型一侧沿用 Search-R1 的多轮模板（Table 1）：<think> 推理、<search> 发起查询、<information> 接收模拟文档、<answer> 作答。检索文档数在所有方法里统一为 5§4.3。

模拟器并非单调受益？7B / 14B 的个别列反向点开看数据与推断

看 Table 4 的单列：SFT-14B 的 PopQA 是 41.40，低于 SFT-7B 的 45.40，也低于 Prompt-7B 的 43.40；Prompt-14B 的 TriviaQA 55.40 也低于 Prompt-7B 的 59.40。也就是说，「更大更细调的模拟器」在 Avg 上更好，但不是每一列都更好。

推断（依据：Table 4 单列数字对比）14B 模拟器在生成「noisy」文档时可能更接近真实干扰分布，PopQA 这类依赖实体精确匹配的任务反而更敏感；但论文没有对这一列现象做解释，这里只作为读表时的注意点，不建议据此下结论。

04

训练：文档难度是一条从易到难的曲线，而不是固定难度

读完你应该知道：噪声概率 pi 怎么随训练步数变、三组模型的实际曲线差多少、以及 Random 基线为什么输了。

rollout 时策略模型发出查询，模拟器按 pi 决定生成 useful 还是 noisy 文档。论文用 Eq. 1 把「难度」写成训练步数的函数：

pi = ps +   ( bi/m − 1 ) / ( b − 1 )  ·  ( pe − ps )
Eq. 1 · i 当前步、m 总步数、b 指数底数（默认 4）、ps/pe 初始/最终噪声概率

把 x = i/m 拿掉看结构：(bx − 1)/(b − 1) 是从 0 涨到 1 的曲线，x 很小时它就是 x 本身（线性起步），x 接近 1 时陡增。所以噪声比例前松后紧：前一半训练里模型主要在干净文档上学会格式和基本搜索，后段才被迫处理噪声§3.4。

05

一条 rollout 里，谁在生成文档、谁在学

读完你应该知道：训练时模拟器是冻结的、只在跑的 token 上有梯度，以及为什么这对 PPO / GRPO 都成立。

论文 Figure 1 画的是「没有搜索引擎的 PPO / GRPO」：上面一行是 PPO 的价值模型 + GAE，下面一行是 GRPO 的组内奖励计算，两行的起点都是同一个Rollout Module：模拟 LLM 替代引擎。模拟器参数在整个训练中冻结§3.1。

三个工程细节决定了它跑得稳

  • 奖励用 F1 而不是 EM：初版实验里 EM 奖励容易被打成「答案写长一点以扩大命中」的策略，即 reward hacking；改用 F1 平衡精确率和召回率。格式不加额外奖励，因为模型自己就稳定输出合规格式§3.5。
  • 文档 token 不算损失：rollout 序列里既有策略模型的 token，也有模拟器给的文档 token。对后者不掩码会引入不稳定；LLaMA-3.2-3B 上的消融（Table 7）里，掩码 Avg 为 36.07，不掩码为 34.53，差 1.54 点§3.6。
  • server 与训练并行：实验中模拟器部署在 4×H20，RL 训练在另 4×H20；加更多 GPU 能提高模拟器生成吞吐、加速大规模 rollout§4.3 / §1。

算法侧只测了三种：REINFORCE、GRPO、PPO。以 Qwen-2.5-3B-Base 为策略模型时，Avg 分别为 34.47 / 33.17 / 32.67，REINFORCE 最高；论文说这与 Search-R1 的观察一致§5.4。

6.3 一笔容易误读的账：64,000 从哪来

Appendix D 写的是 batch 64 × rollout 重复 5 × 200 步，直接乘出来是 64,000 次查询；这恰好等于 batch 64 × 1,000 步。两组乘数是对得上的推断（64×5×200 = 64×1,000 = 64,000）。论文没有说明这两个数的对应关系，这里不作为确定结论。

07

边界：模拟器换掉了 API 账单，但换不掉「知识截止」和「GPU 闲置」

读完你应该知道：论文自己承认的局限有哪些，以及从数据能读出的额外限制。

paper

需要 GPU 承诺

论文 §6 的局限讨论很直接：模拟搜索 LLM 需要 GPU 服务器，虽然比商业 API 便宜，却增加了基础设施成本；Appendix D 进一步指出 GPU 利用率不均衡，建议让多个 RL 任务共享一个模拟器 server 来摊薄§6, Appendix D。

data

模拟器的知识边界靠「问题 + 答案」撑

模板里带上问题和标准答案，是为了扩宽模拟器的知识覆盖Table 2。这项设计的代价是：训练数据里模拟器「知道」答案，学习信号来自可用的答案而非真实的「无结果」。推断（依据：Table 2 模板把 ground truth 写进提示，而真实引擎不会）。在这种设定下，模型学到的「没有找到」行为可能偏少。

data

训练集与评测集不完全同分布

训练只用 NQ + HotpotQA 的合并集§4.3；七个评测集里 TriviaQA / PopQA / 2Wiki / MuSiQue / Bamboogle 都是 OOD。Table 4 里 SFT-14B vs Google 的反超本身是在这七个集子上测的，换一组难集需要重新核。

metric

指标只看答案对不对

论文的奖励只看答案准确率（F1），不加格式奖励，也不罚「瞎搜」§3.5。Fig 2c 显示训练中交互轮数随奖励一起上升再稳定§5.3——这意味着「用更少的搜索拿到同样答案」这种效率目标并不在它的优化里。

一句话：ZeroSearch 换掉的不是「真实网页」这件事，而是训练循环里对真实网页的不受控依赖。推理时模型依然面对 Google；模拟器在什么情况下比 Google 更适合做老师，取决于课程设计——Table 4 的 SFT-7B 与 Google 只差 0.72 点，这个差距比 14B 的「反超」更贴近这套方法的稳定预期。
